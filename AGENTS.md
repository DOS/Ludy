# AGENTS.md

Ludy is the open-source Business OS (AGPL). It must run with `docker compose up` and no DOS service. Anything DOS-specific belongs in the private Ludy Cloud layer, never here.

## Who Ludy is for: OPC and SME, AI-first (owner decisions 2026-10-31 and 2026-11-02)

Ludy is for one-person companies and SMEs in Vietnam. Every issue, plan and PR must pass this gate; details and examples are in [docs/product/scope.md](docs/product/scope.md).
- **Fit:** it serves a task a small business does at least monthly. Enterprise models (several entities, SSO, agency consoles and the like) go to the Icebox. When fit is unclear, the owner decides.
- **Smallest slice:** one person can use it with the defaults and no setup.
- **AI part named:** the acceptance says what the AI coworker does in that screen. Model calls go through the AI budget meter, the core works with AI off, and a person approves money, messages and spend.
- **AI is a coworker; Vy is also an assistant:** Vy leads across the apps and is both a coworker and an assistant (trợ lý); each app has its own coworker, never called an assistant (DESIGN.md 1.1, owner 2026-11-10).

## Rules

- **One write path.** Every state change is a command run through `Runtime.execute()` (`packages/kernel-runtime`). No other code writes tenant tables.
- **Schema only via migrations** in `supabase/migrations/<14-digit UTC>_ludy_<module>_<desc>.sql`: idempotent statements, never edit an applied file, never DDL at runtime. Every function sets `search_path = pg_catalog, pg_temp`, never `''`. The runner's hardening guard (`hardeningViolations`) has no bypass flag or warn mode and must never get one: a deploy that fails it is fixed with a forward migration, never skipped.
- **Indexes on hot tables** (`audit_event`, the outbox, `ludy_jobs`; #1791, #1803): build a new one with `CREATE INDEX CONCURRENTLY IF NOT EXISTS`, alone in a file whose leading comment lines include `-- ludy:concurrent-index` (the runner applies it outside a transaction, drops an INVALID index a failed build left, and records the file only once every index is valid with the asked definition). Such an index uses a built-in access method, names nothing of a schema but `pg_catalog`, depends (on a probe build rolled back first) on no function, operator, operator class, collation or type outside it, a cast's function included, and indexes no column of a user range or composite type, so no user code runs outside a transaction. The migration lint refuses anything else in such a file, and any other index build on a hot table (plain `CREATE INDEX`, `ADD UNIQUE` or `PRIMARY KEY` without `USING INDEX`, `REINDEX`). Add a unique or primary-key constraint with `ADD CONSTRAINT ... USING INDEX` on an index built that way.
- **Tenancy:** every tenant table has `org_id`, `PRIMARY KEY (org_id, id)` and RLS via `ludy_kernel.apply_tenant_rls`. Login roles own nothing.
- **Erasable TypeScript only:** Node runs the kernel's and packages' `.ts` by type stripping, so `tsconfig.lib.json` sets `erasableSyntaxOnly`; no parameter properties, enums, namespaces or `import =` (use explicit fields, const objects with a union type, and modules).
- **Money** is NUMERIC in SQL and a decimal string elsewhere; arithmetic through `decimal.js` (`@ludy/l10n-vn` money helpers). Never JS numbers for amounts.
- **AI** calls only in `packages/agent`, through an OpenAI-compatible endpoint. AI output is tainted: deterministic checks decide, humans approve.
- **Public repo:** no secrets, Supabase project refs, internal URLs or real customer data. gitleaks + G1 run in CI and in the pre-commit hook.
- **English:** code, comments and commit messages in English. No em dashes.
- **License line:** every new source file (`.ts`, `.tsx`, `.js`, `.mjs`, `.sql` and the like) carries `// SPDX-License-Identifier: AGPL-3.0-only` (`--` in SQL) in its first five lines, best as the first (after any shebang). The `Docs check` job fails a PR that adds one without it (`tools/ci/spdx-header.mjs`); third-party files keep their own license (the pg-boss migrations, the vendored pgTAP).
- **Docs-only PRs** need no agent review: `pnpm docs:check` and CI (`Docs check` job) must pass.

## Worktrees (several agents work on this repo at once)

- Never edit in the main checkout. Do every task in its own worktree and branch, from a freshly fetched `origin/dev` (use `origin/main` only for a `dev -> main` promotion PR or a main-only docs/CI fix during transition): `.claude/worktrees/<task-name>` (Claude Code), `.codex/worktrees/<task-name>` (Codex), `.cursor/worktrees/<task-name>` (Cursor), `.agents/worktrees/<task-name>` (Antigravity). Never in `.worktrees`, sibling directories, global `_worktrees` folders or temp directories.
- First check `git worktree list` and open PRs. Never edit another task's or agent's worktree or take over its branch; create a new one. A locked worktree belongs to an active agent.
- Never `git checkout`, `reset --hard`, `clean` or bare `git stash` in a path another agent may use; set work aside with a WIP commit.
- Sync with your target base right before merging: rebase on `origin/dev` for task PRs, and merge `origin/dev` cleanly into `origin/main` for promotion PRs (never rebase or squash-rewrite shared `dev` commits inside a promotion PR). Resolve conflicts by keeping both sides unless one is clearly superseded.
- After the merge, remove your worktree with `git worktree remove` (never force), only if `git status` is clean.

## Picking up work (GitHub Project "Ludy")

- Work comes from the board https://github.com/orgs/DOS/projects/8 (issues in DOS/Ludy). One task = one issue = one worktree = one PR, split by feature and built end to end (migration, server, contract, UI, tests).
- Work without stopping (owner decision 2026-10-20): the plans and designs are the backlog. When a task merges, start the next in the same session. Never end a turn to ask whether to go on, or make the owner type "continue", "status?" or "allowed".
- Next task, skipping issues `In progress` or labelled `owner-action`: an open, unclaimed issue in the earliest milestone with work left (M0, M1, M2, M3, then the GA gate; [backlog review](docs/plan/backlog-review-2026-10-17.md)), `priority:P0`, then P1, then P2. None left: derive the next issues from that milestone's acceptance criteria, `docs/plan/*.md`, the ADRs and `DESIGN.md` (each with scope, acceptance criteria, files touched, its plan line linked, and the plan's milestone and priority), then claim and build one. Milestone done: go to the next. The Icebox stays closed until the owner reopens it. Social is not paused (D5 was answered "no for Social" on 2026-10-17, confirmed by the owner on 2026-11-08); its issues are picked like any other line's.
- Stop and ask only when nothing is left to pick or derive, or a step is hard to undo or crosses a line the plans did not draw (judge each case): losing or rewriting data; weakening tenancy, authentication, approval or ledger rules, or changing an invariant on purpose; going against a written decision or accepted ADR; new spending, production or credentials; a person's sign-off (lawyer, accountant). Ask once, issue linked, and keep working on other tasks meanwhile.
- At each task milestone (PR opened, merged, blocked), comment on the issue what is done and what is next. A resumed or compacted session first reads the open issues it claimed.
- New issues: from a plan, the plan's milestone and priority; anything else (idea, nice-to-have, finding outside the plans) to the Icebox as `priority:P3` for the coordinator's weekly triage. A non-blocking review finding (security, code, bot) is a P3 `review-followup` issue in the Icebox, moved into a milestone only when it blocks that milestone's acceptance criteria or a real user hits it; blocking findings are fixed in the same PR.
- Never build what no plan or design calls for. A new customer-visible feature, pricing change or roadmap commitment no plan calls for goes to the owner as a recommendation in the coordinator's digest, whoever asks: no issue, no build until the owner agrees.
- Security work only when the current milestone's checklist needs it (pilot readiness, then the GA gate), or for a real high or critical vulnerability, which is P0 at once.
- Team leads (owner decision 2026-10-25): `Agent <n>: <area>` sessions each own an area and pick its next issue; the coordinator (`Agent 0`) lists them in https://github.com/DOS/Ludy/issues/1210. WIP: a team lead holds one issue `In progress` plus up to 2 background subagents on its area's issues (at most 3); a Product Owner session runs up to 5 concurrent sub-sessions ([docs/product-owner-config.md](docs/product-owner-config.md#sessions), owner decision 2026-11-18); any other session holds one. Never take an issue a team lead claimed. On a priority tie, prefer your last task's area label (`kernel`, `security`, `auth`, `finance`, `web`, `infra`, `tooling`, `cloud`).
- Claim: set Status `In progress` and comment `Claimed by <session or agent name>, branch <branch>`. One GitHub account is shared, so the comment is the lock: re-read after posting; if another session claimed first, pick another task. Never take over a live claim. After 48 hours with no push, PR update or comment a claim is stale: comment `Taking over the stale claim of <session>` with that evidence, then claim.
- Task PRs target `dev` and say `Refs #<n>` (never `Closes`, so the issue stays open until `dev` is promoted to `main`). When a runtime feature PR merges to `dev` and passes verification on `beta` (when configured) or CI and acceptance checks, add the `ready-for-prod` label to its issue; periodic `dev -> main` promotion PRs carry `Closes #<n>` (or close docs/CI-only issues merged directly to `main`). Work in another area (say UI for a new kernel API) becomes a follow-up issue (P3, Icebox, unless it blocks the milestone), not a bigger PR.
- Migrations (#1492): versions are not reserved; use any above `dev`'s newest (and `main`'s if ahead). Right before merging a task PR to `dev`: merge `origin/dev`, `pnpm migration:rebase`, commit, push, wait for green, merge. When the "Migration order" check fails (re-run on open PRs after each push to `dev` or `main`), rebase the same way (pass `origin/main` for a PR targeting `main`); never merge with the old version ([detail](docs/contributing.md#migration-versions)).

## The owner, merging and reporting

- The owner (JOY) does not code, run commands or merge. Agents merge their own PRs: never leave one that meets the bar waiting, and never ask permission to merge.
- Merge bar, on the PR's final head:
  - every CI check green (a neutral result or a review bot's quota notice is not a failure);
  - synced with the target base (`origin/dev` for task PRs, `origin/main` for `dev -> main` promotion PRs) without conflict; a migration PR passes the migration order check;
  - every review thread answered (fix commit, or why not) and resolved;
  - a protected-path PR has its security review (the agent's, or while #95 is pending an independent one its line's PO runs: a fresh-context flagship-model reviewer, never the session that wrote the change);
  - a PR that changes the shared core (the list in [docs/product-owner-config.md](docs/product-owner-config.md#shared-core-review)) also has the Platform PO's review of those files, still valid while those files are unchanged; after 4 hours without one, a stand-in review by a fresh-context flagship reviewer, which the Platform PO checks after the merge (owner decision 2026-11-16);
  - an `## Acceptance` section (what a user will see change, evidence per acceptance item, review results, risk left; docs-only: the change and the docs check result), and the acceptance gate passed: the line PO's for its line's PRs, protected-path ones included, the team lead's for its other and its subagents' PRs, else the session's own.

  Then squash merge task PRs into `dev` (or merge with a merge commit for `dev -> main` promotion PRs so common ancestry between `dev` and `main` stays intact) with the expected head SHA, and remove task worktrees.
- **Promotion and releases (owner decision 2026-11-27):** task PRs merge into `dev` (triggering `beta` deploy when configured); periodic promotion PRs merge `dev` into `main` via merge commit and close promoted issues (`Closes #<n>`). Pushes to `main` deploy only the `apps/web` landing page to Vercel Production (`ludy.vn` / `ludy.so`); backend `pilot` deploys and `app.ludy.vn` (`release-branch.yml`) remain gated on owner-approved `v*` tags.
- Line POs are peers (owner decision 2026-11-07): each works with the owner directly and routes nothing through another PO. The Platform PO's shared-core review is a code-owner review of those files only, not an approval of the PR.
- Review gate before opening a PR (docs-only PRs skip it): `codex review --base origin/dev` (or `--base origin/main` for promotion PRs targeting `main`) in the background, and a fresh-context reviewer given the diff and the issue. Fix what blocks; say in the PR what was not taken and why, or that Codex was unavailable. A review bot out of quota or rate limited has not reviewed: never wait, retry in a loop or work around it; say so in the PR (on a protected-path PR the line PO's independent security review stands in).
- Review checklist (owner decision 2026-11-19): every review (the fresh-context reviewer, a PO's security or shared-core review, an acceptance check) covers these six and the PR's `## Acceptance` gives a line for each, "not applicable" when it is: correctness (logic, edge cases, error paths); security and authorization (roles, step-up, secrets, injection, AI output as data); tenancy (`org_id`, RLS, member scope); money (decimal strings, NUMERIC, approvals); performance (query plans and indexes on hot tables, N+1 reads, unbounded lists or loops, work inside a transaction, web bundle and render cost); accessibility (keyboard, focus, labels, contrast, 44 px targets on a phone). A blocking finding in any of them blocks the merge. A docs-only PR writes one line, "docs only: the six do not apply"; the automated `Security review (agent)` job keeps its own scope.
- Models (owner decisions 2026-10-27, 2026-10-30, 2026-10-31, 2026-11-15, 2026-11-18, 2026-11-21): on Claude Code, POs (the coordinator included) and fresh-context independent security reviews of protected-path PRs run on a flagship model (`Claude Opus`), and sub-sessions and workers run on the host's worker model (Sonnet 5.5, `claude-sonnet-5-5`). ## Protected paths (Decision 7)

- **What is protected** (plan §10, G6; authoritative list `tools/ci/protected-paths.mjs`, paths only; [in full](docs/security/invariant-suite.md#the-protected-paths-in-full)): workflows, `CODEOWNERS`, git hooks, `.gitattributes`, `.gitmodules`, `tools/deploy/**`; agent harness, policy and PO authority config (`.claude/settings*`, `hooks`, `agents`, `.mcp.json`, `CLAUDE.md`, the root `AGENTS.md`, `docs/product-owner-config.md`); every `package.json`, the pnpm lock and workspace, `.npmrc`, vitest and playwright configs, `global-setup.ts`, `global-teardown.ts`; the gate (`tools/ci/**`, `test/invariant/`, `_*.test.sql`, the pgTAP runner); `packages/kernel-runtime/src/**`; the database context guards and migration runner; `approval.ts`, `identity.ts`; auth, OAuth, MCP, public-link resolvers, credentials, export sealing and the HTTP edge (`apps/kernel/src/auth*.ts`, `sessions*.ts`, `http.ts`, `oauth-server.ts`, `oauth-adapter.ts`, `mcp-endpoint.ts`, `mcp-protocol.ts`, `mcp-wake*.ts`, `sign-link.ts`, `sign-direct-link.ts`, `review-link.ts`, `quote-link.ts`, `report-link.ts`, `booking-page.ts`, `media-ticket.ts`, `stream.ts`, `credentials.ts`, `export-seal.ts`, any `auth/` or `auth.ts`/`auth-*.ts`); sandboxes, PDF sealing, media wrapper and extension manifest policy (`apps/extract/src/sandbox.ts`, `apps/extract/src/seal.ts`, `apps/media/src/ffmpeg.ts`, `apps/extension/src/manifest-policy.ts`); `supabase/migrations/`, `supabase/shared-variants/`; `LICENSE`, `CLA.md`, `agent-autonomy.md`.
- **The invariant suite** is every file under a `test/invariant/` directory plus the pgTAP gate files `supabase/tests/database/_*.test.sql`. Read [docs/security/invariant-suite.md](docs/security/invariant-suite.md) before changing any of it. Keep each directory self-contained: no imports or fixtures from outside it but the code under test. New security tests go there; product flows stay in ordinary `*.db.test.ts` files.
- **What runs** (`.github/workflows/protected.yml`, every PR; both jobs pass in seconds when no protected path changed):
  - `Invariant suite (from base)` runs the base branch's suite against the PR's code. It fails on a failed or skipped test, a base file changed on disk, or a `node_modules` path committed or under a test directory (#1644, #1647, #1786). The `ci` job still runs the PR's copy.
  - `Security review (agent)` reviews protected-path PRs for security, tenancy, authorization and money against the base branch's policy (`git show <base>:AGENTS.md`) and posts a `## Security review (agent)` comment. Without the `ANTHROPIC_API_KEY` secret (owner action, #95) it passes with "Security review pending owner setup" and the line's PO runs an independent security review (plus the Platform PO's review of any shared-core files). A fork PR touching protected paths fails with "Maintainer security review required".
- **A red job:** read the job summary, or the PR's error annotations and the "Report the failed tests" log (#498). It means the PR's code breaks an invariant as the base branch (`dev` or `main`) defines it: fix the code, never the test in the same PR. Changing an invariant on purpose is an owner decision, said in the PR: once the owner approves it in the coordinator's chat, the coordinator merges over the red check after the security review (the owner never merges), or it lands in two steps with a test that accepts both behaviors first. Fix the reviewer's blocking findings before merge.
- A PR editing `protected.yml` or `tools/ci/` runs its own edited workflow: the reviewer and the session check it with extra care.

## Local resources (owner order 2026-11-26, superseding 2026-11-17)

Many agents share the owner's one machine, which he also uses himself. Keep local work strictly lightweight; GitHub Actions CI runs typecheck and all tests.
- **No local typecheck, vitest or Playwright ([owner order 2026-11-26](https://github.com/DOS/Ludy/issues/1210#issuecomment-7171329671)).** Never run `tsc`, `tsgo`, `pnpm typecheck`, `pnpm --filter <package> typecheck`, `vitest`, `pnpm test`, `pnpm test:db`, `*.db.test.ts` or Playwright (`pnpm test:e2e`) on this machine, even for a single package or file. `tools/local-guard.mjs` blocks root `typecheck`, `test`, `test:db` and `test:e2e` unless `CI=true` or a human developer sets `LUDY_FULL_LOCAL=1` on their own personal machine (agents never set `LUDY_FULL_LOCAL=1`). Limit local checks strictly to fast, low-CPU tools (`oxlint --deny-warnings`, `pnpm lint`, `pnpm docs:check`, `node tools/ci/spdx-header.mjs`, `node tools/ci/pii-scan.mjs`, `node tools/ui-colors.mjs`, `node tools/ci/migration-order.mjs origin/dev`, `node tools/ci/migration-lint.mjs`), then push and let CI run typecheck, unit/DB/invariant tests and Playwright. CI green on the PR's head is the test evidence the merge bar asks for; the rest of the bar (reviews, threads, Acceptance) still applies.
- **Shared local Postgres for `pnpm db:types` only:** the container `ludy-pg17-shared` (`postgres:17@sha256:2d2b8998d31037bf721cfdf764d76ba74171b4fab3431b7f72c27c56ddbdf9e3`, as in CI, on `127.0.0.1:55432`, `LUDY_TEST_ADMIN_URL=postgresql://postgres:postgres@127.0.0.1:55432/postgres`) is reserved strictly for `pnpm db:types` after migrations affecting `ludy_tenant` tables or grants (never for `*.db.test.ts` or `pnpm test:db`), one session at a time. Start it only if it is missing; never start a Postgres of your own. Leave leftover-role cleanup to the coordinator.
- **At most one local `docker compose` stack on the machine**, shared. Check UI on that stack; the pilot is never a test target.
- **Stop what you start:** no `tsc --watch`, dev server, test watcher, background compiler or container left running after your step, and never run heavy compile/test commands locally.
- Deeper or cloud-environment testing runs in CI, or on a test VM the owner approves; never on the pilot host.

## Updating pinned images

Every image is pinned as `image:tag@sha256:<digest>`, so a re-pushed tag cannot change what runs. To bump one, use the multi-arch index digest in every file that uses the image, from a build at least one day old: [procedure](docs/contributing.md#updating-pinned-images).
