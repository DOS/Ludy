# 0044. Issuing e-invoices: one port, one adapter per provider, the seller's own account

- Status: Proposed (2026-11-03). Nothing here is built. The first build issues run on an offline provider and need no decision from the owner; point 3 (who approves the posting) needs the Platform PO's security review before it is built.
- Date: 2026-11-03
- Deciders: owner (JOY), who directed on 2026-11-03 in the Accounting PO chat that Ludy integrates with the providers that have an API and does not become a provider; the engineering choices below by the Claude Code session that wrote the plan
- Builds on: ADR-0025 (channel layer: connections, the credential broker, adapters with an egress allowlist, `external_call`), ADR-0013 (evidence storage and integrity), ADR-0018 (untrusted content, the `crove-extract` sandbox), ADR-0027 (the open-source core runs without any DOS service), ADR-0039 (bank feed connectors, the same shape of port and adapters), the draft and proposal paths of finance (#313 sales, #674 signature check, #916 corrections)
- Issue: [#2497](https://github.com/DOS/Ludy/issues/2497); the plan is [einvoice-issue.md](../plan/einvoice-issue.md)

## Context and problem statement

Ludy records sales e-invoices but cannot issue one. Issuing needs a provider that numbers, signs with the seller's certificate and obtains the tax authority's code (Decree 254/2026, in force since 2026-07-01; the plan's section 3 lists the rules and what could not be verified). The owner decided that Ludy is not a provider: each org brings its own provider account, and Ludy calls that provider's API for it.

The survey of the plan (section 4) found one first-party public specification (MISA meInvoice), several providers known only from unofficial copies, no webhooks anywhere, signing without a person only through the provider's HSM or remote certificate, and series and templates made by the seller in the provider's own page. Some APIs still document a cancel call, which the rules for the seller appear to have dropped. The decision is how Ludy talks to providers so that the first one can be replaced or followed by another, the flows can be built and tested with no provider, and nothing legal is ever sent by accident.

## Decision

1. **One port, `EInvoiceProvider`, in a new package `@crove/einvoice`, one adapter per provider.** The port has `testConnection`, `listTemplates` (templates and series, with the symbol), `issue` (one call that numbers, signs and submits for the code; an adapter whose provider splits it into a draft call and an issue call, or a hash-sign pair, hides that behind the one method and declares it), `status`, `files` (signed XML and PDF), `adjust` and `replace`. Each adapter declares static capability data: what it cannot do (no draft, no cancel), its signing kind (`provider_hsm` or `seller_token`), batch size, whether requests must be sequential per series, its egress hosts, and the retry safety of each step (`safe`, `idempotent`, `reconcile_only`, as the channel adapters declare theirs). There is no `cancel` on the port: e-invoice cancellation appears to be gone from the rules (plan section 3, rule 7); if the primary text shows otherwise, it is added as a capability.
2. **The org's own account, sealed.** The "Tích hợp" section that holds it is general, not e-invoice specific: a connection has a kind (`einvoice`, or `marketplace` for the stock design of #2499) and a provider within it, and a later kind reuses the same connection row, sealing, status and kill switches (plan section 7). A connection is a row of `crove_kernel.channel_connection` (provider `einvoice_<name>`, unique per org, legal entity and seller tax code) with its credential in `crove_kernel.credential`, sealed by the vault with the binding of ADR-0025 (org, provider, account). Owners and admins connect and disconnect; the command receives the envelope, never the secret; only the worker opens it; nothing shows it back; a disconnect drops it (the exception of the ads amendment does not apply: an e-invoice credential has nothing to revoke at a third party, so no sealed copy outlives the disconnect). The connecting member must still be an owner or admin when the worker opens the credential, as for every channel. A connection whose signing kind is `seller_token` is refused: a token held on a PC is not a server path. Where the provider allows its own customers to use the API, this needs no agreement between the provider and Ludy; where a provider requires one, its adapter stays off until the owner has it (plan section 10).
3. **Who approves the posting.** The provider holds the legal invoice. Ludy keeps a draft, a state and the signed XML it fetched, and posts the sale **only from that XML**, through the existing intake: `kernel.file.ingest`, the `crove-extract` sandbox, the signature check (#674), the duplicate key (direction, seller tax code, series, number) and the finance proposal path. The issue command is R3 (a legal document that only an adjustment or a replacement corrects): a fresh second factor, owners, admins and members who may approve sales, never an agent. **A person's Phát hành click is the approval of the posting when, and only when, the signed XML's totals, buyer tax code, lines and VAT per rate equal the draft's**, checked by code; any difference leaves the proposal pending for a person to read as a mismatch, and a posted sale is never changed (a correction is a new invoice). This is the one rule that touches the ledger's approval path, so it is a separate build step with the Platform PO's security review, and until it lands the proposal made from the XML waits for an ordinary approval.
4. **Ludy's key, ask before retry.** Each draft holds a UUID made by Ludy and sent as the provider's own idempotency field where one exists. Every provider call is recorded in `crove_kernel.external_call` before it is made, with the states `started`, `succeeded`, `failed`, `ambiguous` (ADR-0025 point 5); a call found `started` on a retry becomes `ambiguous` and the job asks the provider for the key before anything is sent again. An invoice stays `ambiguous` on screen, and no new issue of the same draft is allowed, until the answer is known or a person has looked at the provider's page.
5. **Polling, not callbacks.** No provider found offers webhooks, so a job polls `status` (seconds at first, then minutes, up to a day, one job per pending invoice) with a per-connection concurrency of one and the provider's own limits (30 to 50 invoices per call, sequential per series where declared). A status the adapter cannot map is `pending` until the day ends, then `failed` with the code `STATUS_UNKNOWN`, shown to a person.
6. **The signed XML is the source file.** It is stored as evidence (ADR-0013), append-only, never replaced; the PDF is a convenience copy. Retention follows the books (at least 10 years). A correction is a new invoice that references the original and enters the same intake: the posted original stays in force (adjustment) or is voided in the transaction that posts the replacement (#916).
7. **Egress and the kill switch.** Each adapter calls only its own declared hosts, through `guardedRequest` (public addresses, a pinned connection, one deadline, a byte cap, no redirects); an adapter is off unless the deployment enables it (`EINVOICE_PROVIDERS`, one entry per provider); the channel layer's kill switches stop issuing for an org or a deployment at once. Logs, audit rows and error messages carry codes, never credentials, the buyer's data or a provider's message.
8. **The offline provider.** An in-process `sandbox` provider (on unless `EINVOICE_SANDBOX=false`, as `CHANNEL_SANDBOX`; **refused on a public deployment that runs the finance module**, since what it issues is read into a sale of the books, #2502) numbers, "signs" and returns an XML in the shape the intake reads, can be told to be slow, to reject, to lose an answer and to answer `pending`, so every flow and every failure of this record is tested with no provider and no network. A real adapter is accepted only with recorded-response tests built from the provider's own document or a call the owner made on the provider's sandbox; an adapter written from a forum post is not merged.
9. **The model drafts, a person issues.** The finance coworker may propose the lines, VAT rates and buyer details of a draft (a model call through the AI meter under `finance.einvoice_draft`, with the figure check: every number it states appears in its source). It has no access to the issue command, to credentials or to the provider.

## Consequences

- The adapters are built one at a time, each when the owner has made the check of the plan's section 10 for that provider. Adapter 1 is MISA meInvoice; the order is cheap to change.
- New protected-path surface: two or three migrations (drafts and series; the connection reuses the channel tables), credential handling, the issue command, the approval rule of point 3. Each PR gets an independent security review, RLS matrix rows for the new tables (two-step rule) and a redaction test.
- A provider's API changes on its own schedule: an adapter breaks visibly in "Kiểm tra kết nối" and in its recorded-response tests, and does not fall back to guessing.
- An org that has no provider, or whose provider has no API, keeps the old way: issue in the provider's page, bring the XML into Ludy.
- If a provider's terms forbid use of the API by a third-party application even for its own customer, that adapter is not built.

## Options considered

1. **Ludy becomes a licensed provider.** Rejected by the owner: a licensing, certificate-custody and tax-authority-connection business of its own, and a conflict with running on one `docker compose up` for every org.
2. **A direct connection to the tax authority.** Not available to a small seller: the rules reserve it for large non-coded sellers (1 million invoices a month or more, Decree 254 Art. 16).
3. **One aggregator (SePay, Pay2S) as the only integration.** Rejected as the first path: it adds a second company between Ludy and the seller's provider, its documented operations are narrower (SePay has no cancel; Pay2S no adjust or replace), and its terms are a new dependency. It stays possible as one adapter behind the same port for a seller whose provider has no API of its own.
4. **The seller's USB token signing on the client.** Rejected: needs a person and a PC for each invoice, which is not a server path; a provider with HSM or remote signing is the supported route.
5. **Webhook-first status.** Not possible: no provider found documents callbacks. If one does, its adapter adds a receiver behind the same `status` contract, and the poll stays as the safety net.

## Addendum (#2502, slice A1): who approves the issue

Point 3 names "owners, admins and members who may approve sales". Slice A1 builds the narrower rule the Platform PO ruled on, and records the difference here:

- **Owners and admins approve** a request to issue a sales e-invoice (`finance.einvoice.issue`, R3), with a fresh second factor, the four-eyes rule and the one-person path of policy P10: where no other owner or admin exists, the one who asked may approve their own request. A **member may request but not approve**; the request waits in the Inbox for an owner or admin.
- **Member approval of sales stays out.** Letting a member approve the issue of a legal document would be a change to who approves what, which is an invariant of the approval policy and an owner decision; it goes through the two-step route if the owner ever wants it. Until then the narrower rule is the one the database enforces (`einvoice_submit` checks the role of the approving user, and the approval policy version 5 lists the command for owners and admins).
- The approval is the legal act. The job that follows runs as the system and is R2: it sends what the approval named (the draft's content hash is part of the request, and a change after the request is refused) and never decides anything. The posting of the sale from the signed XML waits for an ordinary approval until the matching rule of point 3 lands as its own build step.
