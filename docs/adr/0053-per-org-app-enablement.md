# 0053. Per-org app enablement: an owner or admin turns apps on and off for their own company

- Status: accepted for slice (a) and the contract; slices (b) to (e) are built from it (owner decision, 2026-11-15, Platform PO chat, popup answer "Làm bật tắt theo công ty"). The three points in "Open points for the Platform PO" are this ADR's own choices, flagged for the PO's acceptance.
- Date: 2026-11-15
- Deciders: owner (JOY) for the feature; the engineering choices by the session that wrote it, for the Platform PO
- Amends: [ADR-0031](0031-module-enablement.md) (it left per-org access to entitlements and did not enforce them)
- Builds on: [ADR-0030](0030-composition-root.md) (the `billing` port), [ADR-0007](0007-tenancy-and-context.md), [ADR-0029](0029-agents-positions-and-org-chart.md), plan Decision 10 (entitlements) and Decision 12 in [crove-os-kernel.md](../plan/crove-os-kernel.md)
- Issue: [#3307](https://github.com/DOS/Ludy/issues/3307)

## Context and problem statement

[ADR-0031](0031-module-enablement.md) turns modules on and off **per deployment** with `CROVE_MODULES`: a module that is off registers no command, query, job, route or menu, and keeps its data. On a shared deployment (Crove Cloud) that is the wrong grain: one deployment serves many companies, and every org sees every module the deployment runs. The `Billing.entitlements(orgId)` port exists in `apps/kernel/src/kernel.ts`, but nothing enforces it (self-host answers `['full']`).

The owner wants each company's owner or admin to switch off the apps the company does not use (Social, Nhân sự, Cuộc họp...) from Settings. A one-person company that never posts to social media should not see Social in its menu, in Home, or in what Vy says. The defaults keep every app on with no setup, and switching one back on restores everything, data included.

The scope gate ([scope.md](../product/scope.md)) is met: it is a task a small business does once or twice, the smallest slice is one switch per app with every app on, and the AI coworker here does nothing (Vy only stops mentioning an app that is off; every change is a person's).

## Decision drivers

- The rule that decides must be **one function** used by every gate, and the same one the entitlements port feeds, so a paid app that is not held and an app the owner switched off are one answer, not two checks.
- The owner's choice takes effect **at once and in the same transaction** as the call it affects: an app turned off is never reachable a minute later through a cache.
- Turning off must be **reversible and lose nothing**: data, connections and queued work come back as they were, except work whose time has passed, which never runs on its own.
- Legal keeping continues for an app that is off: retention, evidence holds, erasure and export are not "work" and do not stop.
- One write path ([AGENTS.md](../../AGENTS.md)): the choice is written by one kernel command and nothing else.
- A module added later is on by default for every org, with no migration of choices.

## Decision

### 1. The effective set

For an org, an app (module) `m` is **effective** when all of these hold:

```
effective(m) = m == 'kernel'
            OR ( m in CROVE_MODULES            -- the deployment runs it (ADR-0031, unchanged)
                 AND entitled(org, m)          -- the org holds it (plan Decision 10)
                 AND m not in org.apps_off )   -- the org did not switch it off
```

- `kernel` is always effective and cannot be switched off. A module needs no other module (Decision 12: modules run when others are off), so switching one off never forces another off.
- `entitled(org, m)` is true when `Billing.entitlements(org)` returns `full` or `m`. Self-host answers `['full']`, so it is always true there.
- `Runtime.installed(m)` keeps its meaning: the deployment level, a registry fact, used when routes and jobs are registered at boot. A new `Runtime.effectiveModules(orgId)` returns the org's set; it is the only place the three parts are combined.

### 2. Where the choice is stored

A column on the tenant row, in a migration, written by one command:

- `crove_kernel.tenant.apps_off text[] NOT NULL DEFAULT '{}'` and `crove_kernel.tenant.apps_version integer NOT NULL DEFAULT 1` (the same pattern as `approval_preset` and `approval_policy_version`, #1402). The default is **the list of apps that are off**, empty for every org, new or existing: no backfill, and a module shipped later is on everywhere until someone turns it off. A column rather than a table because the choice is a short list read on every call with the tenant row, the history lives in the audit log, and a per-app table would add a second row read to the hot path.
- A guard trigger (`tenant_apps_guard`, `BEFORE INSERT OR UPDATE OF apps_off, apps_version`) lets an INSERT through only with the defaults (`apps_off = '{}'`, `apps_version = 1`), because org creation inserts the tenant before its owner's membership exists, and refuses any other change not made by an owner or admin user context of that org, an element that is `kernel` or not shaped like a module id (`^[a-z][a-z0-9_]*$`), a duplicate, and a version that does not grow by exactly one with the change. A constraint trigger (`tenant_apps_requires_audit`, deferred) lets the commit through only with that command's `ok` audit row naming the module and the new state. Staff (a superuser or the migration runner's role) may change it for support. This copies `tenant_approval_policy_guard` and `tenant_approval_policy_requires_audit`; every function sets `search_path = pg_catalog, pg_temp`.
- The database stores any well-formed module id, so removing a module from a later build breaks nothing. The command refuses an id the build does not ship (`AVAILABLE_MODULES`) and `kernel`.
- `crove_kernel.org_app_on(p_org uuid, p_module text) RETURNS boolean` (`STABLE`, `SECURITY DEFINER`, `search_path = pg_catalog, pg_temp`) answers `p_module = 'kernel' OR NOT (p_module = ANY (apps_off))` for sweeps, the outbox relay and public pages, which run without a tenant context. It reads the choice only, so it is the SQL half of the gate: the worker's sweeps, the relay and public pages also ask `entitled(org, m)` through the same TS function that feeds the runtime (the worker and the API both hold the `billing` port), and an app is served only when both answer yes. An org that does not hold Social therefore never gets it served, whatever its `apps_off` says. *(As built, the public pages of slice (c) C2a ask the choice only, not the entitlement; see the C2a bullet under "As built: slice (c)" and follow-up #3393.)* EXECUTE goes to the roles that need it and nobody else (the grants are decided and tested in slice (a), as for the other `crove_kernel` helpers).
- The command: `kernel.org.set_app` with input `{ module, enabled }`, one app per call, `access: ['owner', 'admin']`, risk R2 (a settings change that affects the whole company, reversible, moves no money; R3 and its second factor are kept for what cannot be undone), `sideEffect: 'internal'`. It locks the tenant row (`FOR UPDATE`) so two switches meet on it, changes the list and the version only when the state changes (setting the state it already has writes nothing and emits no event; the runtime's audit row of the run says `changed: false`), writes `ctx.audit({ module, enabled, version, changed })` and `ctx.activity`, and emits `kernel.org.apps_changed` (`{ module, enabled, version }`) for the live app (section 5) and for held work (section 4). An agent actor and an MCP grant cannot run it (the role check refuses them, covered by a negative test), so no AI changes a switch.
- The read: `kernel.org.apps` (any member) returns, per app the build ships, `{ id, deployment, entitled, enabled, effective }` and whether the caller may change it, so Settings can say why an app is off ("chưa có trong gói" versus "đã tắt").

### 3. Where it is enforced

Every gate asks the one function. The check comes **after** the session check and the membership check, so someone who is not a member of the org learns nothing about its apps (the pre-membership refusals stay as they are).

| Point | Answer when the app is off for the org |
|---|---|
| `Runtime.execute` (all actors: user, agent, system), the nested commands of `ctx.command`, and an approved proposal that runs a command | `DomainError` `MODULE_OFF`, status 404, with `module` in its details and a Vietnamese message naming the app. 404 keeps the parity with ADR-0031's deployment case (clients treat it as "not there"); the typed code carries the reason. The enclosing transaction rolls back, so nothing is half done. |
| `Runtime.query` and `Runtime.stream` | The same `MODULE_OFF`. |
| `ctx.query` (so Home, signals, links between apps) | `{ status: 'not_installed', module }`, the same typed answer as ADR-0031 section 4, so every caller that already handles an app the deployment leaves out handles this with no change. |
| Worker sweeps and jobs | Skip the org: a sweep adds `org_app_on(org_id, '<module>')` to the query that finds work; a job that starts for an off org ends without work and without a retry (section 4). |
| HTTP routes and public pages of the app (the booking page, the bio page, client review and report links, calendar feeds, the extension and upload endpoints of Meetings) | The ordinary not-found answer, identical in status, body and headers to an address that does not exist (the lookup does one more index read, as for an unpublished page or a revoked token), so a public visitor cannot tell "off" from "never existed". |
| Inbound webhooks of an app (the bank-feed one; Finance) | Signature checked, then **acknowledged and dropped** (200), never 404: a provider that sees errors retries and then disables the subscription. What was dropped is recovered by the app's own catch-up sync after it is turned back on (section 4). |
| Vy, Home (`kernel.today`), signals, the weekly digest and MCP | The app is left out: its `<module>.today` and signal lines do not run, its tools are not listed (`activeTools` is user permissions ∩ entitlements ∩ the effective set, plan section 8), its coworkers do not wake, and a tool call into it answers `MODULE_OFF` as an MCP `isError`. Vy's prompt names only effective apps. |
| The SPA | The org's effective set comes from `kernel.org.apps` (not from `/api/config`, which stays per deployment); menus use `installedItems` and screens use `screenInstalled`/`outsideInstalled` with that set, so an off app's screen opened by URL redirects as ADR-0031 section 3 says. |

Rules that keep the gate honest:

- **Keeping is not work.** Retention, evidence holds, erasure and crypto-shredding, the org export and offboarding, and the purge keep running for an app that is off, with its data. They run as kernel commands or `SECURITY DEFINER` functions keyed by org, not as the module's own commands. A module command that must run while the app is off declares `runsWhenOff: true` with a one-line reason; the default is refused, and a test lists every such command so a new one is a visible, reviewed addition.
- **Every sweep and job is classed.** A new sweep or job of a module declares whether it is `work` (skipped when off) or `keeping`. A test walks the worker's registered sweeps and fails on one with no class.
- **No cache on the choice.** The runtime reads `apps_off` in the call's own transaction (one primary-key read of the tenant row, or carried by the context-entry function; slice (b) measures and picks). Only the entitlement answer may be cached, for up to 60 seconds per org in each process, because it comes from a port that can be remote.
- **Entitlement failures fail open to the last answer.** If the port cannot answer, the runtime uses its last known answer for the org, and `full` when it has none, and records a security event. Entitlement is a commercial limit, not a safety one; taking every paid app down on a billing outage is the worse failure. The deployment list and the owner's choice still apply.

### 4. Queued work, live connections, and turning back on

The principle: **the database row is the truth and a queued job is only a hint**. Every module's work is found by a sweep over rows, so a job dropped while the app is off is found again later; events that cannot be re-found are held, not dropped. This is the per-org rule. The per-deployment case of ADR-0031 is unchanged: when finance is off for the whole deployment, the relay drops the file events and enabling it later does not read those files.

- **Pending outbox events** for the consumers of an off app stay in `outbox_pending`. The hold is per consumer (`processed_message` is keyed by consumer and event), not per event type: a kernel event such as `kernel.file.ingested` is still delivered to the kernel's consumers and is held only for the app's own (finance extraction), so an uploaded file is stored at once and read when finance is back on. The relay's claim excludes the held pairs (`org_app_on` and the entitlement check), so they do not block other orgs, and they flow in order when the app is on again (the `kernel.org.apps_changed` event wakes the relay). There is no expiry in this slice. The number of held rows is measured, and a limit is a follow-up issue if it grows.
- **Queued pg-boss jobs** of an off org complete without work and without retry. Their rows are found again by the sweep.
- **Time-sensitive work never runs late on its own.** A post planned for a time that has passed by more than 60 minutes (the grace) by the moment the app is back on is not published. It is shown as late and waits for a person (the module's existing late state if it has one; slice (c) checks Social's and adds one if not). A meeting join or recording planned for a time that passed is dropped. The reason is the same as everywhere else: a person approves messages, and a stale public post is a harm that cannot be undone. Posts still inside the grace go out normally.
- **Connections are kept, not revoked.** Sealed OAuth tokens (channels, ads, bank feeds, calendar, meeting platforms) stay in the vault. Refresh and sync jobs skip the org, and Settings shows the connection as "paused, the app is off". A token that expires while paused shows as "needs reconnecting" when the app is back on. To remove a connection the owner uses the app's own disconnect before switching off; the switch's confirmation says so and lists the connections.
- **Webhooks** of the app are acknowledged and dropped while off (section 3); the app's catch-up sync runs when the app is on again and covers the gap. Slice (c) checks each webhook provider for such a sync (a cursor poll) and records any that has none, so the gap is known before the switch ships.
- **Open sessions.** The invalidation stream stops pushing events of the app's entities and the client refetches `kernel.org.apps` on `kernel.org.apps_changed`, so every open tab updates its menus within seconds. MCP grants and extension sessions stay authorized; their calls into the app answer `MODULE_OFF`. A Vy run in progress ends at its next call into the app with `MODULE_OFF`; each command is one transaction, so nothing is partial.
- **A recording in progress is not cut off.** `kernel.org.set_app` refuses to turn Meetings off (`APP_BUSY`, 409, "Đang ghi âm một cuộc họp, hãy dừng ghi âm trước") while a recording is open, because the audio would be lost. The composition root hands `kernel.org.set_app` a probe per app (`appBusy`, as built in C3a: each returns short reason codes, none when the app can go off; the message above is the one Settings shows, and the details carry the app and the reasons); Meetings and Ads have one today. A command that declares it holds the share lock to commit and must lock no member, role-assignment or position row (lock order, `tools/test/lock-order.test.ts`). The probe and a recording start must not interleave, so they meet on the tenant row: a command that opens such work (a recording start) declares `opensBusyWork: true`, and the runtime reads the tenant row `FOR SHARE` in that command's transaction, held to commit; `set_app` holds `FOR UPDATE` on the same row and runs the probe under it. Shared holders do not block each other; a switch conflicts with them, and so does any other UPDATE of the tenant row (the tax code, the address, the preset), which waits for the running command. If the recording start commits first, `set_app` waits and then sees it and refuses; if `set_app` commits first, the recording start then reads `apps_off` and answers `MODULE_OFF`. Every other command reads the choice without a lock.
- **Proposals and Inbox items of an off app** are kept with their own expiry, hidden from the lists with one line ("N việc đang chờ ở ứng dụng đã tắt"), and cannot be approved (`MODULE_OFF`).
- **Turning back on** changes one column. The data was never touched, the registered commands, routes and jobs were never removed, so everything is visible at once. Held outbox events flow, sweeps find the rows, connections resume, and late items wait for a person as above. Nothing is replayed that had a time.

### 5. Tests

- **Slice (a)'s own invariants** in `apps/kernel/test/invariant/` (a protected directory, so the file lands with the migration PR): the guard and audit triggers refuse a direct write by a member, an agent, a user of another org, a duplicate, `kernel`, a version jump, and a write with no audit row; the command refuses members and viewers, agents and MCP grants; the default is empty for new and existing orgs; another org's list is untouched; `org_app_on`'s grants. The file lands in the same PR as its migration, so it needs no lookup of objects that may not exist yet (the lookup pattern of `member-vy-private.db.test.ts` is for a test that lands before its feature, as slice (b)'s does).
- **Slice (b) is a protected path built in two steps** (`packages/kernel-runtime/src/**`; the base-copy job deletes the PR's invariant files and runs the base's against the PR's code, so a strict test cannot ship with the change it pins):
  1. a tests-only PR adds `org-app-gate.db.test.ts`, whose cases for `MODULE_OFF`, `not_installed` and the audit accept **both** behaviors (an off app may still run, or answer `MODULE_OFF`) and pin what must already hold: a non-member learns nothing, `kernel` is never refused, another org is unaffected, entitlement failure fails open;
  2. a runtime PR adds the check; the base copy from step 1 passes against it. A third tests-only PR then makes step 1's file strict (`MODULE_OFF` required), because the runtime PR cannot edit a base file. The strict cases: a command, a query, a stream, a nested command and an approved proposal of an off app each answer `MODULE_OFF`; `ctx.query` answers `not_installed`; a system and an agent actor are refused like a user; the `runsWhenOff` list and the sweep-class list are exact; switching off and on restores the same rows.
- **Slice (c)** adds ordinary `*.db.test.ts` cases: a sweep skips the off org and serves another; a held event flows when back on; a late post waits for a person; a public page answers the not-found response with the same body as an unknown address; a webhook is acknowledged and dropped.
- **Slice (e)** adds: Home, signals, Vy's tool list and MCP's tool list omit the app and `tools/call` answers `MODULE_OFF`.
- CI keeps running the kernel alone ([ADR-0031](0031-module-enablement.md) section 5); a case boots two orgs on one deployment with one app off for one of them.

## As built: slice (b), the runtime gate

- `RuntimeOptions.entitlements` (the billing port's function) and `Runtime.effectiveModules(orgId)` (the modules the runtime registered, that the org did not switch off through `crove_kernel.org_app_on`, and holds); `entitledTo` is exported by `@crove/kernel-runtime` and `kernel.org.apps` uses the same one. `createKernel` always passes `billing.entitlements` (`serverRuntime` takes no `entitlements` option of its own), and `org-app-gate-wiring.db.test.ts` boots the server with a port that holds the org to some apps to prove it.
- `Runtime.execute`, nested commands (so the command an approved proposal runs), `query`, `stream` and `ctx.query` ask one private check after the session and membership checks: the tenant row's `apps_off` read in the call's own transaction (memoized per call, no cache), then the entitlement (cached 60 s per org, 3 s timeout, fail open to the last answer or `full`, one security event a minute). Order in `execute`: before the role check, the idempotency key and the handler, so a refused call leaves no key and no `ok` audit row.
- `runsWhenOff` (a one-line reason) and `opensBusyWork` are on `CommandDef`, `runsWhenOff` on `QueryDef`; registration refuses a kernel definition with `runsWhenOff`, a short reason, and `opensBusyWork` on kernel or beside `runsWhenOff`. Today 43 commands (32 before slice c, 11 added in C1) and 5 queries declare `runsWhenOff`: retention, shredding, erasure, the revocation of a leaver's links, sealed-key reseals, the Ads pause chain, and the commands that only stop, revoke or delete (stop ads and lower a cap, kill a public link or feed, delete a meeting), so an org that lost an app can still stop spend and kill a leaked link; none of them nests into a gated command (Ads disconnect nests the kernel's channel disconnect), listed exactly by the invariant `app-gate-keeping.test.ts`, so adding one is a reviewed edit of a protected file. No command declares `opensBusyWork` yet (slice c: the Meetings recording start).
- A `bootstrap` (org-less) command must be a kernel command (registration refuses any other), because the gate cannot read an org it runs before. A database before slice (a)'s migration has no `apps_off` column: nothing can be off there, so the gate reads it as no choice (an upgrade in progress, and the tests that run the runtime on an older schema); a row the context cannot read on a database that has the column fails closed. The log line for a failing billing port carries the error's name only. The `Billing` port's contract is on its interface: `[]` for an org with no plan, throw only when the service is unavailable.
- Not in this slice, so the gaps are known. The stop commands pause an ad at the platform only through the event `ads.pause.queued`, the relay, the ads-pause job and `ads.pause.begin`/`record` (and a revocation through its sweep and `ads.pause.pending`); slice (c) must class that queue and that sweep as keeping and let the relay deliver those events while the app is off, or `ads.pause_all` of an app that is off cancels launches in Ludy and pauses nothing at the platform. Most revoke and delete commands take an id from a list of the same app, which is gated, so while the app is off only the commands that need no id (`crm.booking_feed.revoke`, `social.calendar_feed.revoke`, `ads.pause_all`, `ads.write.disable`) work from a cold start; the others work for a person who already holds the id (#3361 asks for a keeping list read). Also: `kernel.proposal.request` still raises a proposal for a command of an app that is off (its approval is refused with `MODULE_OFF` and the proposal waits); the year archive of finance is work, not keeping, and stops with the app; turning Ads off while a campaign runs is for the busy probe of slice (c).

## As built: slice (c), C1 (the worker stays quiet)

Slice (c) is built in three PRs after a step 0 of the `runsWhenOff` invariant (#3369): C1 the worker and the relay (no migration), C2 the public pages, the webhooks and the routes (a migration), C3 the outbox hold, the Meetings busy probe and the Social late state (a migration). The owner screen (d) does not ship before C3.

- **Rulings of the Platform PO (2026-11-16).** The four conversation webhooks (Zalo, Telegram, Facebook, WhatsApp) feed the kernel conversation core: they are kernel and never dropped, so section 3 no longer names Facebook as an app webhook; only the bank-feed webhook is an app's (Finance). `/api/files` (upload, download by id) stays ungated: it is kernel data and the owner's own files; only the Meetings upload purposes stop for an off org (C2). Planned takedowns (`social.remove.*`) are exposure-stopping and join `runsWhenOff` in C3 by the two-step.
- **No refusal row for the system.** A `MODULE_OFF` refusal of a call made by the system actor (the worker, a sweep, the relay) writes no refusal-audit row and spends none of the refusal budget; the failed row stays for a person's call and an AI agent's.
- **Jobs end.** A job whose handler meets `MODULE_OFF` resolves: no retry, no dead letter, no Inbox item, no prober alert. One warning a minute per queue and app names the org's first eight characters and never the payload (it is the only signal if a billing port wrongly answers `[]`). The queues of a keeping duty (`ads-pause`, `ads-revoke`, `notes-member-purge`, `notes-trash`, `crm-import-expire`) and the AI agent's approval (`kernel-agent-proposal`) are exempt: a refusal there fails loudly, retried and dead-lettered as before. The queues whose job calls a platform or a provider and then records the answer (Ads launch and activation, the e-invoice issue) end quietly only for a refusal at the job's first gated call (nothing was done yet); a record refused after the call is rethrown as an `AppOffAfterCallError` (not a `MODULE_OFF`), so it fails loudly, and its retries end loudly too (`loudOnRetryQueues`: the retry's begin is refused with `MODULE_OFF`, which would otherwise end the job quietly), so the job reaches the dead letter queue and the spend or the invoice is not left without a trace (`recordAfterCall`). A first attempt refused at begin still ends quietly. Only a `DomainError` counts as `MODULE_OFF`: a provider's error body can carry any code.
- **The relay cannot wedge.** A relay step refused with `MODULE_OFF` is **dropped**, with a line of event id, type and app, instead of rolling back the whole claimed batch (it was claimed again every second, for every org). **This drop is a stopgap: C3 replaces it with holding the event until the app is back on.** The drop is an allowlist (`DROPPABLE_EVENTS`: `ads.campaign.draft_queued` only), so a step added later is never dropped silently. The keeping events (`ads.pause.queued`, `kernel.member.removed` and `kernel.member.role_changed`) never take it: their consumers' first calls declare `runsWhenOff` (a test pins it). The relay step of these events only queues jobs; it is the job that runs the keeping command. Of their queues `ads-pause` and `notes-member-purge` are exempt from the quiet end above; `crm-booking` and `social-notify` are not, and are safe because their first call is a command that runs while the app is off.
- **The cache is not a gate.** `appOn` keeps an answer for 5 seconds, unlike the gate's own read: where it is the only guard (transcription, live notes, import, the calendar agenda read) work can start up to 5 seconds after a switch-off; section 3's "no cache" is about the gate on commands and queries.
- **Sweeps skip.** `Runtime.appOn(orgId, module)` (the effective set, kept 5 seconds per org) lets a sweep skip an org whose app is off before it calls anything: Social's evergreen, recurring, review and assignment reminders, queue-low, digest and report schedules; Finance's missing-invoice reminders and period-closing reminders; CRM's stale-deal scan; Notes' to-do reminders; Meetings' hook, chat and import sweeps; the Social publish sweep queues no job for such an org. The sweeps that read first through a gated query (metrics, account snapshots, external posts, late ids, feeds) are quiet through the refusal rule above and are left as they are; their oldest-first scans, and those of the sweeps above with no `tried` list (`publish_due`, `remove_due`, the hook and chat `open` reads), can still be filled by an off org's rows (starvation), which a later SQL filter closes; the Meetings import sweep pages past the skipped connections instead. Planned takedowns (`social.remove.*`) are not skipped: they are exposure-stopping and join `runsWhenOff` in C3, and until then they are refused quietly. The Meetings chat sweep skips an off org for every kind of row (its records are not on the keeping list), and the hook sweep's expiry still runs (`meetings.hook.record` declares `runsWhenOff`).
- **External effects before a gated call.** Meetings transcription and live notes (their audio is opened through a kernel command), the Meetings import job and sweep (every call is a kernel command), and the calendar agenda read check the org's Meetings before they reach a provider.
- **C2a: the public pages and the bank feed notice.** Three migrations (Social, CRM, Finance; one module schema each) restate thirteen definers, each the body of the newest migration that defines it plus `AND crove_kernel.org_app_on(t.org_id, '<app>')` in its active-tenant test, checked by a script that strips the addition and compares every body with its source. The shared lookups cover the most: `review_link_by_token` (every review link function), `booking_event_type` (booking page, status, request and deal request) and `booking_manage_find` (manage view and request); the report link, short link, bio page (view, go, file), calendar feed, booking feed and quote link (view, logo) look the tenant up themselves. An off app then returns its function's own "nothing found", so each route answers its own not-found body, the same as for an address that never existed, and the visitor's writes (a client's answer, a short link hit, a bio click, a booking request, a quote view count) are refused like those on a revoked link. **The public pages ask the choice only, not the entitlement:** no public lookup exposes the org to the API and the billing port is a TypeScript function, so an org that does not hold Social but never switched it off still has its public pages served; this matters only for a billing port that narrows entitlements (Crove Cloud), and closing it needs the org returned by each lookup (follow-up #3393). The bank feed notice is dropped in `bank_feed_notice_claim` (a notice names the account, not the org): the HTTP answer stays 2xx and the daily sync, which reads each account from its stored cursor, recovers the gap after switch-on. The invariant `app-gate-routes.test.ts` classes every public route of `route-coverage.test.ts` (`sql`, `runtime`, `dropped`, `keeping`, `kernel`, `pending` for the eSign routes of #3324) and fails on an unclassed one, so a new public route must say where its gate is. Left for C2b: the stream filter and its `apps_changed` hint, the Meetings upload purposes and the extension's feature flags.
- **C2b: the stream, the upload purposes and the extension.** A stream of an org with an app off does not push the hints of that app's entities: `HINT_APPS` names the app of every hint type (a total Record, so a new type must say), the stream check also asks `Runtime.effectiveModules` for the apps off (Finance, Social, Notes; a check that cannot read them keeps the filter of the last one that could, and logs the error's class, so a failure never widens a stream; a stream whose first check fails has none), and `StreamConnection` drops those hints on arrival and again when they are sent. A new hint type `org_apps` (id: the org's own) comes from a trigger on the tenant row (`tenant_apps_notify`, only when `apps_off` or `apps_version` changes): every stream of the org gets it, checks again first so its filter is the new set, and the app invalidates `org.apps`. (`kernel.org.apps_changed` stays an outbox event for consumers; the stream hint is the trigger's, because the tenant write can be made by no other path.) The Meetings media upload purposes answer as a purpose that is not installed (404 `NOT_FOUND`, the answer of a deployment that leaves Meetings out; an unknown purpose is a 400) while Meetings is off, at the grant and at the completion (`/api/files/uploads`, its completion and `/api/files`), and the extension is offered no Meetings or agenda feature (`/api/extension/me`) and no `meetings` scope (`/api/extension/authorize`). These HTTP checks read the org's state fresh (`appOn(..., { fresh: true })`), not through the 5-second cache; a read that fails leaves them open, as the calls behind them are gated by the runtime (for an upload, the Meetings media route that seals the recording; the grant itself is a kernel command). The extension's own calls and the session media routes were already refused by the runtime. The client case for `org_apps` names the path `org.apps`, which the Settings and menu slices (d, e) read.
- **C3a: the busy probes.** `kernel.org.set_app` asks the app's probe under the tenant row (`FOR UPDATE`) and refuses the switch-off with `APP_BUSY` (409; details `{ module, reasons }`) while it names open work; turning an app on, or off when it already is, is never refused. Meetings (`meetingsBusy`, through the definer `crove_meetings.org_busy_reasons`, because a meeting is visible only to its recorder and readers and a platform recording only to its member, so the switcher's own context would miss another member's): `recording`, a ready meeting of any member, not ended, started within the 4-hour recording window and not more than five minutes ahead (a start in the future is no recording; the extension's and the in-app recorder's alike; the definer answers two flags, because a `crove_meetings` definer may not return text); `import`, a platform recording `importing`, `staged` or `claimed`. Ads (`adsBusy`, the Platform PO's rule of 2026-11-16): `campaign_running`, a launch `launching`, `live` or `needs_attention`; `wind_down_open`, a stopped launch whose objects are not yet paused at the platform; `activation_open` and `call_open`, a call of such a launch begun and not settled (`started` or `ambiguous`, of any age, so Ads off, on and off again around an activation still sees it). The rows of a launch that is over are history and never count: several paths leave a call unsettled for good, and it must not keep the app on. The owner stops the campaign first (stopping runs while the app is off), then waits for the pause; `APP_BUSY` names the reasons, not the launch, so Settings says what to look at. The commands that open such work declare `opensBusyWork` and take the tenant row `FOR SHARE`: `meetings.meeting.create`, `meetings.import.start`, `ads.launch.begin`, `ads.activate.begin`, so a start and a switch-off never both succeed. Not probed: Social publishing in progress and e-invoice issue (their jobs keep running and recording while the app is off), and live notes (part of a recording).
- **C3b: the outbox hold.** The events of an app that is off wait, and flow when it is back on. In a relay batch, after the claim and before any job is queued, `planHolds` reads, for each distinct org and app of the batch, whether the app is on (`Runtime.appOn`, fresh, all the reads at the same time), and `holdEvents` parks the events of an off app in `crove_kernel.outbox_held` on the claim's own transaction (the claim and the parking commit together or not at all): nothing is queued for them. Which events wait is `heldAppOf` (`apps/kernel/src/outbox-hold.ts`): the events of Finance, Social, CRM and Ads (their prefix), and the two file events whose consumer is Finance's extraction (`kernel.file.ingested`, `kernel.file.reextract_requested`), so a file stored while Finance is off is read when it is back. Never parked: the keeping events (`ads.pause.queued`, `kernel.member.removed`, `kernel.member.role_changed`), the takedown of a post (`social.variant.remove_requested`, which reaches its consumer; the consumer declares `runsWhenOff` in C3c, and until then its job is refused quietly), the kernel's own events, Meetings' (a transcription or live notes of a meeting that is happening are bound to their time), and the three public acts a person asked for at the time (a retry of a comment or a thread, an edit of a published post), which run days later would post or change something nobody expects any more: those are dropped, as time-sensitive work never runs late on its own. Sign's two events (`sign.envelope.inspect_queued`, `sign.envelope.seal_queued`) are not parked either: Sign finds its own pending work again on `kernel.org.apps_changed` (`SELF_RECOVERING_EVENTS`). The mixed kernel events (`kernel.channel.connected` of a bank, `kernel.channel.expired` to Social's notifications) are not parked; the bank feed has its daily sync. Two tests read every event type the relay names in `worker.ts` and fail on one of an app that is neither parked nor listed as never parked or as the kernel's own. **There is no expiry** (section 4: an event that nothing finds again is held, not dropped); what waits is measured by the held sweep, which logs how many events wait and for how many org and app pairs when that changes. The held sweep (every 10 seconds, active orgs only, in key order, up to 25 pages of 200 pairs) asks `appOn` (fresh) for each pair and, when it is on, `outbox_release` puts the parked events back on `outbox_pending`, oldest first, in batches of 500; the relay takes them like any other (after the events emitted since they were parked, so the order is the order of parking, not of the original emit) and parks them again if the app went off meanwhile. This covers an entitlement or a deployment change as well as the owner's switch, and a lost `kernel.org.apps_changed`. A read of the app that fails counts as on: the events are queued as before, and a job of an app that is in fact off ends quietly, so a failed read can still lose an event (the same loss as a switch-off that commits between the plan and the job); the relay drop (`DROPPABLE_EVENTS`) covers the race of a step that meets `MODULE_OFF` after the plan found the app on. The retention job (`outbox_archive_purge`, restated with one addition) answers -1 for the day of an event that waits, so the parked event is not archived away. The table keeps ids only, has RLS on and no login role grant, and the org purge leaves it (`KEPT`, the runbook; a closed org is neither listed nor released). The definers (`outbox_hold`, `outbox_hold_pairs`, `outbox_release`) are the worker's alone. Known limits: a released event keeps its original `created_at`, so the outbox lag readings and the back-pressure check see days of lag for the moment between its release and its relay (seconds); and the Ads requeue sweeps write a new event every ten minutes for a stuck launch without asking the app, so an org that lost the Ads entitlement parks a stream of them (about 144 a day per launch) that all go out on switch-on, where each begin step re-checks its launch (follow-up #3409).
- **Held for C3c.** The Social late state with the 60-minute grace and `social.remove.*` (C3c). The 11 commands that record the outcome of an external write (Social publish, comment, thread, remove, edit, pin, playlist, repost, auto-reply and gate; the Meetings hook delivery) declare `runsWhenOff` since step 0 (#3369) merged, so a call already made is recorded even if the app was switched off meanwhile; a tests-only PR then makes the invariant list strict for them. `ads.launch.record`, `ads.activate.record`, `finance.einvoice.job_record`, `finance.einvoice.job_files` and `meetings.chat.record` are left out on purpose: each also re-arms or opens an external call, so the refused record is the safe outcome (the call is recovered by begin and reconcile once the app is back on).

## Open points for the Platform PO

1. **Entitlement outage fails open** (section 3). The alternative, fail closed, takes every paid app down when the billing service is down. Chosen: fail open to the last answer and record a security event.
2. **Turning Meetings off is refused while a recording is open** (section 4), instead of letting the audio upload end. Chosen for safety; it costs the owner one step.
3. **The 60-minute grace for late posts** (section 4) is a number picked here. It is one constant in slice (c), changeable without a new decision.

## Consequences

- On a shared deployment an owner can run Ludy with only the apps the company uses; the defaults change nothing.
- Every call path pays one read of a tenant row it mostly reads already; slice (b) measures it before merge.
- The entitlements port, for the first time, is enforced, through the same gate, so Crove Cloud can sell apps one by one without a second mechanism.
- Every new module's sweeps, jobs, routes, public pages and webhooks must declare whether they are work or keeping, and must ask the org's gate, not only `Runtime.installed`. The two tests make a miss a red build.
- Data is never deleted by turning off. An org that wants an app's data gone uses the existing erasure and offboarding commands.
- Not decided here: a module-level limit on how long held events may wait, a per-member (rather than per-company) choice of apps, and the order of Vy's first-run suggestions.
