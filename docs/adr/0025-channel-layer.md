# 0025. Channel layer: social and messaging connections in the kernel

- Status: accepted (owner, 2026-10-16, in chat: "Làm đi" to the S2 proposal)
- Date: 2026-10-16
- Deciders: owner (JOY)
- Builds on: plan §4.9 (outbox, jobs, `external_call`), §5.7 (Service and Social share the channel layer), §7.4 (credentials and bindings), §7.7 (egress), ADR-0030 (composition root, `CredentialBroker` port)
- Tracking: [Social plan](../plan/social.md) step S2

## Context and problem statement

Social (publishing) starts now (plan Decision 17), and Service (inbound messages and comments) later. Both need the same thing: an org connects a Facebook Page, an Instagram account, a LinkedIn page or a Zalo OA once, and Crove holds its tokens, refreshes them, and calls the platform from jobs. The kernel has a `CredentialBroker` port with no implementation and no table for connections. If Social builds connections inside `crove_social`, Service would either read another module's tables (banned, §5.4) or connect every page a second time.

## Decision

1. **Connections live in the kernel.** `crove_kernel.channel_connection` (one row per connected page or account, unique per `(org_id, provider, external_account_id)`) with `provider`, `display_name`, `scopes`, `status` (`active`, `expired`, `revoked`, `error`), `credential_id`, `connected_by`, `expires_at`. Modules reference it by composite FK `(org_id, channel_connection_id)`; the kernel module role writes it, others only read.
2. **Credentials: the `crove-local` broker.** `crove_kernel.credential` holds tokens envelope-encrypted: a random AES-256-GCM data key per credential, wrapped by the deployment key `CREDENTIAL_KEY` (Crove Cloud: KMS). Rows carry the key id for rotation. Decryption happens only in provider jobs; the API and the OAuth callback seal, they never open. Tokens never reach the SPA, logs, audit rows, events or query output. The `dos-broker` adapter (plan §7.4) stays a later Cloud option behind the same port.
3. **Providers are adapters in `@crove/channel`.** Small capability interfaces (`Connector`, `Publisher`, `Reconciler`, `MediaUploader`, `MetricsReader`; Social plan §3.6) plus static capability data (limits, media rules). Publish steps declare their retry safety (`safe`, `idempotent`, `reconcile_only`, `never`). Each adapter declares its FQDN allowlist and its fetch is bound to it. The core ships `sandbox` (no network, always available in development and tests) and the platform adapters; a provider is enabled only when the deployment has its app credentials.
4. **OAuth connect in the HTTP edge.** `start` writes a single-use `crove_kernel.oauth_state` (org, user, nonce, PKCE verifier where supported, 10 minute expiry); `callback` consumes it, exchanges the code through the adapter, encrypts the tokens and runs `kernel.channel.connect` through `execute()` (R2, owner or admin, permission `kernel.connection.bind`). Handlers keep doing no network I/O; the exchange happens in the route, before the command.
5. **Outbound calls go through `crove_kernel.external_call`.** A deterministic key per intended effect; states `started`, `succeeded`, `failed`, `ambiguous`. A call found `started` on retry is never repeated blindly: it becomes `ambiguous` and a reconciliation job asks the provider (plan §4.9).
6. **Token lifecycle.** A daily schedule refreshes tokens ahead of expiry. An expired or revoked token sets the connection `expired`, modules pause work queued for it, and the owner is alerted. On every use the connecting user must still be a member; otherwise the job stops and the connection needs reconnecting.
7. **Self-host and Cloud.** Self-hosters register their own platform apps and set their credentials in env; Crove Cloud uses DOS-owned platform-approved apps through configuration in `crove-cloud`. Same code, no DOS dependency in the core.

## Implementation (S2, issue #232)

- `packages/kernel-runtime/src/vault.ts`: `CredentialVault` (the `crove-local` broker) and the `CredentialBroker` port it implements: `seal(secret, binding)` and `open(sealed, binding)`, both authenticated with the binding (org, provider, account), not the connection id, so a token can be sealed before its connection row exists and a reconnect keeps the row. `apps/kernel/src/credentials.ts` keys it from `CREDENTIAL_KEY`, else `CREDENTIAL_KEY_FILE` (created when missing), plus `CREDENTIAL_KEY_PREVIOUS` during a rotation (`docs/runbooks/credential-key.md`).
- `crove_kernel.credential` is definer-only machinery: no Crove role holds a grant on it. `credential_put` and `credential_drop` accept owners and admins of the org in context or the system; `credential_get` is granted to `crove_worker` only, answers in a system context only, and refuses once the member who connected the account has left the org.
- `kernel.channel.connect` (R2, owners and admins) receives the envelope, never the token, and takes no idempotency key: every seal differs, and connecting a connected account again is already a reconnect of the same row. `kernel.channel.disconnect` revokes the row and drops the credential; `kernel.channel.list` never returns a credential; `kernel.channel.credential` is the system query provider jobs use.
- `@crove/channel` holds the provider list and the offline `sandbox` provider; the RPC `channels.connectSandbox` makes and seals a sandbox token (on unless `CHANNEL_SANDBOX=false`).
- A reconnect by another owner or admin replaces the token and makes them the connector; the credential then lives on their membership. `credential_get` also refuses once the connector is no longer an owner or admin, or is disabled.
- Deferred to the steps that need them: `oauth_state` and the OAuth routes (S6), `external_call` and the refresh schedule (S4), a reseal command for rotations.

## Consequences

- Service reuses connections, tokens and `external_call` without touching Social's schema.
- New protected-path surface: two migrations, an HTTP route pair and decryption code. Each PR gets an independent security review, RLS matrix rows for the new tables and a redaction test.
- `CREDENTIAL_KEY` becomes a required secret once any provider other than `sandbox` is enabled; losing it means every connection must be reconnected (documented in a runbook).
- The full egress policy (ADR-0016) is still to write; until then the per-adapter allowlist is the control.

## Alternatives considered

- **Connections inside each module.** Rejected: Service would reconnect every page or read Social's tables.
- **Tokens in plain columns protected only by RLS.** Rejected: a database dump or a backup would expose every page token.
- **Code exchange in a job instead of the callback.** Rejected for v1: the user waits on the redirect either way, and a job adds a pending state to the connect screen; revisit if a provider's exchange is slow.

## Amendment (2026-11-03): a sealed copy of an ads token that outlives a disconnect, only to revoke it

Owner decision, 2026-11-03, in the Platform PO's chat ("Đồng ý"), for [#2296](https://github.com/DOS/Ludy/issues/2296) (W2 of running ads, [ADR-0043](0043-ads-write-running-ads.md) point 4). The rule above, that a disconnect leaves nothing to decrypt, has one deliberate exception, the same kind as the calendar's (a disconnecting calendar connection hands its credential to the worker so it can revoke at the provider, #2144).

- **Why.** Closing an ads write connection (or an ads read connection whose token holds a spend permission) used to drop the sealed token in the same transaction. The permissions the person gave the app at Meta then stayed valid until they expired or the person removed the app, and the pause of what Ludy had launched (ADR-0043 point 7a: a switch-off pauses first) could not run at all, since both calls need the token.
- **What may be kept.** A sealed copy of that one token, in `crove_ads.ad_token_seal`, made inside the transaction that closes the connection, **for at most seven days**. It is the same envelope the credential table holds (same key, same binding to org, provider and account); the kernel's `crove_kernel.credential` is dropped as before. The copy is made by a `BEFORE DELETE` trigger on `crove_kernel.credential` (W2-1: `crove_ads.token_hold`, owned by the migration owner, the only role that can read that table), so it is taken in the statement that drops the credential, by whichever path drops it (the generic disconnect of the channel layer included), and a live credential is never copied. It skips a platform's own data deletion (the person already removed the app; the erasure of an ad account whose write grant is another person's closes it under its own reason and does hold), a read connection with no recorded spend permission, a closed org, and every provider outside the list below. No setting a session can make switches the hold off (the trigger reads none). An org in offboarding still holds, so a disconnect in that window is revoked before the purge wipes what is left; the purge's own credential drops hold too, and the purge deletes the copies and the revoke state of the org as a step of its own after the connection rows, so what is still connected when the purge runs is not revoked (the purge deletes the credential and the owner should switch running ads off before closing the org).
- **Who opens it.** Only the revoke and wind-down worker, through a worker-only definer function, for two calls and no others: `DELETE /me/permissions` and the call that pauses an object. No command, query, API route or login role reads it; the table has no grant to any Crove role. The worker is given a narrowed view of the platform's writer that has those calls alone (a frozen object with the one method `revokeToken`; W2-1 pins the view, the one request it sends, and the source that names it). The definer answers only in the org's system context, for an obligation the sweep has claimed, and counts the try as it opens, so a crash or a retry still counts.
- **Which providers.** Meta's ads providers (`metawrite_ads`, and `meta_ads` with a recorded spend permission) and the offline sandbox. The owner approved this for Meta; another platform needs its own decision, and a provider outside that list gets no copy.
- **The membership rule.** Decision 6 and `credential_get` refuse a credential once the member who connected it has left the org or is no longer an owner or admin. Unlike `credential_get`, the copy opens whatever became of that member, only for these calls and only within its seven days, since ending the access is its only use: a member's removal must not leave the permission valid at the platform, so the revoke runs after the removal and before the copy is wiped.
- **When it ends.** Wiped when the revoke worked, when the person had already removed the app (Meta: error 190 with subcode 458), after ten tries or seven days, whichever comes first (the screen then says to revoke by hand: remove the app in the platform's settings), at once when nothing can be revoked from it (the platform refuses the token for another reason, so the grant may still stand; the copy does not open), when another live connection of the same person needs the grant (no call is made), when the account is connected again, and at once by the org's purge. A member's removal does not wipe it unrevoked: the revoke is tried first, and only then is it wiped. A deployment with no way to call the platform (the worker has no Meta app secret for the provider or no credential key) is a fault of its configuration and ends nothing: the worker records nothing, the copy stays pending, the revoke is tried once the configuration is fixed, and the seventh day ends it as given up by age. It never appears in an audit row, an event, a log line or the data of a job (ids and states only; the job carries no data at all).
- **The revoke is the person's, for the app, across orgs.** Meta's permission belongs to the pair of the person and the app, so `DELETE /me/permissions` also cuts every other live connection of that person for the app, in any org of a deployment (Ludy Cloud's included). So the obligation records the keyed hash of the platform user who granted the connection, and before the call a worker-only definer answers one boolean: whether another live connection with the same hash exists in any org. If it does, the call is not made and the obligation ends as `shared_grant` (the owner's decision, 2026-11-03: not narrowed to a single permission). With no grantor recorded (a connection made and never linked, as a refused link leaves one) the person is unknown, so the same member's other live connection of the same provider, in any org, is taken to be theirs and the call is not made. A new connection of the same account **by the same member** cancels the pending revoke in the transaction that seals its credential (another member's connection leaves the first member's revoke to go on, since the first member's grant at the platform stands). The cost, accepted: a grant that another connection needed can outlive the closing of the one that held the copy. It ends when that other connection is closed in its turn and holds a copy of its own, or when the person removes the app; a Meta read connection holds a copy only when its recorded scopes include a spend permission, so closing one that has none leaves the grant standing until the person removes the app (whether the last close of a grantor's connections should always revoke is open: #2490). A second cost, accepted: a connection made again while the call that removes the grant is already in flight (a window of seconds, after the copy was opened) is cut by that call; Meta then refuses its token on first use and the connection shows as expired, to be connected again. **A platform's data deletion request** deletes the held obligations and copies of the person it names, in every org, by the request's keyed hash (the person removed the app, so nothing is left to revoke); other people's obligations stay. The age wipe runs whether or not the ads module is installed (the hold is the database's, so a copy can exist with the module switched off).
- **Where it is proved.** `apps/kernel/test/invariant/ads-token-seal.db.test.ts` and `ads-token-seal-source.test.ts` (no grant to any role; the worker-only definers and their refusals; the hold on every close and the cases it skips; the guard of the state, the ten tries, the seven days, the age sweep that needs no job; the purge and a close racing it; the shared grant; the reconnect), `ads-token-revoke.db.test.ts` (the flow), `packages/ad-platform/test/revokers.test.ts` and `meta-write.test.ts` (the one request the revoker can send). `channel-credentials.db.test.ts` names the table among the sealed stores; the dated allowance of the step before it is gone, and the RLS matrix and the conformance list no longer carry it as pending.

## Amendment (2026-11-25): a short-lived `drive.file` token in the browser, for Google Picker only

Owner decision, 2026-11-25, relayed by the Meetings line PO, for [#3174](https://github.com/DOS/Ludy/issues/3174) (C2, the audio of a Google Meet recording). Decision 2 above says that provider tokens never reach the SPA. This amendment makes one narrow, named exception to it. Everything else in decision 2 stands: Ludy's sealed credentials, its refresh tokens and every token the server holds still never reach the SPA, a log, an audit row or an event.

- **Why.** A Meet recording is a video file in the organizer's Drive. The scopes that read it from the server (`drive.meet.readonly`, `drive.readonly`) are Restricted, which means a yearly security assessment (CASA) that is a spending decision of [#3177](https://github.com/DOS/Ludy/issues/3177). The owner chose, on 2026-11-15 and again on 2026-11-25, the route that needs none: the member picks the recording in Google Picker, and Ludy then reads only that one file with the non-sensitive `drive.file` scope. Google's web Picker "requires a specific access token passed through setOAuthToken" ([the Picker overview](https://developers.google.com/workspace/drive/picker/guides/overview), read 2026-11-24), so the browser must hold a token for the moment of the pick. There is no other way to run it.
- **What may reach the browser.** One access token, and only this one: minted **in the browser** by Google Identity Services (the token client, an implicit grant to the SPA's own Google client id), for the single scope `https://www.googleapis.com/auth/drive.file`, valid for about an hour. It is a different token from the one Ludy seals: the server never sees it, so it travels in no request to Ludy's API, is stored nowhere (not in a cookie, `localStorage`, `sessionStorage`, IndexedDB, the query cache or a log), and is dropped when the Picker closes. Ludy's sealed token, its refresh token and the connect's Meet scope (`meetings.space.readonly`) never go to the browser. No other provider, scope or picker is covered by this exception; another one needs its own amendment.
- **What the server does with the pick.** The browser sends one thing to the API: the Drive file id the member picked, for one recording row (an ordinary RPC command, no new route). The command refuses unless that id equals the file id Meet gave for that recording, so a member cannot make the server fetch a Drive file of their choice. The worker then downloads the file with the server's own sealed token, the first Google host only, under the adapter's existing host binding and egress guard, hands the video to the C2a extraction in crove-media, and stages only the audio. Nothing is downloaded before the member's click and pick.
- **Off by default, and the policy follows the switch.** The Picker is behind a setting that is off until an operator sets the Google project's API key, app id and client id. Only while it is on does the SPA's Content Security Policy allow the extra script hosts, frames and Trusted Types policy that Google's loader needs, the way Turnstile's keys already widen it (`apps/kernel/src/http.ts`, `apps/app/vite-csp.ts`, `apps/app/vercel.json`). With it off, the policy is byte for byte what it is today. The exact host list and policy names are settled from a real browser run, which needs the owner's Google project (#3177); until then they are written from Google's pages and marked as unverified.
- **What does not change.** The connect still asks the server for `meetings.space.readonly`; the incremental `drive.file` grant is the second permission line on Google's consent screen. The restricted scopes stay unused. The member's account stays the only authority: the server's read works only for files the app was given access to, and a member who only attended a meeting never sees the pick (the listing is the organizer's conferences only).
- **How it lands.** In steps, each behind the existing Google switch and built under mocked HTTP: the adapter (no UI), the data and the pick command (a migration and a contract schema), then the app step with the policy change. An invariant is changed only in two steps: first a test that accepts both behaviours, then the change.
- **Where it will be proved.** In the PRs of those steps: a contract test that no RPC input or output, event or audit detail names an access token or a Picker token field; a test that the SPA's policy is unchanged with the setting off and gains only the named hosts and the one Trusted Types policy with it on; a test that the browser code requests the `drive.file` scope and no other, and never writes the token to storage or the cache; the DB test of the pick command's file id check and its refusals for another member's row; and the adapter's host binding test (the bearer goes to the first Google host only).
- **What a live run must still confirm (gates, not details).** Whether a Meet-created file in the organizer's Drive can be picked and then read with `drive.file`; whether the server's token of the same client and user can read a file that the browser's token picked; how `setFileIds` behaves for a file the app cannot read yet; which Trusted Types policies Google's scripts create. If the first two fail, the route is dropped and the owner's fallback of 2026-11-15, the Ludy browser extension, is assessed by the Meetings PO.
