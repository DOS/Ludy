## Context and problem statement

ADR-0037 made a private note readable by its author only, and its decision N-6 (owner, 2026-10-28) said AI reads a note only when the author asks, one note at a time, and that agents never read notes. On 2026-11-03 the owner went further, in his words: "Với những data riêng thì Vy chỉ trả lời cho user đó thôi chứ. Nôm na là data nào user có access thì Vy (của người đó) có."

**There is one Vy.** A user sees one coworker with one name, in every app. The split below is not two products and not two coworkers: it only decides **whose rights Vy uses** for a piece of work, and so what it may read and write. Vy works in one of two modes:

- **Company mode** (Vy working for the whole company): the work runs as an org-chart agent (ADR-0029, the general manager's position among them), in an agent context under a position. It writes into the org's tables, drafts the team's brief, prepares proposals other people approve, under the write allowlist of #285. It keeps N-6: it reads no private data.
- **Member mode** (Vy working for one person, this ADR): the work runs under that member's rights, with exactly that member's access, and whatever Vy finds in private data goes back to that member only. Its write catalog, its memory and its results belong to that member.

In the technical text below "Vy in company mode" and "Vy in member mode" name these two modes; the code names (`member_vy` and the `member_vy_*` tables) belong to member mode.

What has to be decided is how member mode is built so that it is never more than the member (in the database and in the runtime), never leaks into org-wide outputs or into any sink the write guard does not see, and cannot be turned into a way around the guards company mode lives under. The seven points of the Platform PO's plan on #1677 (comment "Plan for N8, agreed with the Platform PO on 2026-11-03") are decisions 1 to 7; decision 8 sets how a job's output lands for reuse by meetings; decision 9 records the owner's decision of 2026-11-04 on where Vy's knowledge and memory come from; decision 10 records his decision of the same day on who may use Vy.

## Decision drivers

- The owner's rule, word for word: Vy in member mode has what the member has, and no more; private answers go to that member alone; org-wide work reads nothing private. Who may use Vy is a permission the owner or an admin sets (decision 10); the permission never widens what Vy reads.
- The core works with AI off; every model call goes through the AI budget meter; a person approves money, messages and spend (AGENTS.md, scope gate).
- AI output is tainted and deterministic checks decide (AGENTS.md). Note and transcript text is untrusted (ADR-0018), and in a firm a note holds facts about clients and their staff.
- Fail closed: everything a guard refuses an agent today stays refused. A new capability is a narrow, listed, tested admit, never a blanket exception.
- Smallest slice: a one-person company has one member and one Vy, with nothing to set up.
- One write path, tenancy, the sealed context and the agents' allowlist (#285) keep their meaning for the org's agents.

## Decision

### 0. One mechanism, two ways in, built in two stages

Vy in member mode runs in one of two ways; everything else here is the same for both.

- **Interactive run.** The member clicks (summarize this note). The API handles it in the member's own request context: a sealed user context, session-checked as for any request. No new kind of context is entered.
- **Background run.** The member starts work that outlasts the request (transcribe this meeting). The worker enters a member-scoped agent context (decision 1) for that one run. The worker's system context is never used: by ADR-0037 it reads no private text.

Notes N8 needs only the interactive way: one model call, answered in the request, no job. So the work lands in two stages, each with its own invariant step first (decision 7):

- **Stage A, for N8:** the `member_vy` agent row and the run record, the private-read flag, the member-keyed result and memory tables, the budget scope, and a single store command. No change to the notes policies, none to the org-chart agents' allowlist, no new context entry.
- **Stage B, for meetings and any later job:** the member-scoped agent context, its write catalog and guard branch, and the explicit admit of that context in the policies of the tables that opt in (notes first).

**The write boundary of stage A.** In stage A the run is the member's user context, which holds all of the member's write rights; the catalog of decision 2 binds only from stage B. So stage A holds the line in code, and a test pins it:
- the feature functions in `packages/agent` are pure (input in, parsed output out; no database, no runtime, no command);
- the only thing that persists their output is one store command, `kernel.member_vy.result.store`;
- a static test (the pattern of `meter-coverage.test.ts`) fails when a member-Vy feature module imports the runtime or names a command.

The notes plan (section 3.11) expected a definer through which the worker reads "the one note the author asked about". With this design none is needed: the author's own context reads the note through the ordinary policy.

### 1. Run context: the member's, never the system's, ending with the member

- **Interactive:** the member's user context. The run is recorded (below) and every command it causes carries the run in its audit detail, so the audit row shows the member and the Vy run beside it.
- **Background:** `crove_kernel.enter_member_vy_context(org, agent, run)`, worker login only (EXECUTE and `session_user`), the pattern of `enter_agent_context`. It refuses unless all of these hold, each re-read in the entering transaction:
  - the org is active; the run is `running` and not expired; the agent is active and of kind `member_vy` (an org-chart agent is refused here, and a `member_vy` agent is refused by `enter_agent_context`);
  - **the member is active now**, by one shared function (`member_vy_member_active(org, user)`) that both this entry and `kernel.member_vy.run.start` call, and that applies the test `calendar_credential_get` already applies: the user is still a member of the org, holds a base role that may act (owner, admin, member or viewer), holds `vy.use` (decision 10), and `user_account.disabled_at IS NULL` (#985). Background runs never pass `authenticate()`, so the entry must check it itself. The entry takes `FOR SHARE` on the member's `tenant_member` row (as approvals do), so a removal and an entering transaction serialize;
  - no kill switch covers the org, the feature's module or the agent, and the operator's global `ai` switch is not engaged; no hard-stop budget is spent.
- **Ending with the member.** The next transaction after the member stops being active fails with `MEMBER_NOT_ACTIVE`, so even a run in the middle of work cannot write another row; a model call already in flight finishes, but its result is discarded because storing it needs a new context entry. In addition, a system command cancels the member's live runs on: member removal (`kernel.member.removed`), account deletion, a disable, "sign out everywhere" and session revocation (ADR-0028). A background run has no live session of its own: it starts from a user command in a live session and then lives on its own expiry (below), cut short by any of these events.
- **Rights, never broader, in the database.** The sealed context carries the member's base role and `le_scope`, computed by the same function as `enter_context`, so an entity-limited Vy in member mode sees only those entities. It carries `max_risk` R1 at most (the lower of the agent's and the feature's); never R2 or R3, never an approval, never a proposal.
- **Rights, never broader, in the runtime.** Most tenant tables admit any context of the org; who may run which query is enforced by each command's `access` roles in the runtime (`ctx-query-access.db.test.ts`), which an agent-shaped context would otherwise bypass. So a command or query declares `memberVy` access only in addition to `access`, and runs for Vy in member mode only when its `access` also admits the member's base role from the seal. `ctx.query` lookups keep that rule. Feature code reads only through declared queries, never raw SQL on a table outside the feature's `reads`. A viewer who was granted `vy.use` therefore runs no command a viewer cannot run, reads only what a viewer can read, and their results stay in their own tables. (The meter's existing member-role constant, `AI_MEMBER_ROLES`, is owner, admin and member; the budget admit for Vy in member mode checks `vy.use` instead, decision 10.)
- **The shape.** The background context is an agent context (`actor: 'agent'`) with two added fields, both inside the seal: `member` (the user the run acts for) and `kind` (`member_vy`). It always carries a non-null `agent`, so the "system" clause used by the notes, notifications, saved view, calendar and inbox policies (`ctx_user_id() IS NULL AND ctx_agent_id() IS NULL`) can never match it. `ctx_user_id()` stays NULL, so every policy written as `... = ctx_user_id()` refuses it by default. A table that admits Vy in member mode does so through a new helper, `ctx_acting_user_id()` (the context's user for a member, the sealed `member` for a member-scoped agent, NULL for everything else, the org-chart agents and the system included), and only where decision 2's catalog lists it. Every guard branches on the sealed `kind`, never on a lookup. Why not a user context with a `via` marker: every guard written for agents (the write allowlist, `refuse_agent_write`, P02, P03, P05, P06) and every one written for users would need an exception, and one forgotten fails open; here an unlisted table or command fails closed, as for every agent today. The Platform PO accepted the agent shape for background runs and the plain user context for interactive ones.
- **The database holds the binding between member, agent and run**, not only the commands:
  - an `agent` row of kind `member_vy` is inserted only with `member_user_id = ctx_user_id()`, the fixed `member_vy` template (no role key, so permissions come from the member) and no position; `kind` and `member_user_id` never change after insert; one per `(org_id, member_user_id)`;
  - `position` refuses a `member_vy` agent as `holder_agent_id`;
  - an `ai_run` row of a `member_vy` agent is inserted only in that member's own user context;
  - the agent is made by the command that starts the member's first run, so without these a bug in one command could still not give member A a run of B's Vy, or turn an org-chart agent into a "member" context with someone's rights.
- **The run's metadata is the member's, not the org's.** `ai_run` is read today by every context of the org. For a `member_vy` run a restrictive policy lets only its member read the row; owners and admins see its cost through `org_usage` (a figure per member, never a subject), and `ai_run.error` holds a fixed code, never text. The feature and the subject (a type and an id) live on the member-sealed `member_vy_result` row (decision 3), which `kernel.member_vy.run.start` creates in status `running`.
- **A run is for one feature and one subject.** `kernel.member_vy.run.start` (R1, the member's own command in the member's own session) records both. The feature declares an expiry and the kernel caps it (30 minutes for a note, at most 4 hours for a meeting). One live run per member **per feature** (amended 2026-11-12, [below](#amendment-2026-11-12-3029-one-live-run-per-member-per-feature)); the next start of the same feature closes an abandoned run of that feature, so a crashed request does not block the member. The job carries ids, never text.
- **No transaction across the model call.** The store command re-enters the context, re-checks that the member is active and that the run is still `running`, and only then writes.
- **Isolation of a member-mode read, and what it sees of the membership (residual note, #2800 review).** A command of Vy in member mode runs in one READ COMMITTED transaction. A `ctx.query` inside it holds the `FOR SHARE` membership lock that its command took on entry, so a removal of the member waits for the command to end, and the command never writes after the member is gone. A read-only query of Vy in member mode (a `defineQuery` declared `memberVy`) runs REPEATABLE READ and READ ONLY (`runtime.ts`, the same as a streamed query), so the member's rights it entered with and the rows it reads are one snapshot: a removal that commits while such a query runs is not seen by it, and the query ends with that snapshot. This is not a leak: the query reads at most what the member could read an instant earlier, it writes nothing, and the next transaction fails with `MEMBER_NOT_ACTIVE`.
- **The ceiling is the database's; the narrowing is code's.** The database holds a run to the member's rights. That a run reads only its subject (one note, one meeting and its attendees' names) is the feature's declared `reads`, kept by its code, and a test per feature fails when a query outside it appears. The model cannot widen it, because it has no tools (decision 5).

### 2. Two agent kinds, and the allowlist is no back door

- The org-chart agents change nothing: their allowlist (#285), exempt list and write rules stay byte for byte. `crove_kernel.agent` gets `kind` (`org_chart`, the default, or `member_vy`) and `member_user_id`, bound as decision 1 says. The kind is named `member_vy`, not `member_assistant`: Ludy's AI is a coworker (AGENTS.md).
- **Vy in member mode has its own catalog**, `crove_kernel.member_vy_table`: one row per table with a `mode` (`read` or `write`) and the ADR that admits it, filled only by a migration, so each addition is a protected-path PR with a security review. The write guard (`agent_write_guard`) takes a second branch for the sealed `kind = 'member_vy'`: a write passes only if the table is in the catalog with mode `write` and the row passes its own restrictive policy (the row belongs to the member). The write catalog starts with:
  - `member_vy_result` and `member_vy_memory` (decision 3), the member's own rows only;
  - `ai_run`: taint and the private-read flag on its own run, false to true only.

  The audit, idempotency and outbox rows the runtime writes for any agent are **not catalog rows**: they are narrow rules of the guard's `member_vy` branch (audit: this agent and run only, with `detail` limited to listed keys whose values are ids, enums, numbers and flags, decision 4; idempotency: this run's key only; outbox: none, neither `outbox_pending` nor `outbox_event` (the trigger `a00_member_vy_forbid` refuses it), so a member-mode run emits no event; never an agent wakeup). The catalog lists exactly the tables whose policies read `ctx_acting_user_id()`, so the two-way scan below stays exact. `member_vy_memory` is listed with mode `read`: a background run reads its member's memory and writes none, and the write policies stay on `ctx_user_id()`.
  The meetings plan adds nothing to it under decision 8: its output lands in `member_vy_result`.
- **Opting in to read.** A table whose policy reads `ctx_acting_user_id()` is listed with mode `read`; notes are first, in stage B. The B4 test (decision 7) scans `pg_policy` and `pg_proc` for the helper and compares them with the catalog in both directions: it fails for a policy that uses the helper and is not in the catalog, for a catalog row with no policy, for the helper in an INSERT, UPDATE or DELETE policy of a table without mode `write`, and for the helper in any definer that gates owner or admin actions (`private_counts`, the personal-data finder and erasure keep `ctx_user_id()` with `actor = 'user'`, so an owner's Vy never gains owner-only definers).
- **Never in the catalog:** `task`, `task_comment`, `proposal`, any table another member or an org-chart agent reads, and the tables `refuse_agent_write` names. `task` and `task_comment` carry no guard (their own lease rules) but need a lease on a position, which a `member_vy` agent has none of, so they refuse it; a test pins that.
- **Commands.** A command or query is open to Vy in member mode only when it declares `memberVy: { reads?, taint }` (a third access kind beside `access` and `agent`), R0 or R1, with taint `propagate`, and its `access` admits the member's role (decision 1). No task command, no approval command and no other module's command declares it. P03 applies as it does to agents.
- **Result.** "Agents write only the allowlist" is kept for the org's agents, and a second invariant says the same of Vy in member mode with its own catalog. Neither list grows without a migration.

### 3. Memory and results: tables keyed by member, sealed to that member

- **`crove_kernel.member_vy_result`:** one row per run, created by `kernel.member_vy.run.start` and filled by the store command: `org_id`, `id`, `member_user_id`, `run_id`, `feature`, `subject_type`, `subject_id`, `status` (`running`, `ready`, `failed`), `error_code` (a fixed code), `source_revision` (so the screen can say the note changed since), `body` (the text, class `pii`), `tainted` (true until the member acts), `private_read` (decision 4), `created_at`, `expires_at` (30 days). No stored title: the result list shows the subject's title as read in the member's context.
- **`crove_kernel.member_vy_memory`:** what Vy keeps about the member so it is useful. In v1 only entries the member made or confirmed, such as a preference ("tóm tắt ngắn", how they like a client named), shown in a screen "Vy nhớ gì về tôi" where the member edits or deletes each one. Vy writes nothing into memory from a note or a meeting: a model's output never becomes memory without the member's click, so a note cannot plant a memory. It lives until the member deletes it or the purge below. Memory derived from private text is a later decision with its own review.
- **Keys and tenancy.** `PRIMARY KEY (org_id, id)`, `org_id`, RLS through `apply_tenant_rls`, and restrictive policies in the style of ADR-0037: read and write only where `member_user_id = ctx_acting_user_id()`. No owner, admin, other member, viewer, org-chart agent or system context reads or writes a row. No foreign key to `tenant_member`, so a removed member's rows follow the same 30 days as their private notes.
- **A result shows only while its member can still read its subject.** The read query joins the subject through the member's own context, so a result whose subject is gone or unreadable (the author made a shared note private, the member's scope narrowed to some entities, the member lost the meeting) is hidden at once and deleted by the expiry sweep. A summary never outlives its member's access.
- **The worker and the definers.** As in ADR-0037 the worker reaches these rows only through named definers that return no text: `member_vy_results_expire(limit)`, `member_vy_member_data_purge(org, user)` and `member_vy_private_counts()` for the owner's removal warning.
- **Member removed.** The module-independent `kernel.member.removed` subscriber schedules the purge 30 days later, with the rule of `notes.member_items.purge`: counted from the removal's audit row, never purges a member who is back, fails closed when no date exists. A member's notes, results and memory go on the same day. Live runs are cancelled at once (decision 1).
- **Source deleted.** A result whose source note is deleted, purged or erased is deleted with it (by `subject_id`). A note is never kept alive by its summary.
- **Org purge and export.** The org purge deletes both tables (a migration, before the kernel's tasks). The export (#38) holds no row of either, only a count per member, as ADR-0037 N-5 does for private items. Each member downloads their own results and memory with their notes ("Tải về").
- **Personal data (#923).** `body` and memory text are `pii` in the manifest and the registry. The finder counts per member as for private items and never shows text. An erasure (R3, owner) deletes the results whose source it erased, and the others that match the value, without showing them, after the members were told, as `private_erase` does.
- **Search.** No `member_vy_result` in `⌘K` or in any search index in v1; if one is added later it carries the same member-only policy.
- **Logs.** No prompt, no answer and no note text in a log, an error message or the meter. `NoObjectGeneratedError` carries the model's text, so the error object is never logged, only its name, as `metered()` does; each new feature gets a test for it. Worker caches of subject text are keyed by run and dropped at its end; nothing is cached across members or runs.
- **The operator.** As ADR-0037 says for notes, "private" means private from the org. The text Vy in member mode reads is also sent to the AI endpoint the deployment is configured with (decision D9); the button says so, and a self-hosted deployment can point it at a local model.
- **Third parties.** An OAuth client token (ADR-0032) starts a run on private data only with a scope that covers private notes; otherwise a first-party session is needed.

### 4. Org-wide outputs carry nothing private: a flag that blocks, a structure that cannot read, and every sink closed

A rule in a prompt is not enough, so there are three layers, none of them a prompt, and a list of sinks.

1. **The structure.** `member_vy_result` and `member_vy_memory` are readable by the member alone (decision 3), and from stage B Vy in member mode writes only the catalog (decision 2). So the org's briefs, digests, proposals other people approve and everything an org-chart agent or the system composes cannot read what Vy in member mode produced.
2. **The flag.** Each run carries `private_read`, **computed by the kernel**: the store command reads the subject's visibility in the member's context, in the same transaction, and sets the flag when the subject is private or the visibility is unknown; it never trusts a value from the feature code or the client. The member's own `member_vy_memory` entries and any earlier result count as private sources, so a run that reads them inherits the flag. The flag is stored on `ai_run` and on the result (false to true only, never cleared), and the meter's scope carries it. A result with `private_read` is the member's own and never leaves: its text reaches an org-visible sink only through the member's own command, after a click, with the exact text on screen (the rule of hand-over in ADR-0037 and notes plan 3.5). That command takes the result's id, reads it in the member's own context (so another member cannot name it), refuses unless `confirmed: true`, and creates the row `tainted` with a `source_ref` while the text is unedited. Commands with an org-visible sink that take text from a result are on a list (`MEMBER_VY_SINKS`); a test enumerates the commands whose input names a result and fails for one not on it.
3. **The types and the dependency rule.** Readers that return private text return a branded type (`PrivateText`). The org-level features in `packages/agent` accept plain strings only, and a static test fails when one of them imports a reader of `memberVy`.

**Sinks the write guard does not see.** `agent_write_guard` exempts `task`, `task_comment`, `ai_run`, `activity`, `outbox_event` and `refusal_tally`, lets any agent insert `outbox_pending`, and lets an agent write `audit_event` rows with any `detail`; `crove_jobs` is outside it (#333). Each is closed for Vy in member mode, in both stages (in stage A by the single store command, in stage B by the guard branch as well), each with a test:
- **`activity`** (the org-visible feed): refused for a `member_vy` context, or limited to fixed kinds with no text.
- **`audit_event.detail`** (anchored in the WORM stream, never erasable): in the `member_vy` branch limited to listed keys whose values are ids, enums and numbers; the `kernel.member_vy.*` commands audit through `auditValue` markers only. A test plants text in `detail` and expects `AGENT_FORBIDDEN` (stage B) or a marker (stage A). The accepted residue is the one ADR-0037 section 3 names: ids and times. The ids in `detail` (`runId`, `resultId`, `subjectId`, `subjectType`) and `target_id` are bound by the guard to the run's own: the run, its one result row, that result's subject; `target_id` is none, or the run itself under `kernel.ai_run`, and a denied row has none (the runtime drops the refused command's target). `id`, `command_id` and `input_sha256` are set by the runtime (a uuid and a hash) and are the residual the guard does not bind.
- **Outbox events:** none from a member-mode run in stage B: `crove_kernel.emit` is refused with `AGENT_FORBIDDEN`. A later change that lets a background run emit an event declares the event types (ids-only payloads, no org-chart agent wake-up subscribes to them) and relaxes the guard and the trigger together, with an invariant case first.
- **Stream hints:** to the member only, as `stream-notes-audience.db.test.ts` does for private notes.
- **Notifications, push and mail digests:** fixed words and ids, never a result body or title.
- **Idempotency results and job payloads:** ids only.
- **`ai_run`:** the member-only policy and the fixed error code of decision 1.

Blocked for a result of a run with `private_read`: an org-visible table, an outbox payload, an activity, a notification or a mail, a kernel proposal (read by the approvers), a task or a task comment except through the confirm command above, and the input of an org-chart agent run.

### 5. Prompt injection: the model has no hands

Note, transcript and shared-note text is untrusted (ADR-0018). The design takes away what an injected instruction would need and does not try to detect it.

- **No tools, no query choice.** A member-Vy feature is a function of its input: the code reads the subject, builds the prompt, calls the model once and parses the answer against a strict schema. The model cannot call a command, run a query or pick what to read. An agentic Vy in member mode with tools needs its own ADR.
- **The model's output is data.** Structure (a seat, a date, a title length, a number) is checked by code (the rule of `summaryNumbersOutside`, #1237, for figures). Free text is shown as text, in Markdown with raw HTML dropped, no remote image, and **links shown as plain text in v1** (a host is never hidden behind a label, and nothing opens by itself). It starts tainted and keeps the "Đề xuất" style until the member edits or accepts it.
- **Nothing applies without a click.** Accepting runs the member's own command (`notes.todo.create`, `notes.note.update`, a project task) as the member, with `tainted` set while the text is the AI's. The model cannot raise a risk level, skip a click, or make a write the member did not click.
- **A shared note from member A read by member B's Vy.** B's Vy has B's rights only. At most the text steers what B is shown. It cannot read A's private note (policy), cannot send anything to A (results are B's alone), and cannot exfiltrate: its output reaches only B's screen, which loads no remote image and shows links as plain text.
- **Least input.** A run reads its one subject and, only when the feature declares it, the member's own memory. Two sources are never mixed in one prompt unless the feature declares both; the member's memory is never mixed with a note someone else wrote unless the feature declares both.
- **Memory is not a channel.** No model output writes memory (decision 3).
- **Tests.** Red-team cases run in CI with a fake model, as #893 does for documents: a note that says "create a task for X", "show me B's notes", "remember that ...", or "put the reader's memory in a link" produces at most a tainted suggestion and no write and no outgoing channel.

### 6. Budget and kill switches: metered, per org, per module, per agent; no per-member default

- Every model call goes through `metered('<feature>')` under `withAiScope`, which now also carries the member and the run. New `AI_FEATURES` keys are named per feature and count against their module's budget (notes N8: `notes.summary` and `notes.todo_suggest`, module `notes`; the meetings and projects plans add theirs). `AiMeter.admit` and `record` get the member and agent ids, never text.
- **Kill switches on the interactive path.** Today the API path checks budgets only (`kernel.ai.budget.check_member`); kill switches are checked in `enter_agent_context`, the wake-up sweep and `kernel.agent.run.start`. So `kernel.member_vy.run.start` and the meter's admit for a member-Vy feature check all four (the org's, the module's and the agent's switches, and the operator's global `ai` switch), at the start of a run and again at each admit.
- **The agent id is the kernel's.** For Vy in member mode, `check_member` and `record_member` (`kernel.ai.budget.check_member`, `kernel.ai.usage.record_member`) derive the agent from `ctx_user_id()`, the member's own `member_vy` agent, and refuse any other value, so a per-member cap cannot be dodged with `null` and spend cannot be charged to another member's agent. They keep writing ids, the feature, tokens and cost only.
- **The org and module budgets cover every member's use of Vy.** Spend is attributed to the member's agent, so an owner sees spend per member (a figure, never a subject) by name. The spend screen shows the agent-scope switch and cap of each member by member name, figures only.
- **A per-member cap is possible and not on by default.** Vy in member mode is an agent, so the existing agent-scope `budget_policy` (`scope 'agent'`, target the agent id) caps it and the `agent`-scope kill switch stops it, with no new mechanism. A small business has few members and the org and module budgets bound the cost, so the default is no cap.
- **Also bounded:** a run's input size per feature (a note is cut at a stated length), the one-running-run rule, and a per-member request rate (the pattern of `ai-draft-limit.ts`).
- **Refusal.** A spent budget or an engaged kill switch refuses the call with the existing `AI_BUDGET_EXHAUSTED` message; the screen keeps working with AI off.

### 7. The invariant route, in two steps per stage, plus a clean-up

Each stage ships as: (a) an invariant-only PR that the suite can run, merged by the Platform PO; (b) the feature PR that pins the new behavior; (c) a clean-up PR after (b) merges. CI runs the base branch's copy of the suite, so a PR cannot fix a pinned test itself, and an invariant edit in a feature PR takes effect only after it merges. This ADR is step zero.

**Mechanics the suite can run** (the invariant job fails on a skipped test, so there is no `it.skip`):
- Step (a) branches on `to_regprocedure('crove_kernel.enter_member_vy_context(uuid,uuid,uuid)')` and on the existence of the new tables. When the function is absent it asserts that no `member_vy` context can be entered.
- The negative cases are unconditional from step (a): another member's private note, an org-chart agent, the system context, writes off the catalog. The base copy then catches a regression in the feature PR.
- Step (c), after the feature PR merges, removes the "absent" branch.

**Stage A (N8's interactive path):**
- **A1. New author-only tables** `member_vy_result` and `member_vy_memory`: row factories and `PENDING_TABLES` entries first (the three-PR rule, #291); an `AUTHOR_ONLY` exception in the RLS matrix, as notes have: the system context reads no row and writes only through definers; the org-chart agent context reads and writes none. Cross-org cases stay.
- **A2. A test file in the invariant suite,** `member-vy-private.db.test.ts`: another member, an owner, an admin, a viewer, an entity-limited member, an org-chart agent context and the system context read and write none; the definers return no text and refuse every other login; a forged context is refused by the seal; a `member_vy` run is invisible in `ai_run` to everyone but its member and carries a fixed error code; a result is hidden when its subject becomes unreadable to the member (a note made private, a narrowed scope); a disabled or removed member's run cannot start or store.
- **A3. The registry, purge and export checks** (`personal-data`, `org-purge-coverage`, offboarding): both tables classified, deleted by the org purge, and left out of the export except as a count.
- **A4. Metering:** the meter-coverage test accepts the new feature keys and the member and run fields in the scope; kill switches (all four) are honoured on the interactive path; `check_member` and `record_member` refuse an agent id that is not the member's own; no log carries the error object.
- **A5. The `member_vy` agent row and its binding:** `agent.kind` and `member_user_id` exist from stage A, so `enter_agent_context` must refuse a `member_vy` agent from the day the first one exists. Cases: a `member_vy` agent is inserted only with `member_user_id = ctx_user_id()`, the template and no position; `kind` and `member_user_id` are immutable; its `ai_run` is inserted only in that member's context; `position` refuses it as holder. The org chart, agent lists and budget screens leave `member_vy` agents out of the org's positions and counts.
- **A6. Sinks:** the audit `detail` test with planted text, and tests that the store command writes no activity, outbox payload text, notification text, idempotency text or job payload text.
- **A7. The static boundary tests** of "The write boundary of stage A" and of decision 4's layer 3.
- **A8. The provider ports** (decision 9): the fake-provider test (nothing the member cannot read, no other member's memory, `forget` on erasure and removal) and the static test that features import the ports, not a vendor client.
- **A9. The permission `vy.use`** (decision 10): the cases listed there, with the same no-skip mechanics.
- **No change** to `notes-private.db.test.ts`, the agents' allowlist or any notes policy in stage A.

**Stage B (background runs):**
- **B1. ADR-0037 decision N-6 is revised on purpose.** "Agent contexts read and write nothing" becomes "an org-chart agent context reads and writes nothing; a `member_vy` context reads what its own member could, in a table that opted in". This is the one weakening of an accepted invariant, and it is the owner's rule of 2026-11-03. `notes-private.db.test.ts` keeps every existing case and adds: a `member_vy` context reads only its own member's notes (own private, shared per the member's role and scope), never another member's private note, never as the system, never writes a note.
- **B2. The agents' invariant** keeps its allowlist unchanged and gains: `enter_agent_context` and `enter_member_vy_context` refuse each other's agents; Vy in member mode writes only the write catalog and only its member's rows; it cannot write `task`, `task_comment`, `proposal`, `activity` or any table off the catalog; its `max_risk` is R1; the run ends when the member is removed or disabled, signs out everywhere, a kill switch engages or the budget is spent.
- **B3. The sealed context** (`context.db.test.ts`, `context-token.db.test.ts`): `member` and `kind` are inside the seal and a forged one is refused; `ctx_user_id()` is NULL and `ctx_agent_id()` is not for a member-scoped agent, so the "system" clause never matches it; `ctx_acting_user_id()` is as described and NULL for org-chart agents and the system.
- **B4. The catalog test** of decision 2: a two-way scan of `pg_policy` and `pg_proc` against `member_vy_table`, with the INSERT, UPDATE and DELETE and the owner-definer rules.
- **B5. The RLS matrix** adds the member-scoped agent as an actor with its reasoned exceptions; stream hints go to the member only; the runtime test that a `memberVy` command also needs the member's role in `access`.

**Not changed, and if it must change it goes back to the owner:** no system-context read of private text; no read by an owner or admin of a member's results or memory; no R2 or R3 and no approval by Vy in member mode; no org-chart agent reading a note; no model with tools; no result text in an org-visible sink without the member's click (decision 8 keeps this for meetings).

### 8. Reuse by meetings: the output is the recorder's result, published by one click

A background job (the meetings plan: transcript, summary, decisions, action items) is a member-Vy run like any other, and its output lands in the recorder's own `member_vy_result`, readable by the recorder alone. The recorder publishes it to the meeting's attendees with one click: a command of the recorder, as the recorder, with the exact text on screen, creating the meeting's attendee-visible rows `tainted` with a `source_ref` while the text is unedited (the rule of decision 4). No `member_vy` context writes into a table another member reads, so decision 2's catalog needs no meeting table.

Rejected for the first slice: a "subject-audience sink" rule, where a `member_vy` run may write into its subject's own tables when its inputs were exactly that subject, the sink's readers are exactly the subject's readers, and the rows stay tainted. It changes a line of "Not changed", so the owner would have to sign it off; it can be reopened if one click proves too much friction. ADR-0047 section 3 (PR #2554) is updated by the Frontend PO to point here; this ADR's PR does not touch it.

### 9. Vy's brain sits behind a provider interface; the permission boundary stays in Ludy (owner, 2026-11-04)

Vy's "brain" is a knowledge base of the org's shared data plus a long-term memory per member, with a model on top. The owner decided on 2026-11-04 that a hosted provider may supply it in Ludy Cloud while Ludy itself keeps the permission boundary.

- **A provider interface in `packages/agent`.** Three ports: the model (the OpenAI-compatible endpoint of decision D9, as today), **memory** (read, write and forget a member's long-term entries) and **knowledge** (retrieve passages of shared org data for a question). Features call the ports, never a vendor.
- **The built-in implementation.** Self-hosted Ludy ships one, with no outside service: memory is `member_vy_memory` (decision 3), and knowledge is a set of declared queries run in the member's own context (decision 1), so a deployment on `docker compose up` has a working Vy. A richer index (search over shared notes, documents and the books) is a later feature of that implementation, still reading only through declared queries.
- **A hosted provider in Ludy Cloud.** Ludy Cloud may plug in a hosted provider for any of the ports through the private Cloud layer, which is outside this repository (AGENTS.md). Nothing here names it, and nothing in the open-source code depends on it.
- **The boundary does not move, whatever the provider:**
  - Retrieval is filtered by the member's own rights **before anything reaches the provider**: the knowledge port is fed by declared queries run in the member's context, so the provider never sees data the member cannot read, and a result that fails decision 3's "member can still read the subject" test is not sent.
  - One member's memory is never served to another: a provider's memory is keyed by `(org, member)`, and Ludy asks it only for the member the run acts for.
  - The provider holds no permission logic of its own and Ludy never relies on one: the answer to "may this member see this?" is Ludy's, decided before the call. A provider that keeps an index of org data does so only from text Ludy sent for a member who could read it, and its store is never queried for another member.
  - Memory writes stay the member's click (decision 3, "Memory is not a channel"), whatever the provider. Output from any port is untrusted and tainted like a model's (decision 5), and the private-read flag counts a provider's memory and knowledge passages as private sources when they came from private data (decision 4).
  - Deletion reaches the provider: the port has `forget(org, member)` and `forget(source)`, called by member removal, the 30-day purge, source deletion, erasure and the org purge. A provider that cannot delete is not eligible. Its use is metered like any model call (decision 6) and its calls pass the same kill switches.
  - What leaves the deployment is only what the member's context could read, sent for a feature the member asked for (the operator note of decision 3 applies to a hosted provider too, and the button says so).
- **Tests (stage A):** a fake provider that records every input it is given. Cases: nothing a member cannot read ever appears in it; another member's memory is never requested; an erasure and a removal call `forget`; with the built-in implementation the same feature tests pass. A static test fails when a feature module imports a vendor client instead of the ports (the pattern of `meter-coverage.test.ts`).

### 10. Who may use Vy in member mode: the permission `vy.use`, in the role model (owner, 2026-11-04)

The owner's words, in the Platform PO's chat: "Ở chỗ set quyền có thêm 'Sử dụng trợ lý Vy'", and then: "Chỗ phân quyền thì có mấy pre-set role sẵn để admin có thể set/invite nhanh nha. Chứ cho 1 tỷ cái quyền rồi kêu set từng cái không được". So `vy.use` is not a tick in a list of permissions: it lives in the existing role model, and an admin sets or invites a person with presets. This replaces the earlier ruling that every viewer gets Vy. It was added after the Platform PO's review of this ADR; the build review of stage A checks it.

- **The permission and its label.** `vy.use` is added to the permission system (`ROLE_PERMISSIONS`, `ctx_has_permission`). Its label is "Làm việc với Vy" in Vietnamese and "Work with Vy" in English. The owner's wording said "trợ lý"; the label follows the owner's coworker rule of 2026-11-02 (Vy is a coworker, never an "assistant", AGENTS.md). The owner has not confirmed the wording yet; the Frontend PO is asking him.
- **Where it comes from, by presets.**
  - **Base roles:** owner, admin and member include `vy.use`; viewer does not (`crove_kernel.permission_default (base_role, permission)`, filled by migration).
  - **Department preset roles** of the catalog grant it through `role_permission`: `finance.chief_accountant`, `finance.accountant`, `external_accountant`, `crm.sales`, `desk.agent` and `hr.manager`. `finance.viewer` does not. A preset role added later says in its definition whether it includes `vy.use` (a Marketing role for Social and Ads is asked for in [#2612](https://github.com/DOS/Ludy/issues/2612)).
  - **A grant or a removal for one person is only for exceptions**, behind "Nâng cao" on the member row: `crove_kernel.member_permission_override (org_id, user_id, permission, allowed, set_by, set_at)`, written only by the audited command `kernel.member.permission.set`. The screens never show a grid of single permissions ([#2611](https://github.com/DOS/Ludy/issues/2611)).
- **Who may set an exception (decided by the Frontend PO, 2026-11-04).** An owner may change it for anyone. An admin may change it for admins, members and viewers, never for an owner (the rule that already keeps admins from inviting owners). A member cannot change their own. Who may assign a department role is not changed here (today an owner, R3); #2611 asks whether admins may.
- **One resolution.** A function `member_has_permission(org, user, permission)` answers: an override with `allowed = false` means no; `allowed = true` means yes; otherwise the base-role default; otherwise any role assignment whose role grants it. `ctx_has_permission` calls it for a user context, and the background entry of decision 1 calls it with explicit arguments (an agent-shaped context has no user for `ctx_has_permission`), so the two cannot drift. For `vy.use` a role assignment counts whether it is org-wide or for one legal entity, because the permission has no entity meaning and Vy's reach stays bounded by the member's own `le_scope` (today `ctx_has_permission` counts only org-wide assignments). A viewer honours an override or a role grant only for a permission marked `grantable_to_viewer`; `vy.use` is the only one marked, and every other permission keeps its rules, among them "a viewer holds no permission". `kernel.member.role.assign` refuses a viewer a role that grants a permission (`ROLE_PRIVILEGED_FOR_VIEWER`) unless every permission the role grants is so marked: otherwise every preset, now that each grants `vy.use`, would become unassignable to a viewer. A viewer who is given a department role therefore works with Vy, and the member row says so.
- **Where it is checked: every run, at run time.** The start command of an interactive run; every entry of a background run (`enter_member_vy_context`, so the next transaction after the permission is removed fails with `VY_NOT_ALLOWED`); the store command; and the budget admit for a `memberVy` feature (`check_member`). Removing the permission cancels that member's live runs, as removing the member does (decision 1), and a model call in flight has its result discarded.
- **What it does not change.** It only switches Vy in member mode on or off for the member; it never widens what Vy reads, which stays exactly the member's own access (decisions 1 and 2). A viewer who has it reads only what a viewer reads, runs no command a viewer cannot run, and their results stay in their own tables. Vy in company mode is not governed by it. Whoever grants it gains no way to read another member's data through it.
- **In the app.** The members screen offers the preset roles as one pick (a base role plus a department role) and the "Làm việc với Vy" switch behind "Nâng cao"; the buttons that start Vy in member mode are hidden for a member without the permission, and the server refuses regardless. A typed constant (`VY_USE_PERMISSION`, the pattern of #1641) is the one display gate.
- **The invariant route.** This is a permission change, so it is part of stage A's step (a) and names what it changes: `ctx_has_permission` gains defaults, overrides and an entity-scoped role path for one permission (`roles.db.test.ts` pins today's meaning); the rule "a viewer holds no permission" gets one marked exception; `kernel.member.role.assign`'s viewer refusal is narrowed as above; a new setter writes `member_permission_override`. Cases: the defaults are pinned (owner, admin, member yes, viewer no); each department preset grants it and `finance.viewer` does not; a viewer without a grant is refused; a viewer with a grant passes for `vy.use` and for no other permission; a deny beats the default and the role; an admin cannot change an owner's setting and a member cannot change their own; a system or agent context holds none through `ctx_has_permission`; a revoke and a removal cancel live runs; the manifest-permissions test lists `vy.use`; the command-labels test knows the new command. The mechanics are those of decision 7 (no skips, negative cases unconditional).

## Options considered

**For where Vy in member mode runs**
- **A. The member's own context for a request, and a member-scoped agent context for a job (accepted).** Fails closed, one catalog per kind, no definer to read a note.
- **B. A user context with a `via` marker for both.** Rejected for the reason in decision 1: every user guard and every agent guard would need an exception, and a forgotten one fails open.
- **C. The worker's system context with a definer per read.** Rejected by the owner's rule and ADR-0037: the system context would read every member's private text through a growing list of definers.
- **D. One Vy in company mode that checks the asker's rights in code.** Rejected: a check in code is the thing a prompt injection or a bug skips; the database must hold the line, and the Vy in company mode keeps N-6.

**For the budget**
- **A. Org and module budgets, a per-member cap optional (accepted).** **B. A per-member cap by default.** Rejected for v1: setup a one-person company does not need. **C. No attribution per member.** Rejected: the owner should see where the spend goes.

## Consequences

- Good: the owner's rule is enforced by the database and the runtime and tested in the invariant suite, not by a prompt; the org-chart agents' allowlist and ADR-0029 are untouched; N8 needs no new notes definer; meetings and projects reuse one mechanism, built once.
- Good: a one-person company has the same one Vy from the first click and sets up nothing (the owner has `vy.use` by default); admins invite and set people with preset roles, not a grid of permissions; for a viewer who is given it, Vy is limited to what the viewer reads.
- Bad: three new kernel tables or catalogs (the two member tables and `member_vy_table`), a context entry function, a guard branch and several policies: each a protected-path change with its own security review, in two stages.
- Bad: stage B weakens one accepted invariant (N-6) on purpose; the reviewer's judgment, and the owner's rule, carry it.
- Bad: in stage A the write boundary is code (pure features, one store command, a static test) because the run is the member's whole user context; the catalog binds only from stage B.
- Bad: the narrowing of a run to its subject is code, not database, so each feature needs its test.
- Neutral: private text is sent to the deployment's AI endpoint; the operator can read the database as before.

## Review rulings (Platform PO, 2026-11-04, on PR #2572)

1. **Agent shape for background runs, the member's own context for interactive ones: accepted**, on these conditions, all in the text above: the context always carries a non-null agent so the system clause never matches (B3); `member` and `kind` are inside the seal and the guard branches on the sealed `kind`; decisions 1 (disabled members, the runtime ceiling, the database binding) apply.
2. **A catalog, not a naming convention,** with a `mode` column and a two-way B4 scan (decision 2).
3. **The 30-day purge shared with notes: kept.** `member_vy_result` keeps its own 30-day `expires_at`; `member_vy_memory` lives until the member deletes it or the purge; `private_read` is set when unknown, computed by the kernel, counting memory and earlier results as private sources, never cleared (decision 4).
4. **Names:** `member_vy` (the kind) and `memberVy` (the declaration); tables `member_vy_result` and `member_vy_memory`; commands `kernel.member_vy.*`; helper `ctx_acting_user_id()` (it returns NULL for org-chart agents and the system context; `ctx_member_user_id()` would be an equal choice). The tables are not named `vy_*` because Vy in company mode is the same Vy and may one day need result tables of its own.

## Amendment (2026-11-12, #3029): one live run per member per feature

**Owner decision, 2026-11-12**, in the Meetings PO chat: the question was "allow Vy to transcribe a meeting in parallel with the member's other Vy work?", and the owner's answer was "1" (yes).

**Problem** (#2863 item 7). Decision 1 allowed one live run per member (`ai_run_one_running_uq` on `(org_id, agent_id) WHERE status = 'running'`), and `kernel.member_vy.run.start` cancelled a member's running run (`RUN_SUPERSEDED`) before it started the next. A recorder who used Vy for anything else while a transcription ran (up to 4 hours) cancelled the transcription, and the meeting was left without a transcript. A guard in the summary start only covered that one feature.

**Decision.** A member may have one live run **per feature**. A new start supersedes only a running run of the same member **and the same feature**; a run of another feature is left alone. Everything else of this ADR stays as it is: the org-chart agents keep one running run per agent (ADR-0029 section 5), the budget and the kill switches count and stop every run, the expiry caps (30 minutes for a note, at most 4 hours for a meeting) and the 4-hour bound are per run, the audit-id binding is per run, and a removal, a loss of `vy.use` or a kill switch still ends every live run of the member, whatever its feature.

**How the database holds it.**

- `ai_run.feature` (text, the same key format as `member_vy_result.feature`): set for a `member_vy` run, NULL for an org-chart agent's run. The module cannot key the rule: `meetings.transcribe` and `meetings.summary` share the module `meetings`, and the two notes features share `notes`.
- Two partial unique indexes replace `ai_run_one_running_uq`: `ai_run_one_running_agent_uq` on `(org_id, agent_id) WHERE status = 'running' AND feature IS NULL` (the old rule, for the org-chart agents) and `ai_run_one_running_feature_uq` on `(org_id, agent_id, feature) WHERE status = 'running' AND feature IS NOT NULL`. The new ones are created before the old one is dropped, so no moment is left without a rule.
- `ai_run_member_vy_bind` now also refuses a `member_vy` run without a feature, an org-chart agent's run with one, and any change of a run's feature (the trigger fires `OF feature`); `member_vy_result_bind` refuses a result whose feature is not its run's. So no writer can blank or change the feature of a run to get around the rule. (Platform PO, 2026-11-12: both binds restated from their newest bodies, same signature, owner, grants and search path.)
- Two starts of one feature at the same moment: the unique index lets one insert through, and the other gets `VY_RUN_BUSY` (409, try again), never two running runs.

**No per-member concurrency cap.** The live runs of a member are bounded by the number of declared member-mode features (`MEMBER_VY_FEATURES`: four today), because each feature has at most one. The bound is the command's (`run.start` accepts only declared features); the database checks the shape of the key, not the list, so it is not a database guarantee. A new feature raises the bound by one and is a visible change in that list; a separate cap (Platform PO, 2026-11-12) would only duplicate it.

**Module level (meetings).** The kernel rule "the same feature supersedes" is meant for a crashed or abandoned run. The owner's intent is that a transcript is never lost to other Vy use, and losing it to a second recording is the same harm, so the meetings transcription start refuses (`TRANSCRIBE_OTHER_RUNNING`, 409) while a live, unexpired transcription of the same recorder exists for another meeting. A summary no longer supersedes anything; it still waits for the transcription of its own meeting (`TRANSCRIBE_RUNNING`), because a summary of a half-written transcript is wrong. A transcription whose job was lost keeps the recorder from starting another meeting's until it expires (at most 4 hours; the worker closes a run on a normal failure), and the recorder has no command to cancel it; both this and the narrow window in which two starts for two meetings pass the check together are follow-ups (#3033).

**Readers checked.** The background context entry (by run id), the cancel on removal, a loss of `vy.use` and a kill switch (`member_vy_runs_cancel`: by agent, member or module, every running run), the cancel on a meeting's delete (by the result's feature and subject), `kernel.member_vy.run.live` and `.latest` (already feature and subject scoped), the budget meter (it sums cost, never counts live runs) and the org-chart wake-up and daily cap (org-chart agents only). No member Vy run is swept for expiry: a lapsed run stays `running` until the next start of its feature or a cancel, as before.

**Two-step rule.** The invariant suite's raw seeds of a member's run changed first, in their own PR, so they pass before and after the migration; the new rules are pinned in `test/invariant/member-vy-run-feature.db.test.ts`.

## Revisit when

- A feature needs Vy in member mode to call commands on its own (an agentic Vy in member mode). It needs its own ADR: tools, per-command approval and a different taint rule.
- Memory is to be derived from private text, not only from the member's own entries.
- The owner asks for a per-member cap by default, or for break-glass access to a member's results (ADR-0037 option C), or the subject-audience sink of decision 8 is wanted.
- Teams exist, so a result may be shared with a team.
