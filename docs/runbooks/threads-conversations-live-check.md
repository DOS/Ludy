# Threads replies: live check

Settles, on one real Threads profile the owner controls, the Threads API facts that the reply adapter of the conversation core (issue [#3133](https://github.com/DOS/Ludy/issues/3133), [plan](../plan/conversations-channels.md) section 4.4, [ADR-0041](../adr/0041-conversation-core.md)) relies on. **No official page was read when the adapter was built** (the build session's network denied `developers.facebook.com`), so every field name and call shape below is tagged **[M]** (recalled, not seen) or **[U]** (not found) in the plan, and none is a rule of the software until a row here is filled with what the platform answered. Until then the adapter is built against recorded answers of those shapes and a wrong shape fails closed (a reply that cannot be read is dropped, a call the platform refuses is typed and shown), never open.

Markers: **[PERSON]** only a person can do it (the owner: the Meta app dashboard, the Threads profile, a second Threads account for test replies). **[AGENT]** a Ludy session can do it with the owner's go-ahead. Never paste a secret, a token, an app id or a customer's reply into chat, an issue or a commit: write what each step showed ("matched", "no match", the error code, the HTTP status).

## 0. What the owner sets up

**[PERSON]** in the Meta app dashboard (`developers.facebook.com`), on the app that has the **Threads** use case (the one `CHANNEL_THREADS_APP_ID` and `CHANNEL_THREADS_APP_SECRET` name; see [social-live-check.md](social-live-check.md)):

1. **Permissions.** Add `threads_read_replies` to the permissions the app asks for (it already has `threads_basic`, `threads_content_publish`, `threads_manage_replies` and `threads_manage_insights`). Ask whether Meta requires **App Review** for `threads_read_replies` and `threads_manage_replies` before profiles that are not testers of the app can opt in [U]; write the answer in row 1. If review is needed it is an owner action and costs Ludy no money.
2. **Webhooks (only if the Threads product pushes replies [S, U]).** Under **Webhooks**, pick the **Threads** object and set:
   - **Callback URL:** `<PUBLIC_URL>/api/channels/facebook/webhook`. This is the same URL as the Facebook and Instagram webhooks, on purpose: the route tells the product by which secret signed the body, so no second public route exists.
   - **Verify token:** the value of `CHANNEL_META_WEBHOOK_VERIFY_TOKEN` (8 to 200 characters). A deployment that has only the Threads app still sets it, and the route then exists.
   - Subscribe to the replies field of the Threads object (the field name is row 3).
   Delivery is optional: the reconcile read (row 6) is the safety net, so the check can run with no webhook at all, only slower.
3. **A second Threads account** to write test replies, and one **post** on the connected profile to reply under.
4. **The deployment's settings:** `CHANNEL_THREADS_APP_ID`, `CHANNEL_THREADS_APP_SECRET`; `CHANNEL_THREADS_HISTORY=true` (the default) for the reconcile read.

## 2. Steps

1. **Connect with the opt-in (rows 1, 2).** **[PERSON]** in Ludy, `Social > Channels`: tick **Đọc và trả lời các trả lời (reply) dưới bài Threads của bạn trong Hộp thư** next to Threads and connect (or press **Bật đọc và trả lời các trả lời dưới bài Threads** on a profile that is already connected). Grant the permissions. Confirm the profile now shows **Các trả lời dưới bài Threads của hồ sơ này được đưa vào Hộp thư**. **[AGENT]** reads the connection's scopes and confirms `threads_read_replies` is among them (row 2); if the dialog was accepted and the scope is missing, the probe of row 2 is wrong: say what the probe answered (status and code, no body).
2. **Inbound reply by webhook (rows 3, 4, 5).** **[PERSON]** with the second account, reply under a post of the connected profile. Within seconds the reply is in `Social > Inbox` and under the post's **Bình luận** tab, one thread, one unread mark. **[AGENT]** confirms from the worker log that a notice was parked and stored (counts only, no text) and, if the thread did not appear, whether the route answered 401 (row 4: wrong secret) or stored nothing (row 3: other field names).
3. **Reconcile (row 6).** **[PERSON]** stop the webhook subscription (or reply while it is off), reply again from the second account, then **[AGENT]** runs or waits for the hourly history sync of the connection and confirms the reply is stored once, in the thread of its top-level reply. A reply to a reply must land in its top-level reply's thread.
4. **Answer (rows 7, 9, 10, 11).** **[PERSON]** answer the thread from Hộp thư, press Send. Confirm it appears under the customer's reply on Threads, the message ends `sent`, the echo of it (webhook or reconcile) is not a second message, and a text of 501 characters is refused by Ludy before any call. **[AGENT]** reads the cap before and after (`threads_publishing_limit`) and writes the figures.
5. **Dy (AI part).** **[PERSON]** with the AI budget on, open a new reply thread: a draft appears for a person to read, edit and send (metered, `auto_draft` for the automatic ones), saved replies and `{tên}` work, an intent label is suggested. Nothing is sent until the person presses Send. With the AI off the thread still opens and can be answered.
6. **Hide (row 8).** **[PERSON]** only after steps 1 to 4 pass, and only on the owner's own test reply: with `canHide` temporarily true on a test deployment, press **Ẩn** on the second account's top-level reply and confirm on Threads; then **Hiện lại**. Report the answer; the change to `canHide` is made in code after the row is filled, never on a live deployment first.
7. **Outage (row 12).** **[PERSON]** stop the deployment for two minutes while the second account replies, start it again, and say whether the reply came by webhook retry or only by the reconcile read.

## 3. What is not built (and why)

- **Private messages on Threads:** no API was found [U]; Threads is a public-reply channel only.
- **Replies to a reply of someone else's post, mentions and quotes:** the adapter reads replies on the profile's own posts only.
- **Hide before row 8 is filled:** the adapter has the call, the rules do not offer it, and the button is not shown.
- **Data deletion callback of the Threads app:** a person's data deletion request for Threads is not matched by the callback of the Meta apps (it keys on the Pages and Instagram apps' secrets). Whether the Threads app needs its own callback is [U]; the erase, export and retention of the conversation core cover the rows by their tables whatever the channel.
- **Images in replies:** a reply with an image is stored as the placeholder line.
