# Runbook: outside calendars (Google Calendar)

A member connects a Google account from Settings, "Lịch ngoài". The busy times of its primary calendar (start and end only: never a title, never an attendee) block that member's booking slots, and the worker refreshes them every 15 minutes (#1374, #2123). This runbook is for any operator who brings their own Google OAuth app. Steps specific to one operator's cloud project, secret store or domain belong in that operator's private deployment layer, not here.

With no app configured the connect button is hidden and nothing else changes: `docker compose up` needs no external account.

## What you need

- A Google Cloud project with the **Google Calendar API** enabled.
- An **OAuth client of type "Web application"** in that project.
- An OAuth consent screen with the scopes `openid`, `email` and `https://www.googleapis.com/auth/calendar.freebusy`. The free/busy scope is a sensitive scope: Google verifies the app before more than 100 users outside the project's organization can connect (until then the project is "in testing" and each member must be listed as a test user; a test-mode grant also expires after 7 days).
- Optional, for write-back of bookings (a member's confirmed bookings become events in their Google calendar): also the scope `https://www.googleapis.com/auth/calendar.events.owned` on the consent screen (insert, change and delete events on calendars the account owns, which covers its primary calendar; the broader `calendar.events` would also reach every calendar shared with the account, so it is not used). Both written events are `private` and `opaque`, so people the member shares their calendar with see a busy block without the visitor's name. It is a sensitive scope too. Without it members can still connect for free/busy; the write-back switch then asks them to connect again once the scope is on the screen.
- The server's `PUBLIC_URL` is `https`, and `CREDENTIAL_KEY` is set (`credential-key.md`): without a key a token could never be sealed, and the connect is refused before the member leaves the app.

The client is its own: do not reuse the YouTube or Business Profile client (`CHANNEL_GOOGLE_*`), whose consent screen and scopes differ.

## Steps

Each step has a check and a rollback. Never write a secret, a project id or an internal host into an issue, a PR or a file of the repository: name where it comes from.

1. **Create the OAuth client.** Google Cloud console, APIs and services, Credentials, Create credentials, OAuth client ID, Web application. Add the authorized redirect URI `<APP_URL>/calendar/oauth/google_calendar/callback` (`APP_URL`, else `PUBLIC_URL`: the return address is a page of the app, [split-app-api.md](split-app-api.md)), exactly, with no trailing slash.
   - Check: the client shows the redirect URI; the Calendar API shows as enabled.
   - Rollback: delete the client.
2. **Set the consent screen scopes** to the three above (and the events-read scope of the section "Reading a member's own meetings" when that feature is on) and the app name and support address members will see.
   - Check: the consent screen lists `calendar.freebusy` and nothing broader.
   - Rollback: remove the scope.
3. **Give the server the client.** Set `CALENDAR_GOOGLE_CLIENT_ID` and `CALENDAR_GOOGLE_CLIENT_SECRET` on the API and the worker (both read them: the API starts the connect, the worker syncs), from the operator's secret store. Set both or neither: the server refuses to start with one. Restart both.
   - Check: in Settings, the working-hours card shows a "Kết nối Google Calendar" button.
   - Rollback: unset both variables and restart. The button hides, the worker stops syncing, existing connections and their busy blocks stay until the member disconnects or reconnects.
4. **Connect a test account.** As a member (not a viewer), press the button, accept the consent screen, and come back to Settings.
   - Check: the account is listed with "Chưa đồng bộ"; within 15 minutes it reads "Đồng bộ lần cuối ..." and an event in that calendar takes its slot off the member's booking page.
   - Rollback: "Ngắt kết nối" deletes the account's busy blocks and hides the account at once; within 15 minutes the worker revokes the grant at Google (https://oauth2.googleapis.com/revoke, with the refresh token), then drops the sealed token and the row. If Google cannot be reached for 3 days, or the token can no longer be opened (the member left, the key is gone), the connection is removed anyway and the audit row says `revoked: false` with the reason: remove the app's access on the Google account's security page in that case.

## Writing bookings to the member's calendar (write-back)

A member who turns on "Ghi lịch hẹn vào lịch này" under a connected Google calendar (it asks them to connect again when the grant lacks the events scope) gets each confirmed booking as an event in their primary calendar, titled with the event type and the visitor's name: the visitor's name is the only personal data that leaves for Google, into the member's own calendar; no email, phone or attendee. The worker writes it within seconds of the booking (a job the outbox relay queues from the booking's confirmed, moved or cancelled event, queue `kernel-calendar-writeback`; it never renews a token), and the 15 minute sweep repeats the same reconcile as the backstop (a lost job, a token about to run out, a refused token, which only the sweep renews or expires). It moves it when the booking moves and deletes it when the booking is cancelled; each call is idempotent by an event id the kernel derives, so a retry never makes a second event. An event the member deletes by hand stays deleted until its booking changes. Disconnecting a calendar cannot call Google for its events (the token goes), so events already written stay in the member's calendar. Check: turn it on for a test account, make a booking, and within seconds the event is there (at the latest at the next sweep, 15 minutes), on the account's primary calendar (this live round trip also confirms that the `calendar.events.owned` scope covers `primary`; if Google answers 403, the scope is not enough and the switch must not be offered); cancel the booking and it goes. Rollback: the member turns the switch off (writes stop at once, also in a sweep that is running). Removing the events scope from the consent screen does not revoke grants that already carry it; to stop write-back for everyone, a staff step sets `write_back = false` on the connections.

## Google Meet links (C7, #1375)

An event type whose location is "Google Meet, tạo riêng cho mỗi lịch hẹn" gets a Meet for each booking, made by the worker with the booking's event in the host's Google calendar (the write-back above, with the conference asked for in the same insert). **No new scope or OAuth step:** `calendar.events.owned`, already on the consent screen for write-back, covers it. The host picks the kind in Settings, which is offered only to a host who connected Google Calendar and turned write-back on. If Google cannot make a Meet (the account's Workspace edition, an outage, a revoked grant), the booking stands, the fixed link of the type is used when it has one, and the host's mail and the bookings list say so; a booking that has had no answer for 3 minutes is settled the same way, so no mail waits for ever. A booking confirmed while the host's token is about to run out makes the worker ask for a sweep at once (at most one a minute), which renews the token and writes the event with its Meet, instead of waiting up to 15 minutes. Check, once a live Google account is connected: make a booking of such a type and see the join link in the confirmation mail within a minute; if Google answers a link of the form `https://meet.google.com/lookup/<code>`, it is accepted as a Meet address. Nothing to run for this feature beyond the migration. To switch it off, change the event type's location.

## Reading a member's own meetings (Meetings B1, #3165)

A member who turns on "Cho Ludy đọc tên và giờ cuộc họp trong lịch" under a connected Google calendar sees today's meetings on the Meetings tab with "Ghi cuộc họp này", and after a recording is offered the one calendar event it overlaps ("Gắn vào sự kiện lịch này?"). The switch is off by default and nothing reads a title until it is on **and** the member has approved Google's new consent; there is no model in the path (code matches by time overlap and a person clicks every step).

**New scope, one constant.** `https://www.googleapis.com/auth/calendar.events.owned.readonly` ("See the events on Google calendars you own", the narrowest events read; it covers the member's primary calendar). It lives in one constant (`GOOGLE_CALENDAR_EVENTS_READ_SCOPE` in `packages/channel/src/calendar-google.ts`, mirrored in `packages/kernel-contract/src/calendar.ts`, a test pins that they are equal). The connect dialog asks for it only when the member starts the connect from this switch (`include_granted_scopes=false`, so each connect grants exactly the scopes asked that time; the app asks again for the write-back scope too when the connection already carries it).

**Production step (a person with the Google Cloud project runs it; no worker does):**

1. In the Google Cloud console, Google Auth platform, Data access, add the scope `https://www.googleapis.com/auth/calendar.events.owned.readonly`. Check: the consent screen lists it next to the three scopes above.
2. **Confirm the scope category on that screen.** Google classifies calendar scopes as sensitive (verification, no security assessment); this is the working assumption and it is not confirmed on Google's own scope page. When the scope is added, the console labels it "sensitive" or "restricted". If it says restricted, stop: that needs the annual security assessment (CASA) and is an owner decision, so do not publish the consent screen change; turn the switch's button off by leaving the scope off the screen and tell the coordinator.
3. While the app is in testing, a test user's authorization expires after 7 days (the refresh token included), so a tester sees "Quyền truy cập đã bị thu hồi hoặc hết hạn" and connects again, and an unverified app with sensitive scopes is capped at 100 users for its whole life (the cap cannot be reset). Verification removes both. Plan the verification submission before inviting more than a few members.
- Rollback: remove the scope from the consent screen. Grants that already carry it keep working until the member turns the switch off or disconnects; to stop the read for everyone, a staff step sets `read_events = false` on `crove_kernel.calendar_connection` (the next sweep then deletes nothing but writes nothing, and the cache is hidden at once; run the module's clear for the connection to delete the rows).

**What is read and stored.** The worker's 15 minute sweep, after the busy replace, asks Google for the primary calendar's events from 1 day back to 7 days ahead (single events, no deleted ones, at most 2 pages of 250, cut at 300) with a fields mask that names no attendee address, description or attachment: `nextPageToken,items(id,status,summary,start,end,hangoutLink,conferenceData(entryPoints(entryPointType,uri)),attendees(self,responseStatus,optional))`. Per event it keeps the title (cut at 200), start, end, time zone, a Meet, Zoom or Teams address (https only, from `conferenceData.entryPoints[]` with `hangoutLink` as the older fallback) and the number of invitees; all-day, cancelled and declined events are dropped. The cache is `crove_meetings.calendar_agenda`: only its member reads it (an owner, an admin, another member, an agent and the system context read nothing), one writer (`crove_meetings.agenda_replace`, worker login, system context, returns a count) and the rows go at once when the member switches the read off, disconnects, connects again without the scope, or the org is purged. A failing read never stops the busy sync; the log line carries an error name, never a title.

**Check, with a live test account:** connect it, turn the switch on (Google shows the new consent), wait for a sweep (15 minutes, or ask for one) and see today's meetings on the Meetings tab; a Meet event shows its badge; record one with "Ghi cuộc họp này" (the consent step runs as always) and open the meeting: the event shows as linked. Check the invitee count shows only a number: Google's partial response for `attendees(self,responseStatus,optional)` returns the attendee list with those fields, so the count is the length of that list; if the live answer has no `attendees` for a meeting with guests, the count reads 0 and the list still works. Turn the switch off: the list empties at once.

## The live check at booking time (free/busy drift)

The stored busy blocks are at most 15 minutes old. So that a time that became busy in a host's Google calendar a moment ago cannot be booked, the worker asks Google live about the exact slot (with the type's buffers) before it decides a visitor's booking request or a visitor's ask to move a booking, for each host who has a connected Google calendar (queue `crm-booking-live`, `apps/kernel/src/calendar-live.ts`). A busy answer is added to that connection's stored blocks and the decision then refuses the slot as taken, the same answer as for any busy time. Only the window of the slot goes out, and only busy intervals come back. The call is bounded (3 seconds, all hosts in parallel) and only ever helps: no connection, no Google app on the server, a token about to run out or refused, a slow or failing Google all leave the decision to the stored blocks, and the booking never waits longer. The check never renews a token (the sweep does). Because a public booking page can trigger it, it is budgeted in the kernel, shared by every worker: `kernel.calendar.live_take` allows at most 60 live calls per org and 12 per connection in any minute (it counts its own audit rows of the last minute under a lock per org), and a call over the budget is simply not made (the stored blocks decide, the booking is never refused for it). Check: connect a test account, create an event in it at a time the booking page still offers (inside the last 15 minutes' window, so the sweep has not read it), request that time on the booking page: the booking is refused as taken. Turning it off: removing the Google app credentials from the server stops the live call (the worker then decides on the stored blocks). Rolling the code back to a release without the `crm-booking-live` queue: let the forward release drain it first, or move the waiting jobs to `crm-booking` (a staff step on the `crove_jobs` queue tables: rename the jobs of `crm-booking-live` in state created or retry to `crm-booking`), otherwise those bookings stay pending and their page keeps polling.
## When something goes wrong

- **Closing an organization.** An organization being offboarded is not swept: its calendar connections, sealed tokens and addresses stay until the org purge deletes them, and their grants are never revoked (a disconnect made once `kernel.org.offboard` has run is marked but not finished, and only owners can enter an offboarding org). Before running the offboard, have every member disconnect their calendar and wait 15 minutes for the sweep: the audit rows of `kernel.calendar.finish_disconnect` confirm each one. Reopening the org (a staff step) lets the sweep take its connections up again.

- **The button is missing.** Both `CALENDAR_GOOGLE_*` variables are set on the API, `CREDENTIAL_KEY` is set, and the user is not a viewer.
- **"Quyền truy cập đã bị thu hồi hoặc hết hạn".** Google refused the grant (the member revoked the app, or a test-mode grant ran 7 days). The sealed token is dropped; the member connects again. The busy blocks stay until then, so time that may still be busy is not offered.
- **"Lần đồng bộ gần nhất gặp lỗi".** A passing failure (a quota, an outage); the next sweep retries. The log line is `[calendar-sync] connection <id prefix>` with an error name, never a token.
- **Rotating `CREDENTIAL_KEY`.** Calendar tokens are sealed like channel tokens. Keep `CREDENTIAL_KEY_PREVIOUS` until members have reconnected: a calendar token the server can no longer open expires the connection (`credential_unreadable`) and the member connects again. The key reseal sweep and the key counts of `credential-key.md` do not cover calendar tokens yet (tracked as a follow-up): a connection renews its own envelope under the current key at its next token refresh, but the dormant one of a member who left stays under the old key, so do not retire `CREDENTIAL_KEY_PREVIOUS` on the strength of those counts alone.
- **Rotating the client secret.** Create a second secret in the Google console, set it on the API and the worker, restart, then delete the old one. Existing connections keep working: they hold refresh tokens, not the secret.
