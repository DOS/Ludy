# Runbook: the MISA AMIS sandbox check, before the push is turned on

Why this exists: the push of vouchers to MISA AMIS Kế toán ([#3902](https://github.com/DOS/Ludy/issues/3902), S3b of [#3854](https://github.com/DOS/Ludy/issues/3854)) was built and tested only against a fake MISA server written from MISA's documentation. Nothing in it has run against a real MISA sandbox. Until this check has confirmed or corrected what the push assumes, **no deployment turns the push on** and no org's vouchers go to MISA.

This file is for AMIS Kế toán. MISA ASP has [its own check](misa-asp-sandbox-check.md): the two share an adapter, not a document.

Who runs it: only the coordinator, with the integrator's ClientID and a test access code handed over by the secret procedure ([production, secret and credential steps](../contributing.md#production-secret-and-credential-steps)). No worker or team lead runs it, and nothing in this file asks the owner to run a command: the owner's part is the handover of the ClientID and a sandbox company in AMIS, and the coordinator does the rest.

## The three gates, all closed by default

| Gate | What it is | Closed means |
|---|---|---|
| Deployment | `MISA_AMIS_PUSH` is `on` (and `MISA_AMIS_CLIENT_ID` is set) | The worker does not register the push queue and does not queue the push job. The confirm route answers 404 `MISA_AMIS_PUSH_DISABLED` and the confirm button is not drawn when this is off (the list of pushed rows and the settle buttons stay, they send nothing). |
| Connection | The connection's last test is `works` (S2b, [#3885](https://github.com/DOS/Ludy/issues/3885)) | `finance.misa_amis.push` answers `MISA_AMIS_NOT_TESTED`. |
| This check | The list below is done and written in the issue | Nobody sets `MISA_AMIS_PUSH`. |

A person (owner or admin) still approves every push, bound to the digest of what they saw (`MISA_AMIS_PUSH_STALE` if the data changed), and nothing is sent for a voucher with a blocker.

## What to confirm, in order

Every item is **unconfirmed** today. For each, the result is written on #3902 (what was sent, what MISA answered, in plain words, with no secret) and, where Ludy's assumption was wrong, a follow-up issue is opened before the gate opens.

1. **The connection test.** `get_company_info` returns the shape the test job reads (it only needs a non-empty object). The token call works with the access code and the connection's `org_company_code`. ([misa-amis-api.md](../integrations/misa-amis-api.md): "Unconfirmed in MISA's documentation".)
2. **The base path and the token.** `https://developer.misa.vn/apis` plus `/amiskt/v1/...`; the token's real life (the text says 24 hours, the field says 12); whether a rate limit shows up at a batch of 50.
3. **The AMIS branch.** `get_dictionary` with `data_type` 6 (organisation units): which field carries the id that goes in `branch_id` (the worker reads `organization_unit_id`, then `branch_id`, then `id`, and takes only a single well-formed id; with none or several the batch is `failed` with `BRANCH_UNKNOWN`). If a customer has several branches, decide how a person chooses one (a follow-up: today the push refuses rather than guesses).
4. **The shape of a save's answer, and of the results.** `save` answers `Success` with no data; `get_call_back_detail_error` returns the entries of a callback's `data` (assumed), for a date range (the worker asks from one day before the first row was sent to tomorrow, since the time zone is not documented). Check a refused voucher's `error_message` and `error_code`.
5. **Amounts.** Numbers (as the adapter sends them) are accepted; a string would not be needed.
6. **Ludy's three own choices** ([#3902 comment](https://github.com/DOS/Ludy/issues/3902#issuecomment-6994702640)): the purchase purpose defaults to 1; a bank payment is `reftype` 1510 (ủy nhiệm chi); the `reason_type_id` of a cash or bank voucher is derived from its accounts (331 a supplier, 131 a customer).
7. **Unpaid purchases and parties.** A purchase with `reftype` 330 and no `is_paid` is read as unpaid; AMIS accepts a party by name and tax code when no `account_object_code` is given (the push sends no party code).
8. **Sales and discounts.** A sales line without `stock_code` and `stock_name` (the table marks them required); a trade discount as a negative line rather than in `discount_*`. Sales stay out of the first org's push until this is answered.
9. **What a second `save` does under one `org_refid`.** The push never sends one: a row that is queued, sending, sent, accepted or `ambiguous` is not sent again by anything. If AMIS answers "idempotent" (the document implies it), a later change may let a person resend an `ambiguous` row; if it makes a second request, the rule stays as it is. Also: whether a voucher revised after AMIS took it must be deleted and sent again (the push counts it as `revised` and does nothing).
10. **That AMIS creates a request and not the voucher.** The PO's approval of R2 (not R3) for the push rests on AMIS turning a "đề nghị sinh chứng từ" into a voucher only when a person in AMIS does it. If AMIS creates the voucher directly, the decision is reopened before the gate opens.
11. **The 20 character voucher number.** MISA's limit on `org_refno` as the document says; the push blocks a longer number, including after the `/N` of a split voucher, and never cuts one.
12. **A refused `save`.** When MISA answers `Success: false` with an error code to a whole batch, the push takes it as "nothing was created" and marks every row `refused` (with the text Ludy has for that code). Check that a refusal never leaves some vouchers of the batch created.
13. **A refused row sent again.** A person's new confirmed push sends a `refused` row again under the same `org_refid`; check that MISA takes it (a corrected voucher) and does not answer that the id exists.
14. **Results.** `get_call_back_detail_error` returns one entry per `org_refid` (if it returns several, the worker keeps the last), and an entry's `success` is final. Also check how its date range is filtered (by the day of the request, which the worker assumes, asking from one day before the first send day to tomorrow) and that a range of several days is accepted: a row a person confirmed "in AMIS" days later is read from its original send day.
15. **A result of an older send.** The worker matches a result to a row by `org_refid` alone. After a refused row is sent again (the same `org_refid`, one more attempt), check that `get_call_back_detail_error` does not still return the old refusal for it, and whether a result carries something (a session id) that names the send it belongs to; if it does, the worker is to match on it too, before any refused row is sent again for real.
16. **The callback** (S4, [#3903](https://github.com/DOS/Ludy/issues/3903)) is a separate check once that slice exists: `app_id` against the ClientID, the signature, the reply AMIS expects. Built in #3903: `POST /api/webhooks/misa-amis` (set `MISA_AMIS_CLIENT_ID`; the address MISA is told is the deployment's public base URL plus that path). Check: that `app_id` is the ClientID and the signature is the hex HMAC-SHA256 of `data` with it (a test message from the sandbox), what MISA does with the answer `200 {"ok":true}` (accepted, or retried), whether it retries a `429` or `503`, and that a result moves a row from `sent` to `accepted` or `refused` within seconds. Also confirm whether MISA's callback body carries the ClientID as `app_id` (the reader requires `app_id` to equal the ClientID, and the ClientID is also the HMAC key): if it does, a good signature proves only that the sender has seen MISA traffic, so keep the ClientID a secret in config and logs, and keep the edge from logging callback bodies; what still limits a forgery is that the organisation comes from our stored row, the company code must match, moves are forward only, and a refusal counts for attempt 1 only. The route only stores the signed results; the worker relay records them, so a result shows within one relay tick. A result for a row still `sending` or `queued` waits and is taken again after five minutes (MISA can call back before the worker records `sent`). The route's per-address limit is the bank feed notice limiter (120 a minute): MISA's callbacks come from a few source addresses, so on a deployment with many organisations check that a burst is not answered 429 (and whether MISA retries it); polling carries a result that is lost.
17. **The catalogue check** (S3a, [#4112](https://github.com/DOS/Ludy/issues/4112)). Press "Kiểm tra với danh mục" on a preview of a sandbox company that has a few parties and items, and confirm: `get_dictionary` takes `take` 1000 and pages with `skip` (the worker reads at most 20 pages of a kind, and a longer catalogue fails the check as `catalogue_too_large`); a party row carries `account_object_code`, `account_object_id`, `company_tax_code` and `inactive` as the document says (a party is matched by the digits of `company_tax_code` alone, and only while active); an item row carries `inventory_item_code`, `inventory_item_id` and `inactive`; the catalogue the sandbox returns for `data_type` 1 and 2 is the whole company's, not a page of it. Check that a party whose tax code is in the sandbox is `matched` with the right code, that two active entries with one tax code read as ambiguous, and that the voucher then carries `account_object_code`. Write the result on #4112. Nothing of the catalogue (a name, an address, or any field but a matched entry's `catalogue_code` and `catalogue_id`) is stored or logged, with one exception: since S3b part 2 (item 19) a name proposal row (`kind = 'party_name'`, `state = 'name_proposal'`) also keeps the proposed entry's name in `candidate_name`, and no other row does. Look for no catalogue name in any other row of `misa_amis_match`, nor in the audit rows and the worker log. A party row's `match_key` is the voucher party's own tax code; that value is expected.
18. **The re-read before sending** (S3b part 1, [#4124](https://github.com/DOS/Ludy/issues/4124)). With the push switched on in a sandbox: check a batch, confirm within 15 minutes and see the rows go out; then check, deactivate (or delete) a matched party in the sandbox company, confirm and see the batch `failed` with `MATCH_STALE` and nothing created in AMIS; confirm 16 minutes after a check and see `MISA_AMIS_CHECK_REQUIRED`. Also record how long the catalogue read takes with a few thousand entries (the re-read is at most one per five minutes in a run), and whether `get_dictionary` can be asked for one entry by code (it would replace the page reads).
19. **Name proposals** (S3b part 2, [#4124](https://github.com/DOS/Ludy/issues/4124)). In a sandbox company that has a customer or supplier with no tax code in Ludy and an entry of the same name in AMIS: check, see the proposal card with the entry's name and code, confirm it and see the voucher written with that code and the digest change; check again and see the confirmation kept; deactivate the entry in AMIS, check again and see the confirmation gone and the party blocked. Also see what AMIS does with two entries of one name (the proposal must be ambiguous, none shown) and which field carries the name (`account_object_name` is assumed).

## Turning the push on, and off

Only after the list above is done and written on #3902, and only for the deployment the coordinator names: the coordinator sets `MISA_AMIS_PUSH=on` the way any deployment setting is changed, under the owner's approval for that run. Turning it off is the same setting set to empty or `off`: the worker does not register the push job at its next start, so **both sending and reading MISA's results stop** (they are one job; there is no separate gate). Rows already `sending`, `sent` or `ambiguous` stay as they are, nothing is asked of MISA and nothing is sent again. When the setting is turned back on, the first run of the job (a follow-up already waiting in the queue, or any press of the push button) turns a `sending` row older than five minutes into `ambiguous` and asks MISA for the results of `sent` and `ambiguous` rows changed in the last 24 hours; an `ambiguous` row older than that is settled by an owner or admin after three days (`push_resolve`). Nothing already accepted by AMIS is undone from Ludy.

**A `sent` row MISA never answered for:** the worker asks MISA for the result of a `sent` or `ambiguous` row only for 24 hours after the row's last change. After that an owner or admin settles a `sent` row by looking in AMIS (`finance.misa_amis.push_resolve`, migration `20270121100000`): "it is in AMIS" makes it `accepted`, "it is not in AMIS" makes it `failed` (sent again only through a new confirmed push). An `ambiguous` row is settled the same way after three days ("in AMIS" makes it `sent`, and its result is read). The connection card shows both buttons to owners and admins once the row is old enough (24 hours for `sent`, three days for `ambiguous`, by the row's last change; the server checks the age again with the database clock), each after a second click.

If a push goes wrong in the sandbox: nothing is deleted from Ludy; a voucher MISA refused shows on its row with MISA's reason, and a person sends it again through a new confirmed push (one more attempt). Rows in AMIS that must go are removed in AMIS by a person.

## What the push does not log or store

No access code, token, ClientID, party name or amount is in a row, an audit fact, an event, a ledger row or a log line: ids, codes, dates, counts and states. The one piece of MISA's own text kept is the capped `reason` of a refused voucher, shown escaped and never logged.
