# Runbook: the MISA ASP sandbox check, before the push to ASP is turned on

Why this exists: the MISA ASP connector ([#4103](https://github.com/DOS/Ludy/issues/4103)) was built and tested only against a fake MISA server written from MISA's ASP document (V1.0.0, dated 2026-08-05, read 2026-11-19). Nothing in it has run against a real ASP sandbox. What exists today is the client (S1, [#4110](https://github.com/DOS/Ludy/issues/4110)) and the connection and its test (S2, [#4111](https://github.com/DOS/Ludy/issues/4111)); the push, the catalogue matching and Ly's notes come with S3 to S5. **Nothing is pushed to ASP today.** The push to ASP is switched on only after this check, as for AMIS ([the AMIS runbook](misa-amis-sandbox-check.md)), and the AMIS check does not cover ASP: the two products share an adapter, a host and a token call, not a document.

Who runs it: only the coordinator, with the integrator's ClientID for ASP and a test access code handed over by the secret procedure ([production, secret and credential steps](../contributing.md#production-secret-and-credential-steps); the handover itself is [#3792](https://github.com/DOS/Ludy/issues/3792), an owner step). No worker or team lead runs it, and nothing in this file asks the owner to run a command: the owner's part is the handover and the approval of the run, in the coordinator's chat.

## The gates, all closed by default

| Gate | What it is | Closed means |
|---|---|---|
| Deployment, product | `MISA_ASP_CLIENT_ID` is set (S2, [#4111](https://github.com/DOS/Ludy/issues/4111)) | The connect dialog does not offer ASP, `misaAmis.connections.connect` and `.test` answer `MISA_AMIS_DISABLED` for an ASP connection, and the worker leaves an ASP connection's test alone (`product_off`). |
| Deployment, push | `MISA_ASP_PUSH` is `on` (S4, [#4113](https://github.com/DOS/Ludy/issues/4113); it also needs `MISA_ASP_CLIENT_ID`): its own switch, apart from `MISA_AMIS_PUSH` | The confirm route answers 404 `MISA_AMIS_PUSH_DISABLED` for an ASP connection, the confirm button is not drawn, and the worker hands the push job no ASP client (the connection is `skipped` as `product_off`, its queued rows stay queued). |
| Connection | The connection's last test is `works` | The push command answers `MISA_AMIS_NOT_TESTED`. |
| This check | The list below is done and written in the issue | Nobody sets `MISA_ASP_PUSH`. An ASP confirmation is held to a catalogue check of the same batch made in the last 15 minutes (`MISA_AMIS_CHECK_REQUIRED`), and the ASP check ([#4152](https://github.com/DOS/Ludy/issues/4152)) works with the push switch off, so item 15 is done first. |

A person (owner or admin) still approves every push, bound to the digest of what they saw, and nothing is sent for a voucher with a blocker. A legal entity is on AMIS or on ASP, never both (one connection per entity), and the access code of an ASP connection is sealed under its own provider id `accounting_misa_asp`.

## What to confirm, in order

Every item is **unconfirmed** today. For each, the result is written on [#4103](https://github.com/DOS/Ludy/issues/4103) (what was sent, what MISA answered, in plain words, with no secret) and, where Ludy's assumption was wrong, a follow-up issue is opened before the gate opens.

1. **The connection test.** `POST /asp/v1/token` with the access code and the connection's `org_company_code` returns a token, and `get_dictionary` with `data_type` 6, `skip` 0, `take` 1 answers (an array, empty or not). A wrong access code, a code of data not connected to the app, and the deployment's own unknown ClientID each show as the answer the test job reads (`wrong_credentials` for the first two kinds MISA names as a refusal of the credentials, `unreachable` for `InvalidAPPID`); write the real error codes down.
2. **The ClientID.** Whether the ClientID MISA issued for AMIS also works on `/asp/v1` or ASP needs its own approved app (the deployment holds one value per product, so either works; the plan counts approved apps per product).
3. **The token.** The real life (the ASP document says 12 hours), the format and time zone of `expired_time` (the client trusts a token for half an hour at most and renews it once), and whether a rate limit shows up at a catalogue page of 1000 or a batch of 50 vouchers.
4. **The organization unit (the branch).** Which field of a `data_type` 6 row carries the id that goes in `branch_id` (the AMIS adapter reads `organization_unit_id`, then `branch_id`, then `id`, and takes only a single well-formed id).
5. **The read-only catalogues.** Types 1 to 6 only (parties, items, stock, unit, accounts, organization unit): the field names of a row (`account_object_code`, `account_object_name`, `company_tax_code`, `is_vendor`, `is_customer`, `inactive`, `inventory_item_code`, and so on) as S3's matching will read them, the page size, `skip` and `take`, and `last_sync_time`. Types 8, 9 and 14 (AMIS only): the client answers `unsupported` before any request; check no request for them leaves.
6. **The calls ASP does not have.** `get_company_info`, `save_dictionary` and `get_call_back_detail_error` (the polling of results): the client answers `unsupported` before it asks for a token. Check in the egress log of the sandbox run that none of them was requested, and that ASP really has no such endpoint (the document's token text lists `save_dictionary`, which has no endpoint; the document has no counterpart of AMIS's `get_list_acc_obj_debt` either, which Ludy does not call).
7. **The voucher structures.** The pinned lists in [asp-voucher-fields.json](../../modules/finance/test/fixtures/asp-voucher-fields.json) (names only) against what ASP accepts: the keys Ludy writes that ASP's document does not list (the party's `account_object_tax_code`, `_name` and `_address` flat keys on some kinds, and `exchange_rate_operator`): does ASP ignore them or refuse the voucher? Any key it refuses is dropped for ASP and the golden test follows.
8. **The shape of a save's answer.** `save` answers `Success` with no data (assumed); amounts as JSON numbers are accepted; a refused `save` (`Success: false` with an error code) is taken as "nothing was created" for the whole batch. Check a refusal never leaves some vouchers of the batch created.
9. **Ludy's own choices, against ASP.** The purchase purpose defaults to 1; a bank payment is `reftype` 1510; the `reason_type_id` of a cash or bank voucher is derived from its accounts (331 a supplier, 131 a customer). The `reftype` and `reason_type_id` tables were derived for AMIS and are unconfirmed there too: ASP may differ.
10. **A second `save` under one `org_refid`.** The push never sends one while a row is queued, sending, sent, accepted or ambiguous. If ASP answers "idempotent", a later change may let a person resend; if it makes a second request, the rule stays.
11. **That ASP creates a request and not the voucher.** The R2 (not R3) approval for the push rests on the product turning a "đề nghị sinh chứng từ" into a voucher only when a person does it. If ASP creates the voucher directly, the decision is reopened before the gate opens.
12. **The 20 character voucher number.** MISA's limit on `org_refno` as the document says; the push blocks a longer number and never cuts one.
13. **The callback (the one real gap in ASP's document).** The document says only that a save's result comes back "through the callback": no envelope, no signature (the words signature and HMAC do not occur), no registration, no polling fallback. Check: does ASP call the AMIS callback address (`POST /api/webhooks/misa-amis`, built in [#3903](https://github.com/DOS/Ludy/issues/3903)); with which envelope and signature; how the address is registered for ASP; what `app_id` carries and which of the two ClientIDs it equals; and the reply ASP expects. S4 assumes the AMIS envelope and verifies the signature against each configured ClientID. If the sandbox shows a different shape, S4's callback part is redone before the switch is turned on. Without polling, a `sent` row ends only by the callback or by a person's resolve (`finance.misa_amis.push_resolve`).
14. **A refused row sent again, and a result of an older send.** A person's new confirmed push sends a `refused` row again under the same `org_refid`: ASP takes it (a corrected voucher) and does not answer that the id exists, and a result does not carry the old refusal.
15. **The firm's catalogue and S3's matching** (design on [#4112](https://github.com/DOS/Ludy/issues/4112); S3a and S3b). On the sandbox's real catalogue: tax codes as stored (digits only, with dashes, with a branch suffix), the `inactive` flag, two active entries with one tax code or one name (`party_code_ambiguous`), a party whose tax code differs from Ludy's (`party_tax_code_differs`), and that nothing is created in the catalogue. The catalogue is read by the worker's check job (a person presses "check" on the ASP connection, whatever `MISA_ASP_PUSH` says; the job uses the ASP client and opens only an ASP-sealed code; the access code is opened by the worker only), held in memory only, and only match results are stored; a name-only candidate is stored (its code and a capped name) on a proposal row alone, until a person confirms or rejects it. The push reads again the catalogue entries it needs right before sending and refuses a stale match (`MATCH_STALE`, nothing sent). Check that no catalogue row, and no candidate name, appears in a log, an error, an audit row, an event or a model prompt. Units and warehouses (`unit_id`, `main_unit_id`, `stock_id`, which ASP marks required on lines) are a later slice: the ASP push cannot go live without them, so check how ASP answers a line without them.

## Turning the push on, and off

Only after the list above is done and written on [#4103](https://github.com/DOS/Ludy/issues/4103), and only for the deployment the coordinator names: the coordinator sets `MISA_ASP_PUSH=on` the way any deployment setting is changed, under the owner's approval for that run. Turning it off is the same setting set to empty or `off`: the worker does not register the ASP push job, rows already `sent` stay and end by callback or by a person's resolve, and nothing is deleted.

If a push goes wrong in the sandbox: nothing is deleted from Ludy; a voucher MISA refused shows on its row with MISA's reason, and a person sends it again through a new confirmed push (one more attempt). Rows in ASP that must go are removed in ASP by a person.

## What the connector does not log or store

No access code, token, ClientID, catalogue row, party name or amount is in a row, an audit fact, an event, a ledger row or a log line: ids, codes, dates, counts and states. The one piece of MISA's own text kept is the capped `reason` of a refused voucher, shown escaped and never logged. The ClientID of ASP is a secret of the deployment like the AMIS one (the pilot check treats `MISA_ASP_CLIENT_ID` as a secret).
