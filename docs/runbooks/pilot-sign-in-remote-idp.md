# Runbook: sign the pilot in at a remote Supabase identity provider (issue #2704)

Moves the pilot (`app.ludy.vn`, `api.ludy.vn`) from its own bundled Supabase Auth to a remote Supabase Auth project, the identity provider of ADR-0027, so the owner can sign in with his account there. The provider is a Supabase Auth project (ADR-0027, ADR-0028), so Ludy needs no provider-specific code: the kernel verifies its ES256 or RS256 tokens against its published keys (`AUTH_SESSION_CHECK=jwt`) and the app signs in at its Auth URL. What the repository supplies is generic: the settings of [Your own identity provider](../self-host/README.md#your-own-identity-provider) and `AUTH_ALLOWED_EMAILS`. What follows is the pilot's own configuration, with every provider value an input from the provider's owner ("the provider" below). The provider's own values and registrations live in the operator's private deployment layer, never in this repository.

**Owner decisions of 2026-11-24 (JOY, in the Platform PO's chat): "Cloud chỉ DOS ID, chờ id.dos.me" and "Dùng OAuth App, sửa ADR".** The pilot signs in only through the identity provider (DOS ID) by redirect to its own sign-in page, through an OAuth App the provider registers for Ludy (a standard Supabase Auth OAuth 2.1 App, public client, PKCE), as the provider's other products do with Apps of their own: input 14 below, `AUTH_SIGN_IN=oauth` in step 5, issue #4704 and the [ADR-0028 amendment](../adr/0028-identity-sessions-and-revocation.md). The open-source build keeps its own form. The pilot keeps its current sign-in until the provider has registered the App (DOS/DOS.Me#1967). The custom [hosted-login contract](../contracts/hosted-login.md) is no longer the Cloud path (input 15).

**This is a Production, secret and credential step** ([contributing.md](../contributing.md#production-secret-and-credential-steps)). It is run by the Platform PO, one step list per approval from the owner in the PO's chat, stopping at the first failure. A session that writes code never runs it. No value below is in this repository: each says where it comes from.

## Step 0. Human-only inputs (owner and the provider's operator)

Nothing is started until each is answered. Only a person with access to the provider or the pilot's consoles can get them.

| # | Input | Who | Where it comes from |
|---|---|---|---|
| 1 | How the owner signs in at the provider: email and password, or a social provider (Google and the like) | owner | his account at the provider. The pilot's sign-in screen, with `AUTH_SIGN_IN=oauth`, shows only "Continue with <AUTH_OAUTH_NAME>" and the owner signs in on the provider's own page (input 14); without it the screen offers email and password and a button for each provider listed in `AUTH_OAUTH_PROVIDERS` (input 13). A social-only account uses its button; otherwise the owner can set a password at the provider |
| 2 | Who else signs in to the pilot today, and with what addresses | owner | the pilot's members list (Settings, Members) of each org |
| 3 | Which org holds data to keep, and which address owns it (or: nothing to keep) | owner | Settings, Members |
| 4 | The provider's Supabase Auth URL (ends `/auth/v1`), publishable (anon) key, token issuer (`iss`) and JWKS address | the provider's operator | the provider's project settings. The issuer is the `iss` of a real access token; the JWKS is normally `<issuer>/.well-known/jwks.json`. Both addresses and the publishable key are public values; **no service-role key, JWT secret or database password is ever needed or to be sent** |
| 5 | The provider signs its tokens with an asymmetric key (ES256 or RS256) and publishes the JWKS | the provider's operator | its JWT signing keys setting. A project that signs with a shared HS256 secret cannot be used: Ludy would need that secret, and it is never shared |
| 6 | The provider requires email confirmation for its accounts | the provider's operator | its Auth settings. Ludy identifies members by the token's `email` |
| 7 | The provider lets the owner enrol a second factor (TOTP) | the provider's operator, owner | approvals, posting and member changes (R3) need a second factor from the last 5 minutes (`AUTH_STEP_UP=required`, which the kernel enforces on a public URL). Without MFA at the provider those actions are refused with `STEP_UP_REQUIRED` |
| 8 | Registration at the provider: the pilot app's address `https://app.ludy.vn` and its sign-in return paths in the project's allowed redirect URLs (`https://app.ludy.vn/` and `https://app.ludy.vn/reset-password` for the form and provider buttons; with `AUTH_SIGN_IN=oauth` the only return is the OAuth App's registered redirect URI of input 14, and no recovery link is sent) | the provider's operator | its Auth, URL configuration. Without it, password-recovery and confirmation links land on the provider's own default page. The app signs in with a password or a provider button; Ludy holds no OAuth client or secret |
| 9 | The owner's email address(es) at the provider to allow, as `AUTH_ALLOWED_EMAILS` | owner | the address his account at the provider signs in with |
| 10 | Access to set the API's environment and restart it, and to the static host's Production environment (Vercel project of the app) | Platform PO | the pilot's own secret store and console |
| 11 | The owner's user id at the provider (`sub`, a UUID), only when an existing org's data is kept (step 4) | the provider's operator | the account in the provider's admin |
| 12 | A real access token of the owner's account at the provider, decoded (its payload is not secret; never paste the token itself into a ticket): `iss` equals input 4's issuer, the header `alg` is ES256 or RS256, `session_id` is present, and `user_metadata.email_verified` is `true` or absent (an explicit `false` is refused by `AUTH_ALLOWED_EMAILS`, the same 403 as an unlisted address, and after step 5 every old sign-in is already gone) | owner with the provider's operator | the browser's storage after signing in at the provider, or the provider's operator |
| 13 | Only for sign-in buttons (not with `AUTH_SIGN_IN=oauth`, which refuses them): the provider ids the provider's project has enabled for the pilot (for example `google`), and that those providers accept the return address `https://app.ludy.vn/` | the provider's operator | its Auth, Providers and URL configuration. The app starts the standard Supabase sign-in with PKCE at input 4's Auth URL; Ludy holds no provider credential. Every listed provider must issue verified emails: the allow-list is only as strong as that |
| 14 | The OAuth App for the pilot: the provider registers, in its Supabase Auth project's OAuth 2.1 server (its authorization path pointing at the provider's own sign-in and consent page), a **public** client (no secret) for Ludy with the **exact** redirect URI `https://app.ludy.vn/oauth-login/callback` (no wildcard, no other URI), the scopes `openid email profile` and the grant types `authorization_code` and `refresh_token`, and gives the **client id** (a UUID, a public value; never a client secret). The provider's operator also checks that its other OAuth Apps (for example DOS.AI and DOSafe) keep their own client ids: Ludy refuses their tokens | the provider's operator (DOS ID, id.dos.me) | its Auth, OAuth Apps. If the provider's own settings let anyone sign up, the app's "create account" tab creates provider accounts. They cannot use the pilot (not on the list), but tell the provider's operator the tab exists.

## Step 1. Record what rolls back and inspect the env file

**By the deploy** (steps 1 and 5 without a shell on the host, [deploy.md](deploy.md#identity-provider-settings-in-the-deploy-2704)): the Platform PO defines the settings of step 5 in the `pilot` GitHub environment, after the owner approves this step list, and runs the deploy. The deploy makes the dated, mode 600 copy of the env file itself (next to it, `.env.bak-<time>-<random>`; it is the rollback record, and the deploy puts it back on a failed boot or smoke test) and replaces every assignment of the step 5 lines, so a stale value of the second paragraph below cannot survive. The one thing still to do by hand is to note the app's current Production deployment on the static host (its rollback target); the deploy does not touch it.

**By hand:** on the API host, copy the current `.env` to a private, dated file next to it (mode 600, never into the repository), and write down the current values of these lines: `AUTH_ISSUER`, `AUTH_SESSION_CHECK`, `AUTH_UPSTREAM_URL`, `AUTH_SIGNUP_POLICY` (the pilot runs `invite_only`), `AUTH_SIGNUP_ALLOWED_DOMAINS`, `PUBLIC_AUTH_URL`, `PUBLIC_AUTH_ANON_KEY`, `PROBER_AUTH_URL`. Also note the app's current Production deployment on the static host (its rollback target).

Then read the same `.env` for lines the release of step 2 would start honouring: before it, the API and the worker ignored `AUTH_ISSUER`, `AUTH_SESSION_CHECK`, `AUTH_JWKS_URL`, `PUBLIC_AUTH_URL` and `PUBLIC_AUTH_ANON_KEY` from the file (compose fixed them to the bundled Supabase Auth; the prober already read `PUBLIC_AUTH_ANON_KEY`). A stale value there would break the pilot at the deploy, not at step 5. Remove any that is not the intended bundled value, or note it and set it back with the deploy.

## Step 2. The release

The API's compose file must carry the identity-provider settings: a release that includes this runbook's change (`docker-compose.yml` passes `AUTH_ISSUER`, `AUTH_SESSION_CHECK`, `AUTH_JWKS_URL`, `PUBLIC_AUTH_URL`, `PUBLIC_AUTH_ANON_KEY`, `AUTH_ALLOWED_EMAILS`, `AUTH_OAUTH_PROVIDERS`, `AUTH_HOSTED_LOGIN_*`, `AUTH_OAUTH_CLIENT_ID`, `AUTH_SIGN_IN`, `AUTH_OAUTH_NAME` and honours an empty `AUTH_UPSTREAM_URL`; the OAuth settings need the release of #4704 or later, whose migration `20270323020000` the deploy applies). Check the running release is at or after it (`GET /version` build against the PR's merge commit); if not, deploy one first through the normal release ([deploy.md](deploy.md)). Everything after this step is settings only.

## Step 3. The app's build (harmless first)

On the static host's Production environment ([split-app-api.md](split-app-api.md)) set `VITE_AUTH_URL` to the provider's Auth URL (input 4), so the app's Content-Security-Policy lets the browser reach it; the OAuth App's authorize and token endpoints are under that same Auth URL, so nothing more is needed for input 14 (only the older hosted login, input 15, needs `VITE_HOSTED_LOGIN_ORIGIN`). Then rebuild the Production deployment (a redeploy of the current one; the variable is baked into the bundle). It changes nothing yet: the API still names the bundled Auth. Skipping this step makes the sign-in request fail in the browser ("Failed to fetch") after step 5.

## Step 4. Join the owner to the existing org (before the API switches, so no one can sign in at the provider first)

The owner's account at the provider is new here and empty. Which path depends on input 3:

- **Nothing to keep in the pilot** (only test or smoke data): the owner signs in at the provider (step 6, item 5) and creates a fresh org. Nothing else to do.
- **An org with data to keep**: the account that owns it must become the owner's provider identity. There is no Ludy command for that, and an invite cannot make an owner (it grants `admin`, `member` or `viewer`; only an owner promotes), so the old owner's account would be stuck behind a sign-in that no longer exists. The way that keeps every membership, role and audit row is to give the **existing** account row the new identity, once, **before** the owner's first DOS sign-in. It rewrites an account's identity key in the production database, so it needs the owner's separate, explicit approval, and the Platform PO runs it, never a code session:
  1. Inputs: the old owner's account (its email in `ludy_kernel.user_account`, the old `issuer` and `subject` read from the row) and input 11. The old pilot sign-in of that account stops working at the `UPDATE`; the API still names the bundled Supabase Auth until step 5, and nobody can reach the provider's identity here before that, so the check below cannot race a sign-in.
  2. On the database host, as the admin login, in one transaction (save the first `SELECT`'s output privately before the `UPDATE`: the rollback needs the old `issuer` and `subject`; the `UPDATE` writes no audit row, so the Platform PO also notes the change, with the account id and the time but no address, on #2704), check first that exactly one row matches and that no account exists for the new identity (an account created by an earlier sign-in would collide on `UNIQUE (issuer, subject)`; if one exists, stop and ask the Platform PO: it can only be an account made by an earlier sign-in, and removing it is a separate approval):

     ```sql
     BEGIN;
     SELECT id, email, issuer, subject FROM ludy_kernel.user_account WHERE lower(email) = lower('<old owner email>');  -- one row
     SELECT count(*) FROM ludy_kernel.user_account WHERE issuer = '<provider issuer>' AND subject = '<provider sub>';          -- 0
     UPDATE ludy_kernel.user_account SET issuer = '<provider issuer>', subject = '<provider sub>', email = '<provider email>'
       WHERE id = '<id from the first SELECT>' AND issuer = '<old issuer>' AND subject = '<old subject>';             -- UPDATE 1
     COMMIT;
     ```
  3. Then the owner signs in at the provider and finds the org, with the same role. The old pilot login of that account is gone with the old issuer.

Do not link identities any other way (no other table, no copied rows). An owner who also wants a second owner promotes them in Settings, Members once signed in, with a second factor (input 7).

## Step 5. The API's settings

**By the deploy** (opt-in): in the `pilot` GitHub environment itself (never at repository or organization level, which fall back into every environment) define `DEPLOY_IDP_ENVIRONMENT=pilot`, the variables `DEPLOY_IDP_AUTH_ISSUER`, `DEPLOY_IDP_AUTH_JWKS_URL`, `DEPLOY_IDP_PUBLIC_AUTH_URL`, `DEPLOY_IDP_PUBLIC_AUTH_ANON_KEY` and the optional `DEPLOY_IDP_AUTH_OAUTH_PROVIDERS`, `DEPLOY_IDP_AUTH_HOSTED_LOGIN_URL`, `DEPLOY_IDP_AUTH_HOSTED_LOGIN_TOKEN_URL`, `DEPLOY_IDP_AUTH_HOSTED_LOGIN_NAME` (each becomes the line of the same name without the `DEPLOY_IDP_` prefix, as in the table below), and `DEPLOY_IDP_AUTH_ALLOWED_EMAILS` as a **secret** of the same environment (addresses are private), then run the deploy (a release tag, or a re-run of the last one). The deploy checks every value first, asks the provider for its keys and `/health`, keeps the dated copy of step 1, sets and removes exactly the lines of the table below (a line of an optional setting that the environment does not define is removed too), leaves every other line alone, recreates the API, the worker and the prober, and puts the copy back if the release does not become ready or its smoke test fails. Which values pass, what the log says, and how a rollback restores the file: [deploy.md](deploy.md#identity-provider-settings-in-the-deploy-2704). A value outside the allowed shapes (a hosted-login address with a query, an issuer and keys on different origins, an IP address) cannot go this way: use the manual path.

The deploy's `DEPLOY_IDP_*` settings do not carry `AUTH_OAUTH_CLIENT_ID`, `AUTH_SIGN_IN` or `AUTH_OAUTH_NAME` yet (a follow-up of #4704 adds them to the deploy and `deploy.sh`); until then the OAuth lines below are set by hand, after the deploy wrote the others, and the API recreated once more.

**By hand:** in the API host's `.env` (mode 600) set exactly:

| Line | Value |
|---|---|
| `AUTH_ISSUER` | input 4's issuer |
| `AUTH_JWKS_URL` | input 4's JWKS address |
| `PUBLIC_AUTH_URL` | input 4's Auth URL |
| `PUBLIC_AUTH_ANON_KEY` | input 4's publishable key |
| `AUTH_SESSION_CHECK` | `jwt` |
| `AUTH_UPSTREAM_URL` | empty (`AUTH_UPSTREAM_URL=`): no bundled proxy |
| `AUTH_ALLOWED_EMAILS` | input 9, comma separated (exact addresses; `@domain` entries allow a whole domain) |
| `AUTH_OAUTH_CLIENT_ID` | input 14's client id (a UUID). The kernel accepts that client's access tokens and refuses every other OAuth client's, including the provider's other Apps |
| `AUTH_SIGN_IN` | `oauth`: the sign-in screen shows only the button (no password form, sign-up or reset). The boot refuses it unless `AUTH_OAUTH_CLIENT_ID` and an https `PUBLIC_AUTH_URL` are set and none of `AUTH_UPSTREAM_URL`, `AUTH_HOSTED_LOGIN_URL`, `AUTH_OAUTH_PROVIDERS` is |
| `AUTH_OAUTH_NAME` | the button's words ("Continue with ..."), for example the provider's product name; at most 40 characters |
| `AUTH_HOSTED_LOGIN_URL`, `AUTH_HOSTED_LOGIN_TOKEN_URL`, `AUTH_HOSTED_LOGIN_NAME` | leave unset (input 15) |
| `AUTH_OAUTH_PROVIDERS` | leave unset with `AUTH_SIGN_IN=oauth` (input 13 is for the form path): comma separated provider ids, each a "Continue with ..." button under the form. Needs `AUTH_SIGNUP_POLICY` unset or `open`, as above |
| `AUTH_SIGNUP_POLICY` | remove the line or set `open`: the kernel refuses `invite_only` and `allowlist` without the bundled proxy, and the boot fails. Sign-up is the provider's to restrict |
| `AUTH_SIGNUP_ALLOWED_DOMAINS` | remove the line |
| `PROBER_AUTH_URL` | remove the line: it then follows `PUBLIC_AUTH_URL`, so the prober asks the provider's `/health` (with the publishable key) instead of the proxy that no longer exists |

Leave `AUTH_JWT_SECRET` and the other lines alone. Then recreate the API, the worker and the prober in the stack directory (`docker compose up -d api worker prober`; the prober keeps its old `PROBER_AUTH_URL` until it is recreated and would alert on the proxy that no longer exists; with the `COMPOSE_FILE` of [The pilot layout](deploy.md#the-pilot-layout)). A boot failure names the setting (the container exits; `docker compose logs api`): fix it or roll back (below), never loosen a check.

## Step 6. Verify

All of these, from outside the server, and the owner's sign-in (item 5) only after steps 4 and 5:

1. `GET https://api.ludy.vn/api/config` answers `authUrl` = the provider's Auth URL and `authAnonKey` = the publishable key.
2. `GET https://api.ludy.vn/readyz` answers `{"ready":true}`; `/healthz` answers 200.
3. Without a token, `GET https://api.ludy.vn/api/export/ledger.xlsx` and `GET https://api.ludy.vn/api/files/00000000-0000-0000-0000-000000000000` still answer 401.
4. A token from the **old** bundled Auth (an existing member's browser) now gets 401 and the app shows the sign-in screen.
5. The owner signs in at `https://app.ludy.vn`: with `AUTH_SIGN_IN=oauth` the sign-in screen shows one button, which goes to the provider's own page and comes back to `https://app.ludy.vn/oauth-login/callback` signed in (a person whose provider account has a second factor enrols and verifies it in Ludy's Settings as before; the app refreshes the session at once after the verification, so approvals still work); without it, with the provider address (input 9) and password or a provider button (input 13). The app opens with the org of step 4 (a fresh owner of nothing sees the empty start screen). If the sign-in screen shows an error, read the first red line of the browser console and network tab: a blocked request means step 3 did not take; 401 from the API means `AUTH_ISSUER` or `AUTH_JWKS_URL` do not match the token (compare the token's `iss` claim); 403 `ACCOUNT_NOT_ALLOWED` means the address or its case is not in `AUTH_ALLOWED_EMAILS` or the provider reports it unverified.
6. An account at the provider whose address is **not** on the list (the owner's second address, or a colleague's test account) signs in at the provider and then gets "This account is not allowed" from Ludy on every screen; no account is created (the members list shows nobody new).
7. With the OAuth App (input 14): a token issued by the provider to **another** of its OAuth Apps, for the owner's own account, is refused with `401 OAUTH_CLIENT_TOKEN_REFUSED` by the API (any authenticated request, for example `me/get`); the provider's operator produces such a token from a test App. After an hour (the provider's token lifetime) the session still works without a new sign-in (the refresh at the OAuth token endpoint). A sign-out ends the session at the provider (`/logout?scope=local`).
8. `pnpm pilot:check -- --url https://api.ludy.vn` run by a person on the host's checkout: "Sign-up limited" passes through `AUTH_ALLOWED_EMAILS`. The probe does not follow the Auth URL to another host, so its two Auth lines that read the settings answer "check by hand"; the by-hand checks are inputs 6 and 7 above. It sends no sign-up to the provider.
9. The prober reports healthy within its interval, with no Auth alert.

## Rollback

If the deploy wrote the settings and the release did not become ready, it has already put the dated copy back. Otherwise (or to go back after a good deploy): remove `DEPLOY_IDP_ENVIRONMENT` (and the other `DEPLOY_IDP_*` settings) from the `pilot` environment, then `deploy.sh rollback` of the release that wrote them restores the copy while it is still the current release; a later release leaves the file as it is, so restore step 1's lines by hand then. By hand: restore step 1's lines in `.env` (`AUTH_ISSUER`, `AUTH_SESSION_CHECK`, `AUTH_UPSTREAM_URL` unset or `http://auth:9999`, `AUTH_SIGNUP_POLICY=invite_only`, `AUTH_SIGNUP_ALLOWED_DOMAINS`, `PROBER_AUTH_URL`), remove `AUTH_JWKS_URL`, `PUBLIC_AUTH_URL`, `PUBLIC_AUTH_ANON_KEY`, `AUTH_ALLOWED_EMAILS`, `AUTH_OAUTH_PROVIDERS`, `AUTH_OAUTH_CLIENT_ID`, `AUTH_SIGN_IN`, `AUTH_OAUTH_NAME` and `AUTH_HOSTED_LOGIN_*`, and recreate the API, the worker and the prober. If step 4's update ran, first undo it the same way (the same transaction with the old and new values swapped, one row), or that account keeps the provider identity and cannot sign in at the old Auth. The old sign-ins work again at once: the bundled Auth never stopped and no data changed. `VITE_AUTH_URL` may stay (it only allows one more origin in the policy); remove it and rebuild only if the owner wants. Accounts created at the provider stay there, and their Ludy accounts stay (empty or in the org they joined); a person removed from an org by mistake is re-invited.

## Limits to know

- **Sign-outs and bans at the provider take effect when the access token expires**, at most the provider's token lifetime (ADR-0028, section 3). Approving, posting and member changes confirm the session live with the provider first.
- **`AUTH_ALLOWED_EMAILS` is as strong as the provider's email confirmation** (input 6). The kernel refuses a token that says its email is unverified; one that omits the claim passes.
- **A sign-in without a second factor is `aal1`.** A user with MFA at the provider is asked for the code by the app at once, but the kernel enforces it only for approvals, posting and member changes (R3) until the provider states the enrolment in the token (ADR-0028, section 3; gate T1).
- **The provider's other OAuth Apps share its keys.** Their tokens carry the same signing key, audience and role as Ludy's; Ludy refuses them by `client_id` (ADR-0028, amended 2026-11-24). A token the provider's own web app holds for a browser session carries no `client_id` and is accepted as before, for the same person: `AUTH_ALLOWED_EMAILS` decides who may use the pilot.
- **A second-factor verification issues a token without the client id.** Supabase Auth does this on the OAuth session (ADR-0028, fact 11), and the kernel refuses such a token; the app refreshes the session at the OAuth token endpoint right after the verification, which returns a token with the client id and the second factor. A request sent in the instant between the two can be refused once (401 `OAUTH_CLIENT_TOKEN_REFUSED`, which signs the person out of Ludy); the pilot check of step 6 covers it with the real provider.
- **One issuer per deployment.** Running the bundled Auth and the provider side by side needs a different design and is not part of this runbook.
- A provider button takes the user to that provider (not to the provider's own login page) and back through the provider's Auth, so the account is the same account there. The OAuth App (input 14) is the path that shows the provider's own sign-in page. With buttons on, the allow-list is only as strong as each enabled provider's email verification and the provider's automatic identity linking: every listed provider must issue verified emails (input 13).
- Provider buttons need `AUTH_SIGNUP_POLICY=open` behind the bundled Supabase Auth, which opens self-sign-up for every method; against a remote provider (this runbook) sign-up is the provider's to restrict.
- **Taking someone away with the list.** Removing an address from `AUTH_ALLOWED_EMAILS` refuses their next sign-in token, and since #3223 also every use of a Ludy extension token or MCP grant that account already holds (403 `ACCOUNT_NOT_ALLOWED`, no database write; the email checked is the one Ludy saw at the account's last sign-in). Restart the API after changing the list. An open stream ends with its access token's expiry, not at once, and an MCP wake-up webhook already set up for that account is still sent (ids and amounts only) until the account is disabled or the grant revoked. To cut an account off immediately or for good, also disable it ([user-disable.md](user-disable.md)) or remove them from the org.
