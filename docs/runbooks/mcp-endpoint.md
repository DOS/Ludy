# The MCP endpoint (Ludy as the gate for AI apps)

Decision: [ADR-0051](../adr/0051-vys-brain-is-a-dos-claw-agent-ludy-is-the-gate.md) decision 2 and [ADR-0032](../adr/0032-oauth-authorization-server.md). Tracking: issue #2975.

What it is: a standard remote MCP server at `PUBLIC_URL/mcp` (Streamable HTTP, stateless) and the OAuth 2.1 authorization server that guards it, both inside the Ludy API. An owner or admin connects an AI app (Claude, ChatGPT, Gemini CLI, OpenClaw, DOS Claw, your own agent) by pasting the MCP address into it; the app sends them to Ludy's own consent page; they pick the org and allow. The app then reads what the tools offer, with the rights of the person who allowed it, and nothing else. A connection **reads only**, with one exception an owner or admin must tick on the consent page and that only a company connection can hold: writing Social post drafts for a person to review (below). Its read tools are `ludy_about` (the org's name and the connection's own details), `ludy_parties_list` (customers and suppliers), `ludy_invoices_list` (recorded sales and purchase invoices), `ludy_signals`, the two Social reads, the Meetings reads (a company connection only) and the twelve Engage reads below (#3860).

Ludy runs without it: it is off unless you turn it on.

## Turn it on

1. Make the signing key (ES256) and keep it like any secret (never in git). One way, with Node:

   ```bash
   node -e "const {generateKeyPairSync,randomBytes}=require('node:crypto');const k=generateKeyPairSync('ec',{namedCurve:'P-256'}).privateKey.export({format:'jwk'});console.log(JSON.stringify({keys:[{...k,alg:'ES256',use:'sig',kid:'k-'+randomBytes(4).toString('hex')}]}))"
   ```

2. Make the cookie secrets: `openssl rand -base64 48` (one or more, comma separated; the first signs, the others still verify).
3. Set `OAUTH_SERVER=on`, `OAUTH_JWKS=<the JSON>` and `OAUTH_COOKIE_KEYS=<the secrets>` for the API. `APP_URL`, when you set it, must be `PUBLIC_URL`'s own origin: the consent page and the authorization server's interaction cookie share the API's origin in this step (a deployment with the app on another origin cannot turn it on yet; the API refuses to start and says so).
4. Restart the API. `GET PUBLIC_URL/.well-known/oauth-protected-resource/mcp` and `/.well-known/oauth-authorization-server` answer.

To rotate the key: add the new key to the set (first), restart, and remove the old one after 10 minutes (the life of an access token). Refresh tokens are opaque and are not tied to a key.

## Connect an app

Step by step for Claude and ChatGPT, with what is verified and what is not: [Connect Claude and ChatGPT](mcp-connect-claude-chatgpt.md).

Give the app the address `PUBLIC_URL/mcp`. It discovers the rest (protected resource metadata, then the authorization server metadata), registers itself (dynamic client registration or a client ID metadata document), and sends you to `PUBLIC_URL/oauth/interaction/<id>`. Sign in as usual, choose the org (only orgs where you are owner or admin are offered), read the list, allow. The name an app shows is the one it gave itself; the page shows the address the browser returns to, which is the fact to check.

## What it can and cannot do

- **What the two data tools return, and never return** (owner decision 2026-11-11; the privacy review of each is the comment on its query, and `apps/kernel/test/mcp-data.db.test.ts` pins it). An AI app connected to the org sees the customer data the person who allowed it sees, as the HubSpot and Twenty MCP servers show theirs. `ludy_parties_list`: id, company or person, name, the company a person works at, **email, phone, address and tax code**, the day recorded, and `sourceTrust` (who put the row in: `external` means a visitor, a public booking form or an import typed it, so a client should trust it less). `ludy_invoices_list`: series and number, date, sale or purchase, the party's name and **tax code**, subtotal, VAT, total, currency, **the description of each line** (the first 20, with the line count) and whether the invoice was voided and **why**. Never: salaries or payroll, bank account records (a number someone typed into a line description or a void reason is free text and does come through), member-private notes, todos and results, anything a `sensitive` query covers, an invoice line's amounts or accounts, the file an invoice came from. Every text value is cut to one plain line (no line break, no separator, no bidi control, no invisible tag character). Both return the newest 50 at most and say when there are more (`total`, `truncated`); there is no search and no paging yet. **The consent page tells the person plainly that the app will see customer and invoice details, contact information included, and that this leaves Ludy and is kept by that app's provider under its own terms: connect only an app you would give the same information to.** A name or a line description is text a person, a customer, a supplier's invoice or a visitor wrote: it is data for the app, and the tool says so, but a language model can still be fooled by text, so treat an `external` row and any invoice text as untrusted.
- **`ludy_signals`** (Vy V4 and V5, #2967 and #2969; query `kernel.mcp.signals`, read only, no input). It runs the kernel's four cross-app rules as the grant, in its sealed context, and answers `{ items, checked, unchecked }`. `items` are the rules' own Home items (a kind, a severity, a message key with numbers, an in-app link, an amount in VND and a day when there is one): ids, days and amounts only, no name and no text anyone typed, each item passing the strict item schema before it leaves. `checked` names the rules that could look; `unchecked` lists the rules that could not, each with a reason, `partial_view` (the grant's books are only in part in view, for example a branch-limited accountant, so a line refused) or `not_available` (a line has no read, refuses the grant, or has no data yet: the supplier bank change rule stays `not_available` until a supplier bank account record and a supplier-payment flow exist; the unanswered conversation rule (#3124) is always `not_available` over a grant, because a grant's context reads no conversation, so an empty list never says that no customer is waiting). **An empty `items` means nothing was found among `checked`, never that everything was looked at.** Each item counts one row against the grant's daily row budget; the audit row of the call names the tool; the tool and the reads behind it never read an audit table (`apps/kernel/test/mcp-signals-source.test.ts` holds the sources to it). The signal wake-ups of the webhook run since step S5: the worker has its own entry into a company grant's context (`enter_mcp_wake_company_context`, the worker's login alone), so the rules are asked as the grant, five minutes apart; a member-bound grant is never asked (see [the wake-up webhook](mcp-wake-webhook.md)).
- **`ludy_social_posts_list` and `ludy_social_review_queue`** (#3227; queries `social.mcp.posts` and `social.mcp.review_queue`, read only, scope `ludy.read`; design in [the Social plan, section 3.8](../plan/social.md); `apps/kernel/test/social-mcp.db.test.ts` pins them). An AI app sees the Social posts the person who allowed it sees: per post its id, title, text (one plain line, at most 2,000 characters, `textTruncated` says when more was left out), link, status, `origin` (a person or an AI), `actorOrigin`, `tainted`, planned time and zone; per channel its name, provider, status, the text it goes out with, the time it goes out, when it was published and the public link, whether it was taken down and the error code of a failure. `ludy_social_posts_list` filters by status, channel and the time a channel goes out. `ludy_social_review_queue` answers two lists: `inReview` (channels waiting for an owner or admin to decide, the longest waiting first) and `aiDrafts` (AI drafts with a channel not yet sent to review and none waiting there). Never returned: internal comments, assignees, the author, approvals' comments, media files and their storage keys, channel tokens and settings, platform ids, metrics, archived posts. A post's text is data a person, a visitor, a web page or a model wrote, so the tools say so and cut it to one plain line.
- **`ludy_meetings_list` and `ludy_meeting_minutes`** (#3731, owner decision 2026-11-18, company grants only; queries `meetings.mcp.list` and `meetings.mcp.minutes`, read only, scope `ludy.read`; design and the Meetings PO's review on the issue; `apps/kernel/test/invariant/mcp-meetings-company.db.test.ts` pins the database side and `meetings-mcp-projection.db.test.ts` the output). An AI app connected for the **company** reads only the PUBLISHED minutes of meetings whose recorder shared them with the whole company (visibility `org`): per meeting its id, title, start, length, language and publish time; per minutes the text as plain lines (the template's headings are lines of it; at most 80 lines of 2,000 characters), the decisions (at most 30) and the action items (at most 50: title, who as it was said, the due date when one was matched, and `open` or `task_made`; an item that Ludy flagged, for example one holding a contact detail, is left out). The Truncated flags say when more was left out. **Never reachable:** a meeting for attendees only (even one the grantor recorded), a draft or an unpublished meeting, the transcript, the recorder's notes, translations, live lines, readers and who attended, consent records, the recording, speaker names, the template's name, how the meeting was recorded, any user id, and a meeting past its text period. An unknown id, such a meeting and another org's all answer the same not found. A **member grant reads nothing of Meetings**: the tools are not offered to it, the queries refuse it and its sealed context has no row of the module (the hold of 2026-11-13 stays; `mcp_member_table` names no Meetings table). The database holds the line first: the three read policies of `meeting`, `meeting_result` and `action_item` give the sealed company context (kind `mcp_company`) a row only for visibility `org`, the whole-org scope (`'*'` in `ctx_le_scope`, so an entity-limited context reads no org meeting) and, for results and items, a published row; since #3781 the meeting also needs a published result and a text period that has not ended, and an item must carry no flag (one definer, `crove_meetings.is_org_minutes_meeting`, holds the shared test; the kind itself is compared inline in the three policies, `ctx_verified() ->> 'kind'`, and no function names it). The consent page says it in plain words for a company connection. Everything returned is text people and an AI wrote: a client treats it as data. How an agent uses these tools, with two worked flows: [Vy and the Meetings tools](../guides/vy-meetings-mcp.md).
- **`ludy_meetings_open_actions`** (#3804, owner decision 2026-11-18, company grants only; query `meetings.mcp.open_actions`, read only, scope `ludy.read`; `apps/kernel/test/invariant/meetings-mcp-projection.db.test.ts` pins the output). One read of the action items still open across the meetings an app may already read, so a client can follow up on promises made in meetings without opening each meeting's minutes. It lists the PUBLISHED, unflagged action items that no task was made from, of meetings whose visibility is `org` and whose text period has not ended, the newest meeting first, at most 100 (`limit` 1 to 100, default 50). Per item exactly: `meetingId`, `meetingTitle`, `meetingStartedAt`, `title`, `owner` (the free text of who it was said to belong to, or null; never a user id), `dueDate` (an ISO day when one was matched, or null) and `status` (always `open`). The optional `dueBefore` (an ISO day) keeps only items with a due date before that day, so items with no due date are left out when it is set. `total` is how many exist and `truncated` is true when there are more than were returned. Every text is one plain line. **Never reachable:** a draft item, an item Ludy flagged (for example one holding a contact detail), an item already made a task, an item of an attendees-only, unpublished or expired meeting, another org's items, the transcript and any user id. A **member grant reads nothing of it**: the tool is not offered to it and the query refuses it. No database policy was added: the read policies of `meeting`, `meeting_result` and `action_item` named above are the line. Each item counts one row against the grant's daily row budget. The weekly digest or the follow-up reminder that uses it is the client's own skill, not Ludy's.
- **`ludy_meetings_series_open_items`** (#3837, the Meetings PO's direction of 2026-11-18 inside the owner's decision of the same day, company grants only; query `meetings.mcp.series_open_items`, read only, scope `ludy.read`; `apps/kernel/test/invariant/meetings-mcp-projection.db.test.ts` pins the output). The open action items of one SERIES of recurring meetings, so a client can follow up what carried over from week to week. The client names a meeting (a `meetingId` from `ludy_meetings_list`, `limit` 1 to 100, default 50); the tool lists the open items of every meeting in the same series that the grant may already read (published, shared with the whole company, text period not ended), the given meeting included, the newest meeting first. Per item exactly the keys of `ludy_meetings_open_actions` (`meetingId`, `meetingTitle`, `meetingStartedAt`, `title`, `owner`, `dueDate`, `status`), so items of different meetings can be told apart; the answer is `{ series, items, total, truncated }`, where `series` is false (and the list empty) when the meeting is in no series. **No series id leaves Ludy, in or out**: a meeting of the series that the grant may not read is left out and never counted or hinted at. A meeting that is unknown, of another org, attendees only, not published or past its text period answers the same not found as the minutes. The same limits as `ludy_meetings_open_actions` apply: an item already made a task is not listed (and no tool reads Tasks), drafts and flagged items are never listed, a member grant reads nothing of it. No database policy was added; it reads the `series_id` column of the meeting rows the policies already admit. Each item counts one row against the grant's daily row budget.
- **`ludy_meetings_decisions`** (#4016, the Meetings PO's direction of 2026-11-19 inside the owner's decision of 2026-11-18, company grants only; query `meetings.mcp.decisions`, read only, scope `ludy.read`; `apps/kernel/test/invariant/meetings-mcp-projection.db.test.ts` pins the output). The published decisions of recent meetings, so a client can answer "what did we decide this week" without opening each meeting's minutes. Input: `days` (7, 14 or 30, default 14; a meeting counts by its start) and `limit` (1 to 100, default 50). It reads the meetings the grant may already read (published, shared with the whole company, text period not ended) that started inside the window, the newest meeting first, and answers `{ items, truncated }`: per item exactly `meetingId`, `meetingTitle`, `meetingStartedAt` and `decision` (one plain line of at most 2,000 characters), each meeting's decisions in the order they were written and at most 30 of a meeting, as in the minutes. `truncated` is true when anything was left out (over `limit`, over 30 in one meeting, a line cut or dropped, or more than 100 meetings in the window); there is no total, since an exact one would mean reading every meeting. Nothing else of the minutes (summary, actions), no recorder or other user id and no transcript. A member grant reads nothing of it. No database policy was added: it reads the `decisions` column of the published result rows the policies already admit. Each decision counts one row against the grant's daily row budget.
- **`ludy_meetings_search`** (#4030, the Meetings PO's direction of 2026-11-19 inside the owner's decision of 2026-11-18, company grants only; query `meetings.mcp.search`, read only, scope `ludy.read`; `apps/kernel/test/invariant/meetings-mcp-projection.db.test.ts` pins the output and, with a canary word in every hidden place, that nothing outside the boundary can be found). A text search over the published minutes. Input: `q` (2 to 200 characters) and `limit` (1 to 50, default 10). It searches only what `ludy_meeting_minutes` can return of a meeting the grant may already read (published, shared with the whole company, text period not ended): the title, the first 80 summary lines (each cut at 2,000 characters), the first 30 decisions and the titles of the first 50 action items that Ludy did not flag, built with the same helpers, so text past those cuts cannot be confirmed by a search either (no yes-or-no on hidden text). **It does not use the in-app search** (`meetings.search`, which reads transcript lines by the caller's reader rights): the transcript, notes, drafts, translations, readers and attendees are never selected. The typed words are folded in code (lower case, Vietnamese marks and đ removed, like `crove_kernel.search_fold`) and **never reach the database**; at most 8 words count, every word must be the start of a word of one line (title, a summary line, a decision or an action title), and a query with no word of two characters or more answers the empty answer. At most the 200 newest readable meetings are searched. Answer `{ items, truncated }`: one item per meeting, newest first, `meetingId`, `meetingTitle`, `meetingStartedAt`, `field` (`title`, `decision`, `summary` or `action`) and `snippet` (one plain line of at most 200 characters around the first match); `truncated` is true when older meetings were not searched or more meetings matched than `limit`; no total. A member grant reads nothing of it. No database policy was added: it reads the three tables of the minutes under the policies that already admit them. The query text is not stored or logged by this code. A call counts at least one row against the grant's daily row budget (a search that finds nothing is not free), otherwise one per meeting returned.

Twelve read-only tools, each over a dedicated projection query that carries `mcp: { scope: 'ludy.read' }` and an explicit field list (the comment at the top of each query file is its privacy review; nothing here is a UI query exposed as it is). Every text a customer, a visitor or a platform wrote is cut to one plain line (a message keeps its line breaks, `plainText`) and the descriptions say it is data, never instructions. Pages are small and bounded; a call counts one row per row returned against the grant's daily budget (`MCP_GRANT_DAILY_ROWS`).

Who reads which thread is the database's (the sealed contexts of #3858 slice b): a company grant reads the whole org; a member-bound grant reads what its member may (a viewer and a member the comment threads, private messages and email only with `kernel.conversation.direct.read`, only the channels the member is limited to); an unreadable thread answers the same not found as one that does not exist. Leaves per thread: ids, kind, status, channel, the contact (name, the last four characters of the platform id, the linked customer, the sender address of an email), assignee id, times, intent, subject, a 160-character preview; per message: number, direction, who wrote it, the text (at most 4,000 characters), time, send state, hidden, removed, how many images. `tainted: true` on every thread and every customer message. Never returned: a message the author or the platform removed (no text, only `removed`), internal notes, drafts, composing markers, read marks, images, platform message ids, the customer's other threads, free-text search. Because every row of a member-bound read goes through a definer and a permission lookup (#3941 note N1) both reads stay small. `apps/kernel/test/engage-mcp-conversations.db.test.ts`.
  - **CRM** (company and member-bound grants for deals and quotes, module `crm`): `ludy_deals_list` and `ludy_deal` (`crm.mcp.deals`, `crm.mcp.deal`), `ludy_quotes_list` and `ludy_quote` (`crm.mcp.quotes`, `crm.mcp.quote`). The CRM tables carry the org policy only, so a member-bound grant reads the whole org's deals and quotes, as that member does in the app (#3941 note N3); narrowing members to their own deals is not here. Money is a decimal string in VND. A quote has its lines, notes, terms and the buyer's name and tax code; never its links or tokens, the buyer's address or email, stock item ids or who made it. `ludy_bookings_list` (`crm.mcp.bookings`, owner or admin only, so a company grant only: the tool is not offered to a member-bound grant and the query refuses one) lists confirmed and cancelled bookings, upcoming or past: the guest's name, email, phone and note are what a visitor typed (`sourceTrust: external`); never the meeting's join link, the host or the calendar event. `apps/kernel/test/engage-mcp-crm.db.test.ts`.
  - **Results** (a company grant's alone: money the org spends and the numbers of its channels; the channel limits of a member are not readable from a member-bound context): `ludy_social_metrics_summary` and `ludy_social_metrics_totals` (`social.mcp.metrics_summary`, `social.mcp.metrics_totals`: the latest counts of the posts published in the last `days` days, an excerpt of at most 160 characters, and the totals against the window before; counts only), and `ludy_ads_spend`, `ludy_ads_flags`, `ludy_ads_today` (`ads.mcp.spend`: the ad accounts and for one chosen account the spend by month, campaign (at most 50) and day over at most 93 days; `ads.mcp.flags` and `ads.mcp.today`: the pace, day and cost-per-result flags the Ads screen raises), and `ludy_ads_launches` (`ads.mcp.launches`, E4b #4147: the launches that have started, at most 50, with the Campaigns screen's held budget, last day and object status, for the ids the stop, pause, archive, lower-budget and shorten-schedule proposal tools take; no plan, platform id or change history; `apps/kernel/test/engage-mcp-launches.db.test.ts`). A company grant that holds `ludy.ads.draft` is also offered `ludy_ads_pages` (`ads.mcp.pages`, #4367: the org's active Facebook Pages, at most 50, an id and a plain-line name each and nothing else), so a draft saved with `ludy_ads_campaign_draft_save` can name the Page the ad runs as in `pageConnectionId` (every ad needs one; `apps/kernel/test/engage-mcp-results.db.test.ts`). Amounts are decimal strings in the account's own currency, never converted; campaign names come from the platform and are data (a fallback account name Ludy made, "Meta ad account <id>", leaves without the id). The totals list at most 50 channels a window (`channelsTruncated`). The consent page says in both languages what these reads show (`oauthConsent.scope.engageReads`, `engageReadsMember`). `apps/kernel/test/engage-mcp-results.db.test.ts`.

The conversation queries are named `kernel.mcp.*` so the invariant that keeps `kernel.conversation.*` and `kernel.inbox*` closed to a grant holds. Writes (E2) and proposals (E4) are separate steps; the wake events of E3 stay ids, types, dates and amounts only (#3941 note N4).
- **What a sealed grant context reads of Hộp thư and the CRM** (#3858 slice b, ADR-0051 decision 12, owner decision 2026-11-18/19; database side; the tools over it are the Engage reads below (#3860); `apps/kernel/test/invariant/mcp-grant-read.db.test.ts` pins the database side and `apps/kernel/test/invariant/mcp-conversation-reads.db.test.ts` the conversation reads). Migration `20270119100000` gives the sealed contexts of an MCP grant a read-only way into `crove_kernel.conversation` and `conversation_message` (their notes and contact identities follow the thread's row). A **company grant** (`mcp_company`, whole-org scope) reads every conversation of its own org, of every kind (comment thread, private message, email), the rights of the owner or admin who made it; a company context without the whole-org scope reads none. A **member-bound grant** (`mcp_member`) reads exactly what its member reads as a person, worked out in the database by `crove_kernel.conversation_access_mcp_member` from the sealed member: owner and admin everything; a member comment threads, and private messages and email only with `kernel.conversation.direct.read`, on the channels they are limited to; a viewer comment threads; a sealed member who is not a member of the org reads nothing. Attachments, AI drafts, composing markers and read marks stay closed to a grant. The CRM tables (party, deal, quote, booking) carry only the org policy, so a sealed context already reads its own org's rows and no other. **Nothing writes**: the new policies are read policies only, the write checks are the ones a person has, and `agent_write_guard` and the read-only query transaction refuse every write of the sealed contexts. The query layer (which columns leave) is a second, separate layer each line reviews. One thing to know: the mail row of a conversation reply (`mail_message`, source `kernel.conversation.reply`) follows the thread's visibility, so a grant that may read a thread may read the mail row of a reply in it (its recipient address, subject and the member's answer, which the thread's own message holds too).
- **Per-line write scopes** (#3858 slice c, ADR-0051 decision 11, owner decision 2026-11-18/19; `apps/kernel/test/invariant/mcp-write-scopes.db.test.ts` pins it). Beside `ludy.social.draft`, a company grant may hold `ludy.engage.write` (Hộp thư and CRM) and `ludy.ads.draft` (ads drafts). Each is a choice on the consent page: shown only when the client asked for it, only to an owner or admin consenting for the company, unticked by default, and tickable on its own; the grant holds exactly the ticked ones and always the read scope with them (the `agent_grant` CHECK and the grant definer say so; a member-bound grant never holds one). A write scope lets a call reach a command that declares it; **no command declares the two new scopes yet and no sealed write context exists for them** (`MCP_WRITE_CONTEXT_SCOPES` in the runtime lists the one that has it, the Social draft), so a grant that holds one still writes nothing and a command that declares one is refused (`FORBIDDEN`, rule `mcp_scope`) until its context and guard branch land (Engage E2, #3861). An R2 or R3 command under a scope will only ever become a proposal a person approves in Ludy (decision 10, a later slice). The **tool list is filtered** by the grant's role and scopes: a tool that names a write scope (`writeScope` on its descriptor) is listed, and callable, only for a company grant that holds it; a tool that is not read only and names none is never listed. The grants screen shows one badge per write scope.
- **The Engage R1 write tools** (epic #3857, E2, #3861, ADR-0051 decisions 10 and 11, owner decision 2026-11-19: Dy and Uy do the routine steps a person does; `apps/kernel/test/engage-mcp-write.db.test.ts` and `engage-mcp-write-tools.test.ts` pin the tools and `apps/kernel/test/invariant/mcp-engage-write.db.test.ts` pins the database side). Thirteen tools, listed and callable only for a company grant that holds the write scope; each runs one twin command as the grant, in the grant's sealed write context (migration `20270122190000`: kind `mcp_engage_write` for `ludy.engage.write`, `mcp_ads_draft` for `ludy.ads.draft`; no user, tainted, R1). The twins are separate commands (`kernel.mcp.conversation_assign|resolve|reopen|note|link_contact`, `kernel.mcp.party_create`, `crm.mcp.deal_create|deal_move|quote_save|quote_revise|next_step_done|next_step_snooze`, `ads.mcp.campaign_draft_save`) with the app's own input and handler, because `register()` opens `mcp` only to a command for owners and admins alone and the app's own commands are used by members. Tools: `ludy_conversation_assign`, `ludy_conversation_resolve`, `ludy_conversation_reopen`, `ludy_conversation_note`, `ludy_conversation_link_contact`, `ludy_party_create`, `ludy_deal_create`, `ludy_deal_move`, `ludy_quote_save`, `ludy_quote_revise`, `ludy_next_step_done`, `ludy_next_step_snooze` (engage scope) and `ludy_ads_campaign_draft_save` (ads scope: a NEW draft marked `origin ai`, never an edit; the plan fields it sets are the draft's `ai_fields`). - The grant lasts at most 89 days. An owner or admin sees and disconnects every connection in Settings, "Connected AI apps"; the person who allowed one may disconnect their own through the same screen's command.
- **Member grants** (a member connecting their own AI app, ADR-0051 decision 2; the org's owner turns this on in Settings, off by default): a person may hold five live ones per org, and sees only their own. A registration that never obtained a grant expires after a day. The provider's routes answer CORS only for the origins in `MCP_ALLOWED_ORIGINS`, and refuse a body over 64 KB.

## When something does not work

| Symptom | Check |
| --- | --- |
| The API will not start with `OAUTH_SERVER=on` | The message names the setting: `OAUTH_JWKS` must be ES256 private keys with a `kid`, `OAUTH_COOKIE_KEYS` at least 32 characters, `APP_URL` the same origin as `PUBLIC_URL`. |
| The app says the server cannot be discovered | `PUBLIC_URL` is the address the app reaches (https, behind your proxy with `TRUSTED_PROXY_HOPS` set); the two `.well-known` addresses answer JSON. |
| The consent page says the request is lost | The interaction lives 10 minutes and its cookie belongs to the API's origin: open the page in the same browser the app started it in, and do not sign in through another origin. |
| An app is refused after it worked | The connection was disconnected, expired (89 days), the person who allowed it lost the owner or admin role, or the org or the deployment stopped AI. Look at the audit rows `kernel.mcp.call` and the list in Settings. |
| 429 | The grant spent its minute (`MCP_GRANT_PER_MINUTE`), has too many calls in flight, or (a write tool, "Too many changes just now") spent its writes (`MCP_GRANT_WRITES_PER_MINUTE`). |
| tool error "The daily limit of rows ..." | The grant read its day's rows (`MCP_GRANT_DAILY_ROWS`); it starts again at midnight UTC. Raise the setting only if the owner asks. |
