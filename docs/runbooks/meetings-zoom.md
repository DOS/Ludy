# Zoom cloud recordings in Ludy Meetings: set up and operate

A member connects their own Zoom account in Settings and Ludy then lists the cloud recordings Zoom finished, as suggestions. Nothing is downloaded until the member presses "Import" on the Meetings tab ([plan, section 6.3](../plan/meetings-integrations.md)). It is **off by default**: without the two settings below there is no Zoom button and no Zoom adapter.

> **Facts to re-check on the first live run.** This page and the code were written from Zoom's own API documentation and tested only against fixtures and a stub transport; no real Zoom account has been used yet. The scope names, the exact redirect rules and the file types are the facts to confirm against Zoom's current pages when the first self-hoster connects, and the result goes on [#3175](https://github.com/DOS/Ludy/issues/3175).

## What the operator does (once per deployment)

1. In the [Zoom App Marketplace](https://marketplace.zoom.us/) (Develop, Build App) create an **OAuth** app of the **User-managed** kind. A user-managed app reads only the recordings of the Zoom user who connected it. Do not use an account-level or Server-to-Server app: it could read every user's recordings, and a recording in Ludy belongs to the member who imported it.
2. Set the **Redirect URL for OAuth** to `APP_URL/meetings/oauth/zoom/callback` and add the same address to the app's allow list. `APP_URL` is the address of the web app (the same value the calendar connections use; see [split-app-api.md](split-app-api.md)), not the API's.
3. Give the app these scopes (granular names; Zoom's older "classic" names for the same read access also work): `cloud_recording:read:list_user_recordings`, `cloud_recording:read:list_recording_files` and `user:read:user`. The last one lets Ludy read the member's Zoom profile: the connection is keyed by the Zoom user id (so it survives a change of email) and named by the email address. Nothing that writes or deletes is asked for.
4. Put the app's Client ID and Client Secret in the settings of the API **and** the worker (the worker needs them to renew tokens): `ZOOM_OAUTH_CLIENT_ID` and `ZOOM_OAUTH_CLIENT_SECRET`. Set both or neither; the server refuses to start with one. `CREDENTIAL_KEY` must be set too ([credential-key.md](credential-key.md)), or the connect answers 503 before a member leaves for Zoom.
5. A private app in your own Zoom account needs no Zoom review and works for the people in that account at once. A public listing goes through Zoom's own review, which has no published length; that is the operator's choice and not needed for one company.

## What a member sees

- Settings, **Security** tab, card "Kết nối nền tảng họp" (Meeting platforms): a button "Kết nối Zoom" appears only where steps 1 to 4 are done. It opens Zoom's own permission screen; the member approves there and comes back to a page that says which account was connected.
- Ludy then lists the member's recordings of the last 14 days within a few minutes, and the member imports one with a click. The listing prefers the **audio-only** file Zoom makes. A recording that has only a video file imports only where the **media sandbox** (`crove-media`, `MEDIA_URL`) is running ([meetings-video-import.md](meetings-video-import.md)); without it that recording fails with "no audio". The Settings card says this in plain words.
- Zoom keeps **cloud recordings only on a paid plan**, and only if the host turned cloud recording on. A free account lists nothing. A recording made in several segments (the host stopped and started the recording) imports as one: the worker fetches the segments in order, one connection at a time, and the media sandbox (`crove-media`, `MEDIA_URL`) joins their audio into one Opus (video segments only when Zoom made no audio-only file); no segment is kept. It needs the sandbox; without it that recording fails with "no audio". **Deploy crove-media before the kernel** when you upgrade: a kernel that sends a recording in parts to a crove-media with no join endpoint (HTTP 404) fails that recording at once with "no audio" and does not retry. The parts together may not pass half of the sandbox's `MEDIA_MAX_INPUT_BYTES` (1 GiB by default; 150 MiB for audio parts), less a few bytes of framing; a recording over it is refused before any part is downloaded. One extra Zoom API call (the meeting's file list) is made for a single-file import, to find out whether the recording is in parts. The whole recording counts against the same size cap as a single file. [Unverified until the first live run (#3178): that Zoom lists segments of one recording with the same `recording_type` and ordered by `recording_start`.]
- A recording with **no audio file and no video file but Zoom's own transcript** (Zoom keeps only the transcript, for example after the recording files were deleted) can be imported as that transcript: the worker downloads the WebVTT file from `zoom.us` through the same guard as a recording (8 MB at most, one finished transcript file only), reads the lines and the speakers (a cue reads `Name: what was said`), and the member reads and corrects them as a draft labelled "Zoom", with no model call and no cost. [Unverified until the first live run (#3178): that Zoom's transcript names its speakers this way.] A recording that has a video file and no audio-only file still needs the media sandbox for its audio, even when Zoom made a transcript; using the transcript instead there is a later step.
- The member can disconnect in Settings at any time: Ludy forgets the access and deletes the list of suggestions. Meetings already imported stay. To also take the app away on Zoom's side the member removes it in Zoom (Marketplace, Manage, Added Apps).

## How the access is kept

- Zoom access tokens last about an hour, so the worker renews a token shortly before it expires (10 minutes ahead), under a row lock, and **saves the new refresh token Zoom rotates in** on every renewal. If Zoom will not renew the grant (the member removed the app, or the refresh token expired) the connection is marked expired and Settings says "connect again"; nothing else changes. See the plan's [6.1](../plan/meetings-integrations.md) for the renewal rules.
- The tokens are sealed with the credential key for the member's org, platform and account, and only the worker opens them. No screen, answer, log line or audit row carries a token, the code or Zoom's own words; an error is a short code.
- A connect attempt (the state) lasts 10 minutes, works once and only for the member who started it. The one-time code is exchanged before anything is stored, and a refused code uses the attempt up.
- The only hosts Ludy calls for Zoom are `zoom.us` and `api.zoom.us`; a recording file is downloaded only from `zoom.us` or one of its subdomains, and the member's token goes only to the first host of a download.

## When something fails

| What the member sees | Likely cause | What to do |
|---|---|---|
| Zoom says the redirect address is invalid | The Redirect URL in the Marketplace app is not exactly `APP_URL/meetings/oauth/zoom/callback`, or is not on the allow list | Fix it in the Marketplace app; no Ludy change |
| "The platform refused the code ... or does not let Ludy read the account address" (`OAUTH_CODE_REJECTED`) | The code was used or expired, the redirect address differs, the client secret is wrong, or the app lacks `user:read:user`. Ludy does not check the recording scopes at connect: a missing `cloud_recording` scope shows later as an empty or failing list | Check the app's scopes and the two settings, then connect again |
| "The platform is not answering" (`OAUTH_PROVIDER_FAILED`) | Zoom was unreachable or answered something unexpected | Try again; the log line names a short code, never a token |
| No "Kết nối Zoom" button | One of the two settings is missing, `CREDENTIAL_KEY` is not set, or the Meetings screens are hidden (the Meetings module is off, so Settings does not show the card) | Check the settings of the API |
| "Connection expired: connect again" | Zoom would not renew the grant | The member connects again; it is the same row |
| The list stays empty | A free Zoom plan, cloud recording off, no recording in the last 14 days, or the files are still processing | Nothing in Ludy to fix |

## The webhook: a suggestion appears at once (optional)

Without it the listing runs about every 10 minutes and the member's "Refresh" button asks for one at the next pass. With it, Zoom tells Ludy when a cloud recording finishes and Ludy lists that member's recordings again at the worker's next pass (within a minute or so). The webhook is a **doorbell and never data**: the notice carries a download address, a download token and the host's email, and Ludy reads, stores and logs none of them. A recording is still fetched only through the member's own token after the member's click.

1. In the Marketplace app, open **Feature**, **Event Subscriptions**, turn them on and add a subscription with the **Event notification endpoint URL** `<API address>/api/meeting-platform/zoom/webhook`. This is the address of the **API** (`PUBLIC_URL`), not of the web app: it is the one route here that Zoom's servers call. Subscribe to the events **Recording Completed** (`recording.completed`) and **Recording Transcript Completed** (`recording.transcript_completed`); Ludy ignores every other event with a 200.
2. Copy the app's **Secret Token** (Event Subscriptions page) into `ZOOM_WEBHOOK_SECRET_TOKEN` (API; 16 to 200 characters, no spaces; it needs the OAuth app settings above) and restart the API, then press **Validate** in Zoom. Zoom sends a URL validation challenge and Ludy answers it. Zoom may or may not sign that challenge, so Ludy answers it either way, but only for a `plainToken` of letters, digits, `-` and `_` (at most 128): a challenge shaped like a signed message gets no answer, because the answer would be a valid signature for that message.
3. To rotate the token: generate a new one in Zoom, move the old value to `ZOOM_WEBHOOK_SECRET_TOKEN_PREVIOUS`, set the new value in `ZOOM_WEBHOOK_SECRET_TOKEN`, restart, and remove `_PREVIOUS` once Zoom signs with the new one. A notice signed with either is taken meanwhile; the challenge always uses the current one.

What the route does, in this order: refuses a body over 64 KiB before reading it; checks the signature (`x-zm-signature`, HMAC-SHA256 over `v0:<x-zm-request-timestamp>:<body>`, constant time) and that the timestamp is within 5 minutes of the server clock (so keep the server's clock right; a retry refused for age is recovered by the normal listing); then reads the event. A missing, wrong or stale signature all get the same `401`. A verified notice for a recording clears the "last listed" time of the **active Zoom connections of that host**, matched by the Zoom user id Ludy stored when the member connected (compared in lower case on both sides, although Zoom's ids are case-sensitive: two Zoom users whose ids differ only in case would share a key, and the only effect is an earlier listing of the other member's connection with that member's own access; decision of #4011), and answers `200 {"ok":true}` whether or not any connection matched, so nobody can learn which accounts exist. The route does not exist unless `ZOOM_WEBHOOK_SECRET_TOKEN` is set and the Meetings module is installed, and a connection of an org that switched Meetings off is left alone. Refused requests and unsigned challenges share a per-address limit (120 a minute, `429` after that); verified notices are never counted. Nothing of a body, a token or a signature is logged.

If the webhook never rings: check that the URL is the API's and reachable from the internet, that the secret matches, that Zoom shows the endpoint as validated, that the server clock is right, and that the member connected after the connect step existed (a connection is matched by the Zoom user id of the host, so the member must be the host of the meeting). A notice that arrives while the worker is listing that same connection can be overtaken by the listing's own timestamp; the next regular listing, at most 10 minutes later, still brings the recording in. Zoom documents seconds for `x-zm-request-timestamp`; Ludy also accepts milliseconds. That, the exact event names and the retry rules are facts to confirm against Zoom's current pages on the first live run, as for the rest of this page.
