# The invariant suite

The invariant suite is the set of security tests that CI runs from the base branch on every pull request that touches a protected path, so a PR cannot weaken the checks that judge it. [AGENTS.md](../../AGENTS.md), "Protected paths", holds the rules that apply on every task; this page lists what the suite covers, test by test, and how CI runs it. The last section lists every protected path in full.

Read this page before you change, add or move anything under a `test/invariant/` directory or a pgTAP gate file `supabase/tests/database/_*.test.sql`, and when a red `Invariant suite (from base)` job names a test you need to understand.

## How CI runs it

From `.github/workflows/protected.yml`, on every PR:

  - `Invariant suite (from base)`: detects protected paths with the base branch's copy of the script; if any changed, deletes the PR's `test/invariant/` files, `vitest.invariant.config.ts` and `supabase/tests/database/_*.test.sql`, checks out the base branch's copy over the PR's tree and runs it against the PR's code on PostgreSQL 17. It fails if any invariant test fails or is skipped, and if the base copy is no longer on disk with the base content after the install or after the run (PR code runs in both; the files are compared, without git, with the sha256 list and the file types taken before any PR code ran, so a file swapped for a symlink or a hard link fails too, #1647, #1786). On every PR it fails if a `node_modules` path (directory, file, link or submodule) is committed, and on a protected-path PR also if one appears under a test directory during the run: there it could shadow a dependency of the suite (#1644). The ordinary `ci` job still runs the PR's own copy.
  - `Security review (agent)`: on protected-path PRs, the security reviewer agent reviews security, tenancy, authorization and money and posts one `## Security review (agent)` comment (verdict plus findings by severity) and inline comments. Without the `ANTHROPIC_API_KEY` secret (owner action, #95) it passes with the notice "Security review pending owner setup"; until then the session runs its own independent security review on protected-path PRs. On a fork PR that touches protected paths (forks never get the secret) it fails with "Maintainer security review required". The reviewer reads the policy from the base branch (`git show <base>:AGENTS.md`).
  - With no protected path changed, both jobs pass in seconds and say so in the job summary.

## Reading the result

- **Reading the result:** open the job summary. It lists the protected files, whether the base or the PR copy of the suite ran, which invariant files the PR changed (those changes take effect only after merge), and after the run the counts and each failed or skipped test with the first lines of its error. Without a browser, read the failures from the PR's error annotations or from the log of the job's "Report the failed tests" step (#498). A red invariant job means the PR's code breaks an invariant as `main` defines it: fix the code, do not edit the test in the same PR. Changing an invariant on purpose turns this job red by design (the base copy still expects the old behavior); that is an owner decision: say so in the PR, and once the owner approves it in the coordinator's chat, the coordinator merges over the red check after the security review (the owner never merges), or the change lands in two steps with a test that accepts both behaviors first. Blocking findings from the reviewer are fixed before merge, like any must-fix review item.
- A PR that edits `protected.yml` or `tools/ci/` runs its own edited workflow, so the reviewer and the session check those changes with extra care.

## The protected paths in full

Read this when you need to know whether a file is protected. `tools/ci/protected-paths.mjs` is the authoritative list; this is its description from AGENTS.md before the 2026-11-02 restructure.

- **What is protected** (plan §10, G6; the list is `tools/ci/protected-paths.mjs`, matched on paths only): `.github/workflows/**`, `.github/CODEOWNERS`, git hooks, `.gitattributes`, `.gitmodules`; the deploy pipeline (`tools/deploy/**`, it runs on the production host); agent harness and policy (`.claude/settings*`, `.claude/hooks/**`, `.claude/agents/**`, `.mcp.json`, `CLAUDE.md`, `AGENTS.md`); dependencies and test runners (every `package.json`, `pnpm-lock.yaml`, `pnpm-workspace.yaml`, `.npmrc`, `vitest*.config.ts`, `vitest*.workspace.ts`, and in any directory `playwright*.config.ts`, `global-setup.ts`, `global-teardown.ts`); the gate itself (`tools/ci/**`, every `test/invariant/` directory); the command runtime (`packages/kernel-runtime/src/**`); database context guards and the migration runner (`packages/db/src/index.ts`, `packages/db/src/context/**`, `packages/db/src/migrate.ts`); approval policy and identity (`packages/kernel/src/approval.ts`, `identity.ts`); authentication and the HTTP edge (`apps/kernel/src/auth*.ts`, `sessions*.ts`, `http.ts`, any `auth/` directory); every change under `supabase/migrations/` and `supabase/shared-variants/` (the SQL `migrate` runs in a shared database in place of a migration, #2284); `_*.test.sql` and the modules' pgTAP runner `packages/db/test/pgtap.db.test.ts`; `LICENSE`, `CLA.md`, `agent-autonomy.md`.
